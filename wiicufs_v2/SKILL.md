# WIICUFS — 写"说人话"的技术课程文档

> **WIICUFS** = What If I Catch Up From Scratch
> 一套让"没学过的人"也能看懂的技术教程写作方法。
> 本文件是规则速查；完整案例、模板、踩坑实录见 [reference.md](reference.md)。

## 什么时候用

当你需要写一套**多讲次的技术教程**（如"从零学 X"系列），面向**没学过这个领域**的读者，要求他们能看懂、能练手、能信任内容正确性、能单纯凭借它通过正经的诸如考试，考核，科研等实际应用考验时。

典型场景：
- 给自己补一门没上过的课
- 给团队写技术入门系列
- 从零开始恶补一门甚至"不知道自己不知道什么"但又对当前极其重要的领域或课程
- 给社区写开源教程
- 期末考试(绝望)(绝对不能想当然，绝对不能漏或跳知识点)(不能口语和散装到完全用不了)(要前因后果但是不要像写小说一样卖关子讲口水话)(要系统地组织)

## 核心原则（违反即 bug）

1. **说人话，但不因说人话而漏知识点**：不用官话、不堆砌不知所云的术语，能用大白话说清的概念不用学术黑话。不退化成博物馆导游——系统、不啰嗦、不卖关子、有清晰主线。说人话 ≠ 省略知识点：该完备的必须完备，该系统的必须系统。

2. **严禁空降概念**：新术语第一次出现，当场给三样之一——① 完整解释；② 一句话"它是干啥的 + 现在只需知道这么多 + 第 N 讲细讲"；③ 明确标注"这个词现在可以跳过"。作者脑里有上下文会无意识跳过定义，读者第一次见没有这个上下文——这是长篇教程最易违反的一条。

3. **不藏着掖着**：列出的每样东西至少配"它长这样、这意味着什么、完整方法论心智模型、是否先记下来后面再说"。不要直接甩一堆没解释的东西让读者自己观察。不要因为后面会细讲就在前面故意藏着不说——前面的知识点要完备，作业过饱和了是正常的。可以总结提炼心智模型、总结干货时不要吝啬：不因为前文讲过了就不给，也不因为要给心智模型就让前文故意不讲。

4. **丰富具体例子**：倾向工程/数值计算方向，能跑的代码优先。抽象概念用数值实验坐实。规则已知时用物理/公式而非 ML 去学——白费力气还加误差。

5. **每讲结尾留作业**：可自验证——数值题附答案和验算方法，代码题附能跑的验证。**两条硬约束**：① 答案只能用**已教过的概念**（答案里出现未教语法＝隐形空降）；② 答案块**一律平铺**为"**参考答案**："段写在题下，**禁用 `<details>`/HTML 折叠**——部分渲染环境会整体报错，未闭合会吞掉后续内容。

6. **标明理解角度、深度，并给心智模型**：每个概念不只说"是什么"，还要给：
   - **理解角度**：这个知识是"工具"（要会用）还是"清单"（遇到时打勾验证）还是"直觉"（建立感觉就行）？
   - **理解深度**：要能推导？要能复述？只要知道"有这回事 + 什么时候找它"？
   - **方法论或心智模型**：什么时候怎么用、怎么找方向——否则退化成让人无所适从的字典。

7. **任务驱动、应用出发**：每讲围绕一个**能跑的小任务**展开，概念只在"任务卡壳"的那一刻引入，**不上来罗列原理**。三个配套：① 每讲开头一张"本讲怎么走"脉络图 + 每节末尾一句"下一站"；② 每讲一个可立即编译运行的成品程序开场；③ 同一课程的多讲尽量串成一条故事线。（C++ 课程因"先入为主背概念"被读者投诉后全量重写三讲，详见 reference.md §1.7）

8. **解释的位置和解释本身同样重要**：概念的解释如果放在读者产生疑问的位置**之后**，效果等于空降。审查时按"读者第一次遇到的顺序"走一遍，不是按作者的知识组织顺序。读者自然产生的疑问必须在疑问产生的当页或前一页就有答案。

9. **地毯式覆盖优先于组织优雅**：写一个概念时，主线任务只决定"必须讲什么"，但读者要的是"这个东西的**完整形态**"——标准形式之外每段能不能换、能不能嵌套、能不能被外部控制、重复了会怎样、好习惯坏习惯、和相邻概念的边界。作者按"任务需要"写，读者按"完整形态"问——两者错位，所以**先地毯式列出完整形态再组织**，不许只写主线需要的部分，不许把规范/边界/习惯当"讲外内容"默认略去，更不许等读者问一个补一个。判断"这里先理解即可后面会讲"的时机是写到具体那一讲的时候，不是现在——现在只有"写全"和"不写"两个选项，没有"故意藏一半"。（C++ 课程 A36–A42 七连追问实录见 reference.md §1.8）

10. **先定读者心智模型再动笔**：写作前先明确假想读者是谁（要简明手册的 / 完全踏入陌生领域、不知道自己不知道什么的 / 基本覆盖的技术入门 / 带旧语言经验来的），每一讲都要写一条该讲假想学生的**认知思维链条**——它是**学习者第一人称的自我梳理**（"我以为……等等，那岂不是……"），不是作者用第三人称替他做的总结。统一五段骨架、好坏对照、写法详见 reference.md §1.9。链条是参考，不因迁就读者发散的思维就放弃系统化知识组织讲解——迁就混乱的结果是更多的混乱；但也要顺着一个健康的认知链条。

11. **问答/破误段不是教学容器**：任何新知识（定义、定理、记号、结论）必须**先由正文系统节完整教过**；"想当然/常见问法"类段落只做**对答案与校准表态**，首句须声明"本节零新知识"，且逐条锚定正文系统小节；问法数量**由内容决定**，禁止固定套路数字（如一律三个）。就地破误按原则 8 守在疑问自然产生的位置附近，不攒成一节逃避。同理，问答笔记（如 QnAnExperience）是索引不是正文的替身——正文有漏必须回填正文。写法与事故实录见 reference.md §1.11。

## 写作流程：先 PLAN 后逐讲（两遍走）

```
第 0 步：建 PLAN.md（课程目录最前面，agent 自用，不给读者）
  → 明确目标 + 读者画像（哪一种学生，见原则 10）
  → 骨架大纲（每讲的任务/回答什么/成品）
  → 对照领域完整知识清单做地毯式覆盖检查（见下方"地毯式覆盖检查"）
  → 每讲的假想学生认知思维链条（五段骨架，见 reference.md §1.9）
  → 前置 PLAN 疯狂穷举发散知识点，留下的作为兜底，后文反复对照
  → PLAN.md 模板见 reference.md §1.10
第 1 遍：逐讲写作
  1. 预写讲义初稿（每讲先定"本讲的任务"再定内容；每个新机制按"完整形态六问"展开）
  2. 写验证脚本，实跑验证预写结论（不限 Python：C/C++ 用"生成源码→编译→运行→对照"同样成立）
  3. 对照预想 vs 实测：一致→嵌入实测数据；偏差→插入"我说过头了"段（见 reference.md §3）
  4. 概念空降检查 + 作业答案未教概念检查（对照已教清单逐句查）
  5. 格式自检：`<details>` 残留计数为 0；引号风格一致；编号体系单一；同一数据只有一个权威出处
  6. 归档验证脚本（移入课程脚本目录、加编号前缀，不删）、把本讲新概念/公式补进 AA_一览、回填 PLAN.md 状态、同步导览页
第 2 遍：交付前全课程回查
  1. 对照 PLAN.md 的地毯式覆盖清单逐项打勾，没写上的要么补、要么给出"不写"的理由
  2. 按读者顺序从头走一遍，查漏（尤其"规范/边界/习惯/被控形态"这类主线外内容）
  3. 对照每讲思维链条：每一个疑问是否都能在正文找到答题小节、且答题位置不晚于该疑问自然产生处；AA_一览批量对账去重
```

## 地毯式覆盖检查（写任何机制前必过）

**每个新机制（语法/概念/工具）第一次教时，按"完整形态六问"逐项回答**——这是 C++ 课程被读者连环追问后总结的清单，每问对应一类真实被漏：

| 问 | 内容 | C++ 课程被漏的实例 |
|---|---|---|
| ① 标准形态 +**每一部分的自由度** | 标准写法是什么；每一段/每个位置能不能换成别的、空着 | for 三段全是自由位（i+=2/多条件/for(;;)） |
| ②**嵌套与组合** | 能不能嵌套自己；能不能和别的结构混着套；什么绝对不能嵌套 | if/for/while 可随意嵌套，唯独函数定义不能 |
| ③**被控与外部打断** | 能不能被外部逻辑控制；谁让它变假/停；被控形态叫什么 | while 的标志驱动/忙等，循环体不自己前进 |
| ④**重复与共存** | 重复写会怎样；能不能改名复用；听谁的 | 声明/定义/赋值三件套、遮蔽、重载、ODR |
| ⑤**规范：好习惯/坏习惯** | 怎么用是对的；怎么用会埋坑 | 循环/函数的习惯表、垃圾值纪律 |
| ⑥**相邻边界与对比** | 和相邻概念的区分；和读者旧语言（如 Python）的行为差异 | 函数不能嵌套 vs 控制流可嵌套；Python 参数也改不动外面 |

**执行纪律**：六问的答案不一定都进正文（有些可以标"认识即可"），但**必须在写作时逐问过并做出决定**——"决定不写"和"没想到"是两回事。决定记录在 PLAN.md。

## 数值验证闭环

每一讲含数值实验的，必须跑脚本验证——不能只靠"我觉得这个结论对"。流程、脚本规范、完整范例、C/C++ 变体、多尺度实测、抽样波动实测见 reference.md §2。

## 预写偏差修正

预写结论 ≠ 实测结果时，不要偷偷改掉——诚实记录偏差描述 + 实测数据 + 根本原因。完整案例见 reference.md §3。

## 概念首次出现即定义

写的时候每个新术语首次出现就给定义，以及括号内英文专有名词，不要等"后面再补"。不要因为它解释起来复杂就直接避开不讲，不然会漏知识点。跨讲引用要回追根：第 03 讲用了第 01 讲没定义的缩写 → 回第 01 讲补定义。高危类型清单见 reference.md §4.2。

## 多讲次课程的结构

```
课程目录/
├── PLAN.md             agent 自用的写作计划（目标/读者画像/大纲/地毯覆盖清单/每讲思维链条），不给读者，但必须先于一切存在
├── 00_导览.md          课程大纲、讲次列表、前置、学完能做什么、达标判据
├── 01_xxx.md           第一讲
├── 02_xxx.md           第二讲
├── ...
├── scripts/            验证脚本归档：文件名 = 讲次-序号_原名（如 lec03-01_verify_gd_loss.py）
├── NN_与X的接口.md     固定的最后一讲：和后续/应用的连接点
└── AA_一览.md          全课程附录：关键概念/公式/中英对照的严谨字典（编号用 AA，永不重排）
```

**AA_一览**——附录字典：收关键概念/术语/缩写（中文名 + 英文/缩写 + **说清"是什么"的定义** + 首次出现讲次 + 理解层次）和关键公式（符号各指什么 + 适用条件 + 出处讲次）。它是字典，不必像正文循循善诱从头讲，但**每条都要说清"是什么"**——只说"怎么样/怎么用"不说"是什么"是鬼话，禁止。首次出现的叙述性教学仍在对应讲正文里（原则 2 不空降），AA 提供措辞严谨的字典形态。每讲交付后把本讲新概念/公式补进 AA。

**每一讲的固定结构**：开头（前置/预计时间/本讲回答什么/本讲目标）→ 脉络图 → 正文（任务驱动的成品开场，说人话，概念不空降，例子偏工程/数值）→ 本讲小结 → 掌握度自测（行为化 checklist）→ 作业（可自验证）。**目标行不是可选项**：每讲开头必须让读者一眼看到"这讲结束我能做出什么、怎么判断我达标了"。详细模板见 reference.md §5。

## 多课程并行时的文件边界

- 所有操作限定在当前课程目录内
- 严禁修改全局 README.md 或 JOURNAL.md（其他并行任务在维护）
- 只改课程专属文档（课程 00_导览.md + 系列总览.md）
- 验证脚本建在课程目录内，不污染工作区根目录

## 常见踩坑（精简版，完整实录见 reference.md §6）

| 坑 | 症状 | 解法 |
|---|---|---|
| 文件快照失效 | 凭会话内印象 SearchReplace，匹配失败或改到旧版本 | **改前必 Read 当前版本**，不信任会话内的旧印象 |
| GBK 编码 | `UnicodeEncodeError: 'gbk' codec` | 脚本 print 里不用 ✓、²、³ 等 Unicode 符号，改 `[OK]`、`^2`、`^3` |
| PowerShell 剥引号 | `wsl -e bash -lc "..."` 嵌套引号/heredoc 被毁 | 复杂命令写成脚本文件再执行；测试源文件用 Write 工具生成 |
| 解释在错误位置 | 解释存在但排在读者需要它的位置之后，读感等同空降 | 按"读者第一次遇到的顺序"审查，不按作者知识组织顺序 |
| 只写主线、漏周边 | 读者连环追问补漏 | 每个新机制过"完整形态六问"；先有 PLAN.md 地毯清单再动笔 |
