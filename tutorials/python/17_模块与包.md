## 0. 场景：一个 800 行的 `main.py`

第 05 讲提过"巨无霸单文件"，第 15 讲给了拆分顺序：先拆函数，再拆文件。这一讲就是"拆文件"的具体做法。

拆之前先想清楚一件事：**模块不是一个语法单位，是一个职责单位。** 一个模块应该能用一句话说清"它负责什么"：`data.py` 负责读写数据，`report.py` 负责输出，`main.py` 负责串起来。如果一句话说不清，说明还得再拆。

## 1. `import` 到底做了什么

### 1.1 模块顶层的代码会被执行

建一个 `tools.py`：

```python
print("tools 模块被加载了")

def double(x):
    return x * 2
```

再建一个 `main.py`：

```python
import tools
print("在 main.py 里，tools.__name__ =", tools.__name__)
print("double(5) =", tools.double(5))
```

跑 `python main.py`，实测：

```text
  [python main.py] 退出码=0
    tools 模块被加载了
    在 main.py 里，tools.__name__ = tools
    double(5) = 10
```

第一行 `tools 模块被加载了` 出现在 `main.py` 的任何输出之前——因为 `import tools` 这个动作**把 `tools.py` 整个文件从头到尾执行了一遍**，只是把执行结果（函数、变量）绑到 `tools` 这个名字下面。

这一条解释了很多现象：

- 模块顶层的 `print`、文件读写、网络请求，**只要被 import 就会执行**；
- 所以"模块顶层只放定义（函数、类、常量），不放动作"是一条硬纪律；
- 库的作者常常在顶层做很重的事（加载模型、连数据库），这就是为什么 `import` 某个库会卡好几秒。

### 1.2 同一个模块只会执行一次

再 `import tools` 一次，不会再跑一遍那个 `print`——模块对象被缓存起来了。Python 把已加载的模块存在 `sys.modules`（一个字典）里，第二次 import 直接查表返回。

这条的后果：**模块里的全局变量会成为"单例"状态**，多个文件 import 同一个模块，看到的是同一份变量。这既方便（共享配置）也危险（谁改的说不清）。

## 2. `__name__` 与 `__main__`

### 2.1 两个值

在 `tools.py` 末尾加一段：

```python
if __name__ == "__main__":
    print("直接运行 tools.py，__name__ =", __name__)
    print("double(21) =", double(21))
```

直接运行它：

```text
  [python tools.py] 退出码=0
    tools 模块被加载了
    直接运行 tools.py，__name__ = __main__
    double(21) = 42
```

而上一节 `python main.py` 的输出里**没有**这两行。原因是：

- 直接运行时，这个文件是"主程序"，`__name__` 是 `'__main__'`；
- 被 import 时，`__name__` 是模块名 `'tools'`。

### 2.2 为什么必须写这个 if 块

它解决一个具体问题：**同一个文件，既要能被别的模块 import，又要能自己单独运行来测试。**

- 不写 if 块：import 时那段测试代码也会跑，别人用你的模块就被迫看你的调试输出；
- 写了 if 块：import 时 `__name__` 是 `'tools'`，块里的代码不执行；直接运行时才执行。

所以"能跑"和"能当模块用"是两件事，这个 if 块是两者的分界线。

### 2.3 一条纪律：模块顶层只放定义

```python
# data.py —— 好的形态
import csv

def read_rows(path):
    ...

def write_rows(path, rows):
    ...

if __name__ == "__main__":
    # 只在这里做"手动测试"
    print(read_rows("demo.csv"))
```

反面是"顶层直接读文件、直接打印、直接发请求"。那样别人 import 你的模块时，会莫名其妙地执行一堆动作，甚至报错——而他只是想用其中一个函数。

## 3. 三种 `import` 写法

```text
  [三种写法] 退出码=0
    json.dumps: {"a": 1}
    as 别名   : {"a": 1}
    from 直接拿: 3.0 3.1416
```

| 写法 | 拿到什么 | 调用时怎么写 | 适用 |
|---|---|---|---|
| `import json` | 整个模块对象 | `json.dumps(...)` | 最常用，来源一目了然 |
| `import json as js` | 整个模块，换个名字 | `js.dumps(...)` | 模块名太长、或避免与本地名字冲突 |
| `from math import sqrt, pi` | 只有这几个名字 | `sqrt(9)` | 名字短、用得多、无歧义 |

### 3.1 `from ... import` 的代价

`from math import sqrt` 之后，`sqrt` 就是一个普通名字，**看不出来源**。代价有三种：

- **命名冲突**：你本地也有个 `sqrt`，后写的覆盖前写的，而且不报错；
- **可读性**：读代码的人看到 `dumps(...)`，得往上翻才知道它来自 `json`；
- **可替换性**：想换成别的同功能函数，得改所有调用处。

实践建议：**优先 `import 模块`**，让 `json.dumps` 这种带来源的写法成为默认；只在名字很短、用得很频繁（`math` / `os.path`）时才用 `from ... import`。

### 3.2 别用 `from 模块 import *`

`from json import *` 会把模块里所有公开名字倒进当前命名空间。你无法知道多了哪些名字，也无法知道哪个覆盖了哪个。除非是交互式实验，否则不用。

## 4. 包：把模块装进一个目录

### 4.1 目录 + `__init__.py`

```text
项目/
├── main.py
└── pkg/
    ├── __init__.py
    ├── a.py
    └── b.py
```

`pkg` 是一个包：**一个目录，里面有一个 `__init__.py`**。`__init__.py` 可以是空文件，它的存在本身就是"这是一个包"的标志。

实测 `import pkg.a` 与 `from pkg import b`：

```text
  [import pkg.a / from pkg import b] 退出码=0
    pkg/__init__.py 被执行了
    pkg/a.py 被加载
    b 看到 a.VALUE = 来自 a
    pkg.a.VALUE = 来自 a
```

执行顺序：先 `pkg/__init__.py`，再被导入的那个模块。`from pkg import b` 会执行 `pkg/b.py`，而 `b.py` 里的 `from pkg import a` 又会执行 `a.py`。

### 4.2 `__init__.py` 里放什么

两种做法，各有理由：

- **留空**：最省事，包只作为"目录分组"存在；
- **暴露接口**：把常用的名字从子模块里提上来，让调用方写 `from pkg import read_rows` 而不是 `from pkg.data import read_rows`。

第二种的代价是：`__init__.py` 里 import 什么，`import pkg` 时就会执行什么（第 1 节的规则），包会变"重"。

### 4.3 绝对导入与相对导入

- 绝对导入：`from pkg import a`，从包的根写起，清楚；
- 相对导入：`from . import a`、`from ..utils import f`，`. ` 表示当前包，`..` 表示上一级。

相对导入只在包内部有意义，且对"从哪运行"很敏感。本课程建议：**项目内部一律用绝对导入**，只在库的深层模块里偶尔用相对导入。现在知道 `.` 和 `..` 这两个写法存在就够。

## 5. `python -m` 与入口

### 5.1 `__main__.py`

给包加一个 `__main__.py`：

```python
print("pkg/__main__.py 被当作入口执行")
from pkg import a
print(a.hello())
```

用 `python -m pkg` 跑：

```text
  [python -m pkg] 退出码=0
    pkg/__init__.py 被执行了
    pkg/__main__.py 被当作入口执行
    pkg/a.py 被加载
    hello from a
```

`-m` 的意思是"把这个包当成程序来跑"：Python 先执行包的 `__init__.py`，再执行 `__main__.py`。

### 5.2 两种跑法的区别

| 跑法 | 执行哪个文件 | `sys.path[0]` 是 | 包内绝对导入 |
|---|---|---|---|
| `python main.py` | `main.py` | `main.py` 所在目录 | 正常 |
| `python -m pkg` | `pkg/__main__.py` | 当前工作目录 | 正常 |
| `python pkg/__main__.py` | 那个文件 | `pkg/` 目录 | 可能失败 |

第三行是最容易踩的：文件能跑起来，但 `from pkg import a` 会失败——因为 `sys.path[0]` 变成了 `pkg/`，Python 在 `pkg/` 里找不到 `pkg` 这个包。

结论：**包内部要用绝对导入，就用 `python -m 包名` 启动；不要直接 `python 包/内部文件.py`。**

### 5.3 推荐的项目入口

```text
项目/
├── main.py            ← 给使用者：python main.py
└── mypkg/
    ├── __init__.py
    ├── __main__.py    ← 也可以用：python -m mypkg
    └── core.py
```

两种入口指向同一套逻辑，谁都不会迷失。第 26 讲会把这个结构正式化（`pyproject.toml` + 入口命令）。

## 6. `sys.path` 与 `ImportError` 的排查

### 6.1 `sys.path` 是 import 的搜索路径

```text
  [sys.path 前四项] 退出码=0
      sys.path[0] = 'C:\\Users\\...\\Temp\\tmpca_imq9q'
      sys.path[1] = '...\\python312.zip'
      sys.path[2] = '...\\DLLs'
      sys.path[3] = '...\\Lib'
```

- 第一项是**入口脚本所在目录**（用 `-m` 时是当前目录）；
- 接着是标准库的位置；
- 再往后是 `site-packages`（第三方包装的地方，第 03 讲）。

所以"我自己写的 `tools.py` 为什么能被 import"的答案很朴素：**它和入口脚本在同一目录，而那个目录在 `sys.path` 第一项**。

这也解释了两类常见事故：

- 在 A 目录运行、脚本在 B 目录 → 找不到同目录的模块；
- 本地有个文件叫 `random.py`，把标准库 `random` 遮住了 → `import random` 拿到的是你的文件。

### 6.2 三种 `ImportError` 对应三种原因

| 报错 | 意思 | 常见原因 |
|---|---|---|
| `ModuleNotFoundError: No module named 'xxx'` | 压根没找到这个模块 | 没装、拼错、不在 `sys.path` |
| `ImportError: cannot import name 'yyy' from 'xxx'` | 模块找到了，但里面没有这个名字 | 名字拼错、版本不同、循环导入 |
| `ImportError: ... partially initialized module ...` | 模块正在加载中就被要求提供名字 | 循环导入 |

排查顺序：先看**模块名和文件名是否一致**（`import tools` 对应 `tools.py`），再看**当前工作目录**，再看**是不是装了**（`python -m pip list`），最后看**有没有同名文件遮蔽**。

### 6.3 一个具体的坑：文件名与标准库同名

把文件命名成 `json.py`、`random.py`、`types.py`、`email.py`，会遮住标准库同名模块。症状很怪：报错信息里说的全是标准库的东西，但你根本没改标准库。

判据：报错栈里出现的文件路径是**你自己目录下的那个文件**，就说明是遮蔽。改文件名即可。

## 7. 循环导入

两个模块互相 import，会怎样？实测：

```text
  [循环导入] 退出码=1
      Traceback (most recent call last):
        File "...\circular_demo.py", line 1, in <module>
          from cyc.x import x_func
        File "...\cyc\x.py", line 1, in <module>
          from cyc.y import y_func
        File "...\cyc\y.py", line 1, in <module>
          from cyc.x import x_func
      ImportError: cannot import name 'x_func' from partially initialized module 'cyc.x'
      (most likely due to a circular import) (...\cyc\x.py)
```

过程是这样：

1. 开始加载 `cyc.x`，执行到第一行 `from cyc.y import y_func`；
2. 于是去加载 `cyc.y`，它执行 `from cyc.x import x_func`；
3. 此时 `cyc.x` **只执行到第一行**，`x_func` 还没定义；
4. 于是报"不能从半初始化的模块里导入名字"。

### 7.1 一个必须说清的细节：不是所有互相 import 都会报错

我第一版脚本写的是 `from cyc import x` / `from cyc import y`（导**子模块**），实测**不报错**、正常退出。

原因：导子模块时，Python 只是把"已经在加载中的那个模块对象"给你，哪怕它只执行了一半；而 `from cyc.x import x_func` 要的是**模块里的某个名字**，那个名字此刻还不存在。

所以准确说法是：**循环导入的报错取决于"你导的是子模块还是名字"，以及"那个名字在对方第几行定义"。** 这比"互相 import 一定炸"准确得多，也解释了为什么有些循环导入能跑、有些不能。

### 7.2 三种修法

- **拆公共部分**：把两边都要用的东西移到第三个模块 `common.py`，双方都 import 它（最干净）；
- **延迟导入**：把 `import` 挪进函数体内，等真正调用时才加载；
- **只导模块不导名字**：`import cyc.x` 然后 `cyc.x.x_func()`，避开"半初始化时取名字"。

## 9. 安装名与导入名可能不同

`pip` 装的名字和 `import` 的名字不一定一样：

| 安装 | 导入 |
|---|---|
| `pip install pillow` | `import PIL` |
| `pip install opencv-python` | `import cv2` |
| `pip install scikit-learn` | `import sklearn` |
| `pip install beautifulsoup4` | `import bs4` |

这不是错误，是历史原因（包名与模块名是两套命名系统）。本机没有装这些包，所以这里只列事实、不做实测。遇到"我明明装了却 import 不到"，第一反应应该是**查官方文档写的 import 名**，而不是重装。

## 10. 这一讲留下的东西

- `import` 会执行模块顶层代码，且只执行一次（缓存）。
- `__name__` 直接运行时是 `'__main__'`，被导入时是模块名；`if __name__ == "__main__"` 是"能当模块"与"能单独跑"的分界线。
- 模块顶层只放定义；动作放函数里，手动测试放 if 块里。
- 三种 import 写法各有适用；优先 `import 模块`，别用 `import *`。
- 包 = 目录 + `__init__.py`；入口用 `__main__.py` + `python -m 包名`。
- `sys.path[0]` 是入口脚本所在目录，这决定了"自己写的模块能不能被导入"。
- 循环导入只有在"从半初始化模块里取名字"时才报错；修法是拆公共部分或延迟导入。
- 标准库按用途查，不必背；安装名与导入名可能不同。

下一讲处理程序出错这件事：异常。你会看到 `try` 的四段到底各管什么、为什么不能裸 `except`、`finally` 里的 `return` 会怎样、以及怎么读一条完整的 traceback。

## 小结

- `import tools` 会打印 `tools 模块被加载了`（实测），因为整个文件被执行了一遍；模块顶层不要放动作。
- 直接跑 `tools.py` 时 `__name__` 是 `__main__`（实测），被 import 时是 `tools`。
- `import 模块` / `as` / `from 模块 import 名字` 三种写法实测输出一致；`from` 写法看不出来源。
- 包里先执行 `__init__.py` 再执行被导入模块（实测）。
- `python -m pkg` 执行 `pkg/__main__.py`（实测），且 `sys.path[0]` 是当前目录。
- `sys.path[0]` 实测是本项目目录，之后是标准库目录，`site-packages` 更靠后。
- 循环导入实测报 `ImportError: cannot import name 'x_func' from partially initialized module 'cyc.x'`；但导子模块的循环不报错。
- 标准库 14 个常用模块按用途列表；`pillow` → `PIL` 这类"安装名 ≠ 导入名"是常态。

## 作业

**Q1.** 你把 `read_rows`、`write_rows` 从 `main.py` 拆到 `data.py`，`main.py` 里加了 `import data`。运行后屏幕上多了一行你不认识的输出。最可能的原因是什么？

**参考答案：** `data.py` 顶层有 `print`（或读文件、发请求等动作），`import` 时整个文件被执行，那行输出就出现了。

修法：把动作移进函数，只在 `if __name__ == "__main__":` 块里保留手动测试（本讲第 1、2 节）。判据是：import 一个模块不该产生任何输出与副作用。

**Q2.** 下面两个文件，`python main.py` 输出什么？`python utils.py` 又输出什么？

```python
# utils.py
print("加载 utils")
def add(a, b):
    return a + b
if __name__ == "__main__":
    print("utils 作为主程序运行")
```

```python
# main.py
import utils
print(utils.add(1, 2))
```

**参考答案：** 两种跑法各有一行差异：

`python main.py` 输出：

```text
加载 utils
3
```

`python utils.py` 输出：

```text
加载 utils
utils 作为主程序运行
```

区别只在 `__name__`：被 import 时是 `'utils'`，直接跑时是 `'__main__'`，所以后者会多打印一行。注意 `加载 utils` 两次都有——它是顶层代码，与被不被 import 无关。

**Q3.** 你有目录结构 `proj/app.py` 与 `proj/pkg/__init__.py`、`proj/pkg/core.py`。在 `pkg/core.py` 里写 `from pkg import utils` 时：用 `python app.py` 能跑，用 `python pkg/core.py` 报 `ModuleNotFoundError: No module named 'pkg'`。为什么？怎么改？

**参考答案：** 因为 `sys.path[0]` 是"入口脚本所在目录"：

- `python app.py`：入口在 `proj/`，`sys.path[0]` 是 `proj/`，能找到 `pkg`；
- `python pkg/core.py`：入口在 `pkg/`，`sys.path[0]` 是 `proj/pkg/`，这一层下面没有 `pkg`，所以找不到。

改法：不要直接跑包内文件，改成 `python -m pkg.core`（在 `proj/` 下执行）；或者给包加 `__main__.py`，用 `python -m pkg` 作为入口（本讲第 5 节）。

**Q4.** 解释这条报错的含义，并给出两种修法：

```text
ImportError: cannot import name 'y_func' from partially initialized module 'cyc.y'
(most likely due to a circular import)
```

**参考答案：** 含义：`cyc.y` 正在加载、还没执行完，就有人要从它里面取 `y_func`，而这个名字还没被定义。

两种修法：

1. 把两边都要用的部分抽到第三个模块（如 `cyc/common.py`），`x` 和 `y` 都只依赖它；
2. 延迟导入：把 `from cyc.y import y_func` 移到真正调用它的函数体内，等函数被调用时才 import。

补充：如果一方只写 `import cyc.y`（导模块而不是导名字），通常不会触发这个错误——但那样调用时要写 `cyc.y.y_func()`。

**Q5.** 你写了一个文件叫 `json.py` 放在项目里，之后 `import json` 就报一些奇怪的错（错误信息指向你的文件）。为什么？怎么修？

**参考答案：** 文件名与标准库模块同名，`sys.path[0]`（当前目录）优先于标准库目录，所以你自己的 `json.py` 遮住了标准库的 `json`。所有 `import json` 拿到的都是你的文件。

修法：把文件改名（如 `my_json.py`）；如果确实要写"和标准库同名"的包装，就必须用包结构把它们隔开，并在文档里写清。

判据：看 traceback 里的路径——出现你自己目录下的 `json.py`，就是遮蔽。

**Q6.** 判断对错并说明理由：
(a) `import` 一个模块会执行它的全部顶层代码；(b) 同一个模块被 import 两次会执行两次；(c) `from 模块 import *` 是推荐写法；(d) 包必须有一个 `__init__.py`。

**参考答案：** 四条逐一看：

- (a) 对。本讲实测：`import tools` 打印了 `tools 模块被加载了`。
- (b) 错。模块对象会被缓存（`sys.modules`），第二次 import 直接返回缓存，不再执行。
- (c) 错。`import *` 会把一堆名字倒进当前命名空间，无法判断来源、容易覆盖，除交互式实验外不用。
- (d) 对（常规包而言）。目录里有 `__init__.py` 才是常规包；Python 3.3+ 还有"命名空间包"不需要它，但那属于进阶用法，本课程统一按"有 `__init__.py`"来写。
