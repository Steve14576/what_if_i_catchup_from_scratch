## 0. 场景：装了三个编辑器，跑代码还是靠终端

你的桌面上可能同时有 VS Code、Cursor、Qoder。每个都能打开 `.py` 文件、都有一堆按钮；但真正要跑代码时，你还是切回终端敲 `python main.py`。编辑器对你来说只是一个"带颜色的记事本"。

问题不在编辑器不好用，而在**你还没把它接上你的环境**。编辑器要帮你跑代码、补全、调试，中间有一座必须搭的桥：**它得知道用哪个 Python**。桥搭好了，这三件事才会从"能用"变成"顺手"。

## 1. 三个词：编辑器、IDE、AI 编辑器

| 类别 | 是什么 | 代表 | 你需要付的代价 |
|---|---|---|---|
| 编辑器 | 只管编辑文本，运行、调试靠扩展或外部终端 | VS Code（裸装）、Sublime、Vim | 要自己配扩展与解释器 |
| IDE（集成开发环境） | 编辑器 + 运行 + 调试 + 项目管理，开箱即用 | PyCharm | 体积大、启动慢、界面复杂 |
| AI 编辑器 | 在编辑器基础上内建 AI 补全与改写 | Cursor、Qoder | 有订阅/额度成本；容易一路 Tab 接受而不审查 |

一个必须先说清的关系：**Cursor、Qoder 都是基于 VS Code 的二次开发**。它们的界面布局、快捷键、扩展生态都跟 VS Code 高度相似——你会用一个，基本就会用另一个。VS Code 本身免费，扩展要自己装；AI 编辑器在它上面加了模型能力，代价是额度与"接受得太快"的风险。

这个关系有实测支撑。本机装了三套入口，脚本 `scripts/lec07-01_demo_editor.py` 逐个问了版本：

```text
  PATH 里的 code: 退出码=0 版本=1.24.2
  Qoder（系统安装）: 退出码=0 版本=1.33.0
  参数指定: 退出码=0 版本=1.127.0
```

三行分别是：`E:\...\App-Qoder\Qoder\bin\code.cmd`（1.24.2）、`C:\Program Files\Qoder IDE\bin\code.cmd`（1.33.0）、`E:\...\App-VSCode\Microsoft VS Code\bin\code.cmd`（1.127.0）。

这里有个真实而典型的坑：**你装了新版 Qoder（1.33.0），但敲 `code` 打开的是旧版（1.24.2）**。原因不是安装失败，而是第 02 讲那条规则——`PATH` 是一份有序清单，同名命令只跑第一个命中的。旧版所在目录排在前面，它就赢了。

想确认"我敲的 `code` 到底是哪一个"，用：

```powershell
Get-Command code -All
```

它会列出所有同名入口，第一个就是实际生效的那个。想换，就把想要的目录在 `PATH` 里往前挪，或者直接用完整路径调用。

## 2. 装：VS Code、Cursor、Qoder

### 2.1 装完怎么验证

三条路，选一条：

- 官网下载安装器（VS Code：`code.visualstudio.com`；Cursor、Qoder 各有官网）；
- 包管理器：`winget install Microsoft.VisualStudioCode`；
- 便携版（zip 解压即用），适合没有管理员权限的机房。

安装时如果问"为所有用户安装 / 仅为当前用户安装"，**没有管理员权限就选后者**（回第 03 讲）。装完最有效的验证不是"双击图标能打开"，而是在终端里：

```powershell
code --version
```

实测输出是版本号 + 提交哈希 + 架构：

```text
1.127.0
4fe60c8b1cdac1c4c174f2fb180d0d758272d713
x64
```

退出码 `0` 且打印出版本，说明终端与编辑器已经打通——之后你才能用 `code 文件名` 打开文件、用 `code .` 打开整个项目。

### 2.2 为什么必须装 Python 扩展

裸装的编辑器**不认识 Python**：它只会把 `.py` 当普通文本，没有补全、没有跳转、不能调试。

Python 扩展（扩展 ID 是 `ms-python.python`，作者 Microsoft）提供的是这条链：

- 语法高亮与括号匹配；
- 补全与类型提示（依赖 Pylance 这类语言服务）；
- 函数跳转与查找引用；
- **选择解释器**；
- 启动调试器（依赖另一个扩展 `ms-python.debugpy`）。

装法：打开扩展面板（左侧方块图标），搜 `Python`，认准作者是 Microsoft 的那个，点安装。它会连带装上调试支持。

本机实测两个编辑器的扩展清单（只列与 Python、AI 相关的）：

```text
  PATH 里的 code: 18 个扩展
    - ms-python.autopep8
    - ms-python.debugpy
    - ms-python.python
    - ms-python.vscode-python-envs
    - saoudrizwan.claude-dev
  参数指定: 8 个扩展
    - anthropic.claude-code
    - ms-python.debugpy
    - ms-python.python
    - ms-python.vscode-pylance
    - ms-python.vscode-python-envs
```

两条可读的信息：

- 两套都有 `ms-python.python` 与 `ms-python.debugpy`，这是"能写、能调"的最小配置；
- 一套装了 `pylance`（补全更强），另一套没有，但装了 `autopep8`（格式化）。**扩展是按需装的，不是越多越好**：同一类功能装两个（比如两个格式化器）会互相打架，表现为"保存时格式变了两次"或者"格式化没反应"。

验证装好没有，三个动作就够：打开一个 `.py` 文件看有没有高亮；按 `Ctrl+Shift+P` 输入 `Python: Select Interpreter` 看有没有候选；在编辑器内置终端里跑 `python -c "print(1+1)"` 看能不能出 `2`。

### 2.3 装不上、没权限怎么办

- **没有管理员权限**：选"仅为我安装"，装到用户目录；便携版解压到自己的文件夹也能用。
- **扩展装不上**（写不进扩展目录）：启动时用 `--extensions-dir 你的目录` 指定一个可写位置。
- **公司网络装不上**：扩展也可以离线安装（下载 `.vsix` 文件后从本地安装），这和 pip 的离线 wheel 是同一类思路（第 03 讲）。

## 3. 第一件事：选解释器

### 3.1 为什么这一步不能跳

编辑器要用解释器做三件事：**运行**、**补全**、**调试**。它不知道用哪个，就只能猜；猜错了，你看到的现象会很迷惑：

- 明明 `pip install` 过了，运行时还是 `ModuleNotFoundError`（装到了另一个环境）；
- 补全里没有你刚装的库（语言服务看的是另一个解释器）；
- 调试器起不来，或者断点根本不生效。

这三种现象，根都是同一件事：**编辑器用的解释器，和你以为的不是同一个**。

### 3.2 怎么选、怎么确认

在 VS Code / Cursor / Qoder 里：

1. `Ctrl+Shift+P` 打开命令面板，输入 `Python: Select Interpreter`；
2. 选项目里的 `.venv\Scripts\python.exe`（第 03 讲建的那个）；
3. 打开编辑器内置终端，跑：

```powershell
python -c "import sys; print(sys.executable)"
```

输出的路径应该指向 `.venv`。如果不是，说明终端里的 `python` 和编辑器选的那个不是一回事——多半是没激活环境，或者 `PATH` 里有别的 python 抢在前面（第 02 讲）。

"选解释器"到底选了什么？就是选了一条路径。实测本机两个解释器：

```text
  当前脚本的解释器（venv）: E:\...\WHATIFICATCHUPFROMSCRATCH\.venv\Scripts\python.exe
  基础解释器（母本）   : C:\Users\Administrator\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none\python.exe
```

两个路径不同、版本可能相同。编辑器里那一下选择，记下的就是其中一条路径；之后运行、补全、调试全部围绕它展开。

### 3.3 一条习惯

**每个项目一个 `.venv`，并在编辑器里选中它。** 这样"项目 A 的依赖"和"项目 B 的依赖"从根上就不会互相污染，也不需要每次跑之前想"我现在在哪个环境里"。

## 4. 断点调试：让程序停下来给你看

### 4.1 `print` 的天花板

`print` 能告诉你"这个变量在这一刻是多少"，但它有三个做不到：

- 你只能打印你**事先想到**的变量；
- 循环跑到第 37 次出错时，你得让它打印 37 次，然后在一屏里找；
- 你不知道"是谁把它改成这个值的"。

### 4.2 调试器的三件事

调试器只做三件事，但每件都补上了 `print` 的洞：

1. **停住**（断点）：程序跑到你指定的那一行就暂停；
2. **查看**：暂停时能看所有变量的当前值、调用栈；
3. **单步**：一行一行往下走，看每一步之后变量怎么变。

本讲没有演示图形界面（截图无法在终端里复现），而是用 Python 自带的命令行调试器 `pdb` 跑了同一套机制。脚本 `lec07-01_demo_editor.py` 第 5 节让一个函数在循环体里暂停，然后依次执行"看 x、看 s、单步、再看 s、继续"：

```text
  > ...\debug_demo.py(5)total()
  -> s += x
  (Pdb) 3
  (Pdb) 0
  (Pdb) > ...\debug_demo.py(3)total()
  -> for x in xs:
  (Pdb) 3
  (Pdb) > ...\debug_demo.py(5)total()
  -> s += x
  (Pdb) result = 8
```

逐行读：

- 第一行 `> ...(5)total()` 表示"停在第 5 行、在 `total` 函数里"，下一行 `-> s += x` 是即将执行的语句；
- `(Pdb) 3` 是执行了 `p x`（打印变量 `x`）的结果：`x` 现在是 3；
- `(Pdb) 0` 是 `p s` 的结果：累加器还是 0；
- `n`（next）执行一行，跳到第 3 行的 `for`，再 `p s` 得到 3——说明刚加完 3；
- 最后一个 `c`（continue）让程序跑完，输出 `result = 8`（3 + 5）。

图形界面里是同一件事的三个按钮：在行号左侧点一下出现红点（断点），`F5` 启动调试，左侧出现变量面板；`F10` 单步跳过、`F11` 单步进入函数。**会看变量、会单步，调试器就算入门了**，剩下的都是快捷键。

### 4.3 什么时候值得用调试器

三种情况，用调试器比 `print` 快得多：

- 问题只发生在循环的第 N 次（要看到那一轮的现场）；
- 你不确定某个变量是**谁**改的（调用栈能告诉你路径）；
- 报错发生在很深的调用里，`print` 要加在五六个地方。

反过来说，一个几十行的脚本、只想知道一个值，`print` 更快。工具没有高下，只有合用不合用。

## 5. 三类 AI 工具

### 5.1 编辑器内联

Cursor、Qoder、以及各种 Copilot 类插件，都是这个形态：你在文件里写，它在你光标附近补全或按你的指令改写。

- 能做什么：补全整段、按注释生成代码、选中一段让它重写、解释当前文件。
- 风险：**一路 Tab 接受**。你接受了十次建议，最后不知道自己这份代码里哪几行是自己想清楚的、哪几行是"它顺手加的"。第 08 讲的 `diff` 就是防这个的——但如果你连提交都没做，`diff` 也救不了。

### 5.2 命令行代理

Claude Code、Codex 这一类，形态完全不同：**它本身是一个可执行程序，在终端里运行**，可以读你的项目文件、可以执行命令、可以一次改多个文件。

本机实测（脚本第 6 节）：

```text
  ~/.claude 存在吗 = True
  PATH 里有 claude 命令吗 = None
  找到的可执行文件: C:\Users\Administrator\.vscode\extensions\anthropic.claude-code-2.1.310-win32-x64\resources\native-binary\claude.exe
```

三行说明三件事：

- 它有一个自己的本地状态目录（`~/.claude`：配置、会话、集成信息）；
- 它**不一定在 `PATH` 里**——扩展把可执行文件放在自己的资源目录下，所以"装了扩展"不等于"终端里能直接敲 `claude`"；
- 想让终端也能用，要么按产品的官方方式安装命令行入口，要么把那个目录加进 `PATH`（第 02 讲的三条修法）。

和聊天式最大的区别只有一条：**它能动手**。能动手就意味着"权限"成了你必须在场决定的事（第 08 讲第 6 节按读 / 写 / 执行分了三档）。

### 5.3 怎么选

| 你的任务 | 合适的形态 | 理由 |
|---|---|---|
| 写一段独立的函数、转换数据格式 | 聊天式 | 不需要项目上下文，贴进去就行，成本最低 |
| 在现有文件里补全、小改 | 编辑器内联 | 它有当前文件上下文，改完你能立刻看到 diff |
| 跨多个文件重构、跑命令验证、批量改 | 命令行代理 | 只有它能读全项目、执行命令；也最需要你先提交 |
| 学习一个新概念 | 聊天式 + 自己写 | 让它解释，然后自己敲一遍；不要让它替你写 |

一条纪律适用于三种形态：**先提交，再让它动手**。这不是保守，是因为"回退"是唯一能让你放心试错的东西（第 04 讲）。

## 6. 坏了怎么查

| 症状 | 先查什么 | 判据 |
|---|---|---|
| 敲 `code` 打开的不是我想要的那个编辑器 | `Get-Command code -All` | 第一个就是实际生效的；版本对不对 |
| 编辑器里运行报 `ModuleNotFoundError` | 编辑器选的解释器 vs 终端里的解释器 | 两处 `sys.executable` 是否指向同一个 `.venv` |
| 补全里没有刚装的库 | 语言服务用的解释器 | 换解释器后重启窗口再看 |
| 断点不生效 | 调试配置里的解释器、文件是否真被执行到 | 调试面板显示的解释器路径；断点是否变灰 |
| 扩展装不上 | 扩展目录是否可写 | 换 `--extensions-dir` 再试 |
| 两个格式化器打架 | 同类扩展是否装了多个 | 只留一个，或在设置里指定默认 |

这六条覆盖了新手九成以上的"编辑器不听话"。共同点是：**先确认"它到底在用哪个解释器/哪个目录"，再谈设置**。

## 7. 这一讲留下的东西

- 编辑器、IDE、AI 编辑器是三种取舍；Cursor / Qoder 与 VS Code 同源，会一个基本会另一个。
- `code --version` 是验证"终端与编辑器打通"的判据；`Get-Command code -All` 能查出同名命令的实际赢家。
- Python 扩展（`ms-python.python` + `debugpy`）是"能写、能调"的最小配置；同类扩展别装两个。
- 选解释器就是选一条路径；选错的三种症状都能用 `sys.executable` 定位。
- 调试器三件事：停住、查看、单步；`print` 与它各有适用场景。
- 命令行代理是一个能读写文件、能执行命令的可执行程序，不一定在 `PATH` 里；能力越大，越要先提交、先划权限。

下一讲把"它动完代码之后怎么管"完整走一遍：看 diff、验证、划权限、回退。

## 小结

- 编辑器只管编辑；运行、补全、调试要靠扩展与解释器配合。
- Cursor、Qoder 基于 VS Code，界面与扩展生态接近；三套并存时，`code` 指向 `PATH` 里第一个命中的那个（本机实测旧版 Qoder 1.24.2 抢在前面，而系统里还有 1.33.0）。
- 装完用 `code --version` 验证，退出码 0 且打印版本才算通。
- Python 扩展提供高亮、补全、跳转、选解释器、调试；最小配置是 `ms-python.python` + `ms-python.debugpy`。
- 选解释器 = 选路径；验证方式是 `python -c "import sys; print(sys.executable)"` 指向 `.venv`。
- 调试器三件事：断点停住、查看变量与调用栈、单步执行；实测用 `pdb` 完成了一次"看 x=3、看 s=0、单步后 s=3、继续得 8"。
- 三类 AI 工具：聊天式（无项目上下文）、编辑器内联（有文件上下文、容易一路接受）、命令行代理（能读写与执行，权限风险最大）。
- 命令行代理不一定在 `PATH` 里；本机 `claude` 不在 `PATH`，可执行文件在扩展资源目录中。

## 作业

**Q1.** 你装了新版编辑器，但敲 `code` 打开的界面和以前一样。用两条命令找出原因，并说明怎么改。

**参考答案：** 先 `Get-Command code -All`，它会列出所有同名入口，**第一个就是实际生效的**；再对你怀疑的那个用完整路径跑 `--version` 对比版本。本讲实测就是这样发现"旧版 1.24.2 抢在 1.33.0 前面"的。

改法两种：把想要的那个目录在 `PATH` 里往前挪（第 02 讲）；或者直接用完整路径调用（脚本里"参数指定"那一行就是这么做的）。

**Q2.** 你在编辑器里运行脚本，报 `ModuleNotFoundError: No module named 'requests'`，但你在终端里 `python -m pip list` 明明看到了 `requests`。列出最可能的原因和验证方法。

**参考答案：** 最可能的原因：编辑器用的解释器与终端里那个不是同一个环境。

验证：在编辑器内置终端里跑 `python -c "import sys; print(sys.executable)"`，看它是不是项目的 `.venv`；再用编辑器命令面板的 `Python: Select Interpreter` 看选的是哪条路径。两处不一致，就以 `.venv` 为准重选，并重启编辑器窗口。

如果终端里显示的是全局 Python，说明虚拟环境没激活（第 03 讲）——`pip install` 装到了全局，脚本却在 `.venv` 里跑。

**Q3.** 用自己的话说明：调试器的"断点"和 `print` 各自适合什么场景？各给一个具体例子。

**参考答案：** `print` 适合"我只想知道某个值是什么、而且大概知道该在哪打印"：例如在一个 20 行的脚本里确认 `total` 算出来是多少。

断点适合"要看现场"：例如循环跑到第 37 次才出错，你要看那一轮的 `x` 和累加器 `s`；或者某个变量被改成了意料之外的值，你要通过调用栈看是谁改的。断点的优势是不需要事先猜到该打印什么，也不会因为打印语句改变程序行为（打印本身也是 I/O，偶尔会影响时序）。

**Q4.** 命令行代理（Claude Code / Codex 类）和聊天式工具，本质区别是什么？为什么说它"更需要你先提交"？

**参考答案：** 本质区别是**能不能动手**：聊天式只产出文本，你自己决定贴不贴、改不改；命令行代理是一个普通程序，能读你的文件、能执行命令、能一次改多个文件。

因为它会直接改磁盘上的东西，而且可能一次改很多处，人工恢复几乎不可行；有了一次提交，最坏情况也只是 `git restore` 一条命令（第 04 讲）。没有提交，你就只能靠记忆和运气。

**Q5.** 本机实测 `claude` 不在 `PATH` 里，但能找到 `claude.exe`。这说明"装了扩展"和"能在终端用"是什么关系？

**参考答案：** 是两件事。扩展把可执行文件放在自己的资源目录（本机是 `...\extensions\anthropic.claude-code-2.1.310-win32-x64\resources\native-binary\claude.exe`），只有扩展自己知道那个路径；`PATH` 里没有它，所以终端敲 `claude` 找不到。

想在终端用，有两条路：按产品的官方方式安装命令行入口；或者把那个目录加进 `PATH`（第 02 讲三种修法）。这也解释了第 02 讲那句"命令找不到，多半不是没装"。

**Q6.** 你的编辑器保存时格式会变两次，偶尔还报格式化失败。最可能的原因是什么？怎么排查？

**参考答案：** 最可能装了多个同类格式化扩展（本机就同时见到过 `autopep8` 与 Pylance 提供的格式化能力），它们都想在保存时动手，于是先后执行、互相覆盖，甚至冲突。

排查：打开扩展列表，找出所有提供"格式化"的扩展；在设置里明确指定默认格式化器（`Format Document With...` → 选一个并设为默认）；把多余的卸掉。判据是：保存一次，文件只变一次，且 `git diff` 里只出现你预期的改动。
