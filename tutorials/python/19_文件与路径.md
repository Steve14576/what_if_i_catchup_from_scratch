## 0. 场景：三件跟文件有关的事

- 你把一份有人名的 CSV 交给脚本，它读出来全是 `锟斤拷`。
- 你写了一个"保存配置"的函数，第二次运行时把上一次的配置清空了。
- 你要统计一个 2 GB 日志里的关键字，`read()` 一开就把内存吃满、电脑开始卡。

三件事的共同点：**文件不是内存里的对象，它有一层操作系统与编码在中间**。这一讲把这层讲清楚。

下一节先看 `open` 的模式：打开一个有副作用的动作。

## 1. 五种模式：打开就有后果

`open(路径, 模式, encoding=...)` 的第一个参数给文件，第二个参数决定"打开的瞬间发生了什么"。

| 模式 | 含义 | 打开时对文件的影响 | 文件不存在时 |
|---|---|---|---|
| `r` | 只读 | 无 | `FileNotFoundError` |
| `w` | 只写 | 立即清空为 0 字节 | 新建 |
| `a` | 追加写 | 无（写入追加到末尾） | 新建 |
| `x` | 独占写 | 无 | 新建；已存在则 `FileExistsError` |
| `b` | 二进制（叠加用） | 无 | 不适用 |

实测（同一个文件，先写入 100 字节）：

```text
  写入 100 字节后 size = 100
  以 'w' 打开、未写之前 size = 0  ← 打开即清空
  写入 'new\n' 后 size = 5
```

三件事值得注意：

1. **清空发生在打开时，不是写入时**。`open(..., "w")` 一执行，原内容就没了；哪怕你随后什么都没写、甚至抛了异常，文件也已经空了。
2. **`size = 5` 而不是 4**：`"new\n"` 是 4 个字符，但文本模式在 Windows 上会把 `\n` 写成 `\r\n`，所以落盘 5 字节。这是第 9 节"行尾"的伏笔。
3. **`a` 追加**实测内容变成 `'new\nappended\n'`；`x` 打已存在的文件抛 `FileExistsError: File exists`，这是"我不想覆盖"时的正确工具。

`b` 不能与 `encoding` 同时用，实测：

```text
  'rb' 同时给 encoding: ValueError -> binary mode doesn't take an encoding argument
```

报错信息说得很直白：二进制模式不谈编码，因为它不做任何解码（第 8 节展开）。

下一节回答最关键的一问：既然 `open` 可以不写编码，为什么不写就会出事。

## 2. 为什么必须显式 encoding

`open` 的 `encoding` 默认值不是 UTF-8，而是"当前平台的偏好编码"。本机实测：

```text
  locale.getpreferredencoding(False) = 'cp936'
  sys.getdefaultencoding()           = 'utf-8'
  sys.getfilesystemencoding()        = 'utf-8'
```

这里有个很容易误读的地方：`sys.getdefaultencoding()` 是 `'utf-8'`，但它管的是**字符串与字节之间的内部转换**，不是 `open` 的默认编码。真正决定文本文件读写编码的是第一个：`cp936`（GBK 系列）。三行放在一起看，才能对上后面两种失败。

第一种失败，读：

```text
  不指定 encoding 读: UnicodeDecodeError -> 'gbk' codec can't decode byte 0xad in position 2:
  illegal multibyte sequence
  显式 utf-8 读: '中文内容 abc'
```

文件是脚本用 UTF-8 写的（18 字节），读的时候用 GBK 去解，第 2 个字节就对不上。这类报错在换机器、换系统语言之后突然出现，原因就是默认值不同。

第二种失败更隐蔽，写：

```text
  不指定 encoding 写: 字节数 = 14（utf-8 应为 18）
```

同样四个汉字加 `abc`，UTF-8 是 18 字节，GBK 是 14 字节。**它不报错**，只是落盘的字节换了一套。等你把文件发给别人，对方用 UTF-8 打开，看到的就是乱码。

所以纪律只有一条：**每一处 `open` 都写 `encoding="utf-8"`，不依赖默认值**。`pathlib` 的 `write_text` / `read_text` 同理，它们默认也用平台偏好编码。

下一节看"打开之后谁负责关上"，以及不关会发生什么。

## 3. with 保证了什么

文件对象是操作系统资源：打开会占用一个句柄，写入先进缓冲区。不关闭的后果有两个：句柄泄漏（打开太多会报错）、缓冲区内容没落盘（程序崩溃时最后几行丢失）。

`with` 保证的是"离开这块代码时一定关闭"，不管你是正常结束、抛异常、还是 `return`：

```text
  进入块之前 f.closed = False
  块内 f.closed   = False
  退出块之后 f.closed = True
```

这就是第 18 讲 `try/finally` 的自动化版本：`with open(...) as f:` 等价于"打开 → try → finally 关闭"，但不用你手写，也就不会忘。

一条容易忽略的细节：`with` 关闭的是文件，不是"你的数据已经安全"。写到一半断电，没 `flush` 的部分仍会丢。要更强的保证需要 `f.flush()` + `os.fsync()`，本课程不要求，知道存在即可。

下一节换一个方向：文件到底在哪个路径上。

## 4. pathlib：路径不要用字符串拼

路径拼接有两个老问题：分隔符（Windows 是 `\`，Unix 是 `/`）、以及相对路径到底以谁为起点。`pathlib` 一次解决两个。

实测（在项目根目录下运行）：

```text
  cwd              = E:\E_Vault\CC_Formed_Projs2\WHATIFICATCHUPFROMSCRATCH
  拼出来的绝对路径 = C:\Users\...\Temp\tmpigwosccd\proj\data\raw.csv
  p.parent.name    = data
  p.suffix / stem  = '.csv' / 'raw'
  p.exists()       = True
  相对写法 data/raw.csv 的 resolve() = E:\E_Vault\CC_Formed_Projs2\WHATIFICATCHUPFROMSCRATCH\data\raw.csv
```

要点四个：

1. `Path("a") / "b" / "c.txt"` 用 `/` 拼接，Windows 上也照写，库里负责转换。
2. `.parent` / `.name` / `.stem` / `.suffix` 把"取目录、取文件名、去后缀、取后缀"变成属性，不用手写字符串切分。
3. `.resolve()` 把相对路径变成绝对路径，起点是**当前工作目录**（cwd）。最后一行那个 `data/raw.csv` 在项目根下并不存在，但 `resolve()` 照样算出一个位置——这正说明"相对路径永远相对于 cwd"，而不是相对于脚本文件。
4. `.mkdir(parents=True, exist_ok=True)` 一次建多层目录，重复执行不报错；这是写"导出结果"类脚本的标准开头。

最后一条是本讲最容易踩的坑：你在项目根目录运行 `python src/main.py`，cwd 是根目录；你 `cd src` 之后再运行，cwd 变了，脚本里写的 `data/raw.csv` 就指向别处。第 02 讲讲的"文件找不到"就是它。稳妥写法是用 `Path(__file__).parent` 定位到脚本所在目录，再往上拼数据目录；第 26 讲会给完整示例。

下一节处理"文件太大"。

## 5. 读大文件：三种写法的内存

先看实测。文件 13.73 MB、20 万行，三种读法各测一次峰值内存（`tracemalloc`）：

| 写法 | 峰值内存 | 适合 |
|---|---|---|
| `f.read()` | 54.94 MB | 小文件、需要整份内容一起处理 |
| `f.readlines()` | 28.27 MB | 小文件、需要按下标反复访问 |
| `for line in f` | 49.6 KB | 任何大小；一次只留一行 |

差别接近三个数量级。原因不复杂：前两种都把"整份内容"搬进内存，而且字符串对象本身有额外开销，所以 13.73 MB 的字节会变成几十 MB 的对象；逐行迭代只保留当前这一行。

三个实践结论：

- **判断标准不是文件大小，而是"要不要把全部内容同时放在内存里"**。要排序、要随机访问，就得整份读；只是一行行过滤、统计、转换，就用迭代。
- `readlines()` 比 `read()` 省，是因为它不额外复制一份大字符串，但它仍然持有全部行对象。
- 逐行迭代的文件对象是一次性的：读到底之后再 `for` 一遍不会重新开始，要重读得 `f.seek(0)` 或重新打开。

下一节开始处理结构化数据：CSV 与 JSON。

## 6. CSV：newline 与逗号里的逗号

CSV 看起来简单，两个坑必须先知道。

**坑一：`newline=""` 不写会出现空行。** 实测同一个表格写两次：

```text
  不写 newline: 字节 37，CRLF 3 个，CR+CRLF 3 个，首句 b'name,score\r'
  写 newline  : 字节 34，CRLF 3 个，CR+CRLF 0 个，首句 b'name,score'
```

CSV 规范要求行尾是 `\r\n`，`csv.writer` 就按规范写。但文本模式在 Windows 上还会把 `\n` 再转一次，于是每行变成 `\r\r\n`：多出的 `\r` 在 Excel 里表现为空行，字节数也多了 3。写 `newline=""` 是告诉 Python"行尾我自己管，你别转换"，差异就消失了。

**坑二：`split(",")` 不是 CSV。** 字段里带逗号、带引号、带换行时，手写切分会错。`csv` 模块负责引号转义，读回来用 `DictReader` 直接拿字典：

```text
  DictReader 读回 2 行，第一行 = {'name': '张三', 'score': '90'}
```

注意两点：读回来的值**全是字符串**（`'90'` 不是 `90`），要算数得自己转（第 09、10 讲）；表头行默认被当成列名，不计入行数。

`csv` 是标准库：不用安装，`import csv` 即用；验证方式是"写一个含逗号字段的表再读回来，字段数不变"；它不存在"装不上"的问题。真正会缺的是第三方生态（pandas 等，第 23 讲），那时才需要装。

下一节看 JSON。

## 7. JSON：ensure_ascii 与写盘

JSON 的两个决定：中文要不要转义、缩进要不要。

```text
  ensure_ascii=True  字符数 80: {"name": "\u5f20\u4e09", ...
  ensure_ascii=False 字符数 50: {"name": "张三", ...
  写盘再读回: {'name': '张三', 'scores': [90, 85], 'note': '中文注释'}
  写盘字节数（utf-8, 不转义）= 89
```

- `ensure_ascii=True` 是默认值：中文会被写成 `\u5f20\u4e09` 这种转义序列。**语义没错**，但人看不懂、体积也大（80 字符 vs 50 字符）。
- 给人看的文件写 `ensure_ascii=False, indent=2`，同时 `open` 仍要 `encoding="utf-8"`。这两件事要一起做：只改一个，乱码或转义至少留一个。
- 读回来是普通字典/列表，键仍是字符串、数字仍是数字（对比 CSV 全是字符串）。

`json` 同样是标准库。判据：文件要给人看 → 不转义 + 缩进；要机器读 → 两者都无所谓，体积优先。

下一节处理"根本不是文本"的文件。

## 8. 文本与二进制

同一个文件，两种打开方式拿到的是两种东西：

```text
  read_bytes() 前 12 字节 = b'\xe4\xb8\xad\xe6\x96\x87\xe5\x86\x85\xe5\xae\xb9'
  len(bytes) = 18，解码后 len(str) = 10
  'rb' 读 6 字节 = b'\xe4\xb8\xad\xe6\x96\x87'  ← 可能切在汉字中间
```

- 文本模式（默认）：读出 `str`，中间做了一次解码；编码写错就报 `UnicodeDecodeError` 或产生乱码。
- 二进制模式（`b`）：读出 `bytes`，不做任何解码；`len` 是字节数（18），不是字符数（10）。
- 用 `rb` 按字节读时，可能正好切在一个汉字的中间，单独解码这几字节会失败。所以"按字节处理文本"要么整段解码，要么用能处理边界的库。

判据：图片、压缩包、音频、Excel（`.xlsx`）、pickle 这些都是二进制，必须 `b`；`.txt`、`.csv`、`.json`、`.py` 这些是文本，用文本模式加显式编码。

下一节把前面所有"行尾"的碎片收拢。

## 9. 行尾与 universal newlines

行尾在不同系统上不同：Windows 传统是 `\r\n`，Unix 是 `\n`。Python 的文本模式默认做"通用换行"转换：读的时候把 `\r\n` 和 `\r` 都归一成 `\n`，写的时候把 `\n` 转成系统行尾。

实测一个混合行尾的文件：

```text
  默认模式 splitlines 得 3 行: ['第一行', '第二行', '第三行']
  newline='' 原样读到的 repr = '第一行\n第二行\r\n第三行\n'
```

同一个文件：
- 默认模式：三行都干净，看不出原本哪个是 `\r\n`；
- `newline=""`：原样保留，`\r\n` 看得见。

这两条合起来解释了本讲三个现象：`w` 写入 `"new\n"` 落盘 5 字节（转成 `\r\n`）；CSV 不写 `newline=""` 会出现 `\r\r\n`（CSV 自己写 `\r\n`，文本模式再转一次）；读日志时 `line` 末尾常常带一个 `\n`，要 `line.rstrip("\n")` 或 `splitlines()` 处理。

一条纪律：**处理行尾敏感的数据（CSV、生成的配置文件）时显式写 `newline=""`，把转换权收回来**。

四类现象（模式、编码、路径、内存）到这里都说完了，下一节把本讲结论收起来。

## 10. 这一讲留下的东西

- `open` 的第二个参数决定打开时的副作用：`w` 立刻清空、`a` 追加、`x` 独占创建。
- 默认编码是平台偏好（本机 `cp936`），不是 UTF-8；`sys.getdefaultencoding()` 不是它。
- 不写 encoding 的两种失败：读报 `UnicodeDecodeError`，写不报错但字节不一致（18 vs 14）。
- `with` 保证异常路径也关闭文件；不关的后果是句柄泄漏与缓冲丢失。
- 相对路径以 cwd 为起点，不是以脚本文件为起点；`Path(__file__).parent` 才是脚本位置。
- 13.73 MB / 20 万行：`read()` 峰值 54.94 MB、`readlines()` 28.27 MB、逐行迭代 49.6 KB。
- CSV 必须 `newline=""`（否则 37 字节、`\r\r\n`）；读回来的值全是字符串。
- JSON 写给人看用 `ensure_ascii=False, indent=2`，并配 `encoding="utf-8"`。
- 二进制模式不做解码，按字节读中文可能切断汉字。
- 通用换行默认把 `\r\n` 归一成 `\n`；`newline=""` 才看得到原貌。

- 实测 `w` 模式：100 字节的文件在打开瞬间变成 0，写完 `"new\n"` 是 5 字节（文本模式把 `\n` 写成 `\r\n`）。
- 实测 `a` 追加得 `'new\nappended\n'`；`x` 打已存在文件抛 `FileExistsError`；`'rb'` 配 `encoding` 抛 `ValueError`。
- 实测默认编码 `cp936`；UTF-8 文件 18 字节，GBK 写出来 14 字节；不写 encoding 读 UTF-8 中文抛 `UnicodeDecodeError`。
- 实测 `with` 块外 `f.closed = True`；块内为 `False`。
- 实测 `Path('data/raw.csv').resolve()` 落在当前项目根下，证明相对路径以 cwd 为起点。
- 实测三个读法的峰值内存：54.94 MB / 28.27 MB / 49.6 KB。
- 实测 CSV：不写 `newline` 37 字节、3 处 `\r\r\n`；写了 34 字节、0 处。
- 实测 JSON：`ensure_ascii` 开关让同一条数据从 80 字符变 50 字符。
- 实测二进制：18 字节解码成 10 个字符，`rb` 读 6 字节正好是两个汉字。
- 实测行尾：默认模式看不见 `\r\n`，`newline=""` 能看见。

**Q1.** 下面这段"保存配置"的代码，为什么第二次运行会把上一次的配置清空？给出一个不破坏原文件的写法。

```python
def save(config):
    f = open("config.json", "w", encoding="utf-8")
    import json
    json.dump(config, f)
```

**参考答案：** `open(..., "w")` 在打开的一瞬间就把文件清空了；如果 `json.dump` 中途抛异常（比如配置里有不可序列化的对象），你会得到一个空文件——旧配置已经没了。

更稳的写法是"先写临时文件、成功后再替换"：

```python
import json
import os
from pathlib import Path

def save(config, path="config.json"):
    target = Path(path)
    tmp = target.with_suffix(target.suffix + ".tmp")
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(config, f, ensure_ascii=False, indent=2)
    os.replace(tmp, target)
```

要点：`with` 保证关闭；写临时文件保证失败时原文件还在；`os.replace` 在同一磁盘上是原子操作。另外这段代码里我故意保留了原版的 `import json` 位置问题——它写在函数里虽然能跑，但应该在文件顶部统一导入。

**Q2.** 你在自己电脑上读到正确的中文，把脚本发给同学，他那里报 `UnicodeDecodeError`。最可能的原因是什么？给出两条修法（一条治标、一条治本）。

**参考答案：** 最可能的原因是 `open` 没写 `encoding`，两边默认编码不同（你这边是 UTF-8 或 cp936，他那边是另一个）。也可能是文件本身用 GBK 存的，而你这边恰好能解。

- 治标：把读的地方写成 `open(path, encoding="utf-8", errors="replace")`，先把程序跑起来、看清楚坏在哪几个字。
- 治本：确定一套编码（本课程统一 UTF-8），读写两端都显式写 `encoding="utf-8"`；老数据用一次性转码脚本转成 UTF-8 并留档。

**Q3.** 一个 2 GB 的日志文件，你要统计包含 `ERROR` 的行数。下面三种写法哪个不能用？为什么？

```python
# A
with open("huge.log", encoding="utf-8") as f:
    n = sum(1 for line in f if "ERROR" in line)

# B
with open("huge.log", encoding="utf-8") as f:
    lines = f.readlines()
n = sum(1 for line in lines if "ERROR" in line)

# C
with open("huge.log", encoding="utf-8") as f:
    text = f.read()
n = text.count("ERROR")
```

**参考答案：** B 和 C 都不能用。它们都要把整份文件搬进内存：C 最糟（一个 2 GB 的字符串，且 `count` 还会数到 `ERRORS` 这类包含关系）；B 稍好但仍然持有全部行对象。本讲实测 13.73 MB 的文件，`read()` 峰值 54.94 MB、`readlines()` 28.27 MB。

A 是正确做法：逐行迭代，峰值内存只跟"最长的一行"有关。如果还要更严格，可以顺便加一个"单行超过 N MB 就截断"的保护。

**Q4.** 你用 `csv.writer` 写出的文件在 Excel 里打开，每两行之间夹一个空行。原因是什么？怎么改？

**参考答案：** `csv.writer` 按 CSV 规范写行尾 `\r\n`；`open` 默认的文本模式在 Windows 上又把 `\n` 转成 `\r\n`，于是每行变成 `\r\r\n`，多出的 `\r` 让 Excel 看成空行。本讲实测：不写 `newline` 是 37 字节、3 处 `\r\r\n`；写了是 34 字节、0 处。

改法是写文件时显式关掉转换：

```python
with open(path, "w", encoding="utf-8", newline="") as f:
    csv.writer(f).writerows(rows)
```

**Q5.** 判断对错并说明理由：
(a) `sys.getdefaultencoding()` 是 `'utf-8'`，所以 `open` 默认就是 UTF-8；
(b) `Path("a") / "b"` 在 Windows 上会出错，因为分隔符不对；
(c) 文件对象被垃圾回收时会自动关闭，所以不写 `with` 也没关系；
(d) 用 `rb` 读文本文件是"更保险"的做法，因为不会乱码。

**参考答案：** 五条逐一看：

- (a) 错。`sys.getdefaultencoding()` 管的是内部 str/bytes 转换；`open` 的默认编码是 `locale.getpreferredencoding(False)`，本机实测 `cp936`。
- (b) 错。`pathlib` 的 `/` 在 Windows 上自动用 `\`（或接受 `/`），这正是它替代字符串拼接的理由。
- (c) 半对半错。CPython 在对象被回收时确实会关闭文件，但"什么时候回收"不确定：异常路径、长生命周期引用、解释器退出时都可能出问题，缓冲内容也可能来不及落盘。把它当保证用是错的。
- (d) 错。`rb` 不解决乱码，它只是"不解码"：拿到的是字节，显示出来仍是 `b'\xe4...'`，而且按字节切还可能切断汉字。正确做法是用文本模式并写对 `encoding`。

**Q6.** 写一个函数 `count_errors(path)`：逐行读一个大日志，返回包含 `"ERROR"` 的行数，并顺手返回总行数；文件不存在时返回 `(0, 0)`。要求不把文件整体读进内存。

**参考答案：** 一个逐行版本，不整读、不吞其它异常：

```python
def count_errors(path):
    errors = 0
    total = 0
    try:
        with open(path, encoding="utf-8") as f:
            for line in f:
                total += 1
                if "ERROR" in line:
                    errors += 1
    except FileNotFoundError:
        return 0, 0
    return errors, total
```

四个要点：`with` 保证关闭；逐行迭代不整读；`try/except FileNotFoundError` 只捕这一类（第 18 讲的"最小捕获"）；返回两个数而不是打印，方便测试（第 25 讲）。
