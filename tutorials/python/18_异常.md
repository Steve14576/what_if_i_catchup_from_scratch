## 0. 场景：三个真实的崩溃

- 脚本昨晚跑得好好的，今天报 `FileNotFoundError`——文件被移走了。
- 用户输入 `abc` 时程序直接崩，屏幕上是一长串红字。
- 某个 `try` 里写了 `except: pass`，现在结果不对，但什么错误信息都没有。

三件事都属于"程序遇到意外情况"。异常机制解决的是：**让意外有名字、有位置、有处理方式**。它不是为了"让程序不崩"，而是为了"崩得清楚，或者在该恢复的地方恢复"。

下一节先学读 `traceback`：从哪一行看起。

## 1. `traceback` 怎么读

先看一条完整的。三个函数的调用链，最里层打开一个不存在的文件：

```python
def read_config(path):
    return open(path, encoding='utf-8').read()

def load():
    return read_config('config.ini')

load()
```

实测（退出码 1）：

```text
    Traceback (most recent call last):
      File "...\trace_demo.py", line 7, in <module>
        load()
      File "...\trace_demo.py", line 5, in load
        return read_config('config.ini')
               ^^^^^^^^^^^^^^^^^^^^^^^^^
      File "...\trace_demo.py", line 2, in read_config
        return open(path, encoding='utf-8').read()
               ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    FileNotFoundError: [Errno 2] No such file or directory: 'config.ini'
```

### 1.1 从下往上读

- **最后一行**：错误类型 + 消息。`FileNotFoundError` 是类型，后面那句说"找不到 `config.ini`"。这一行决定你往哪个方向查。
- **倒数第二块**：`File "...trace_demo.py", line 2, in read_config`——真正出错的位置（文件、行号、函数名），下面那行是源码，`^^^` 指到具体表达式。
- **上面的块**：调用链。`in <module>` 是"模块顶层"，说明是从第 7 行开始调的；再往上是 `load` 调了 `read_config`。

一句话：**最下面一行告诉你"什么错"，最下面那个块告诉你"错在哪"，上面的块告诉你"怎么走到那儿的"。**

### 1.2 什么时候没有 `traceback`

语法错误（`SyntaxError`）和缩进错误（`IndentationError`）**没有** `Traceback (most recent call last):` 这一行。因为它们在编译阶段就被发现，程序一行都没执行，没有"调用链"可回溯（第 01 讲讲的就是这个区别）。

### 1.3 读 traceback 的顺序建议

1. 先看最后一行：什么类型、什么消息；
2. 再看最下面那个 `File ... line ...`：是不是**你自己**的文件（还是库内部的）；
3. 如果是库内部的，往上看一层：是你在哪一行调了它；
4. 最后才去查这个异常类型通常意味着什么。

这个顺序能避免一种常见的浪费时间：一看到红字就从第一行开始读，读了半天都是库的路径。

读法定了，下一节看 `try` 四段各管什么。

## 2. `try` 的四段

### 2.1 执行顺序实测

```text
  没出错时: ['try', 'else', 'finally']
  出错时  : ['try', 'except', 'finally']
```

- 正常：`try` 跑完 → `else` → `finally`；
- 出错：`try` 中断 → 匹配到 `except` → `finally`。

### 2.2 各段管什么

| 段 | 什么时候执行 | 放什么 |
|---|---|---|
| `try` | 总是 | **只放可能出错的那几行**，越短越好 |
| `except` | 匹配到异常时 | 恢复动作：重试、给默认值、提示用户、记录日志 |
| `else` | 没抛异常时 | "成功之后"的动作（容易被忽略的一段） |
| `finally` | 无论如何 | 收尾：关文件、释放锁、删临时文件 |

### 2.3 `else` 存在的理由

你完全可以把成功后的代码写在 `try` 的最后一行，效果看起来一样。但那样有个副作用：**`try` 里的任何异常都会被同一组 `except` 捕获**——包括成功之后那段代码自己抛的异常。

```python
try:
    data = read(path)
    result = parse(data)      # 如果 parse 抛 ValueError，也会被下面捕走
except FileNotFoundError:
    ...
```

用 `else` 能划清界限：

```python
try:
    data = read(path)
except FileNotFoundError:
    ...
else:
    result = parse(data)      # 这里的异常不会被上面的 except 误捕
```

所以 `else` 不是装饰，它是"缩小 try 范围"的工具。范围越小，`except` 捕到的就越确定是自己想处理的那个错误。

四段清楚了，下一节看 `except` 的匹配与顺序。

## 3. `except` 的匹配

### 3.1 第一个匹配就停

```text
  KeyError      -> KeyError 分支
  IndexError    -> LookupError 分支（KeyError 的父类）
  ValueError    -> Exception 分支
```

`except` 是**从上往下匹配，命中第一个就停**。上面这个例子里，`IndexError` 落到了 `LookupError` 分支——因为 `IndexError` 是 `LookupError` 的子类。

### 3.2 子类必须写在父类前面

```python
except LookupError:      # 父类
    ...
except KeyError:         # 子类：永远轮不到
    ...
```

这段能跑，但第二个分支是死代码。正确顺序是"从具体到宽泛"：

```python
except KeyError:
    ...
except LookupError:
    ...
except Exception:
    ...
```

最后那个 `except Exception` 是兜底，通常用于"记日志 + 重新抛出"，而不是"悄悄吞掉"。

### 3.3 捕获多个与取名

```python
except (ValueError, TypeError) as exc:
    print("输入有问题:", exc)
```

`as exc` 把异常对象绑到名字上，能读 `exc` 的消息（`str(exc)`）与类型（`type(exc).__name__`）。注意这个绑定在 `except` 块结束后就失效了（Python 3 的行为），别在块外引用。

匹配规则定了，下一节看裸 `except` 到底错在哪。

## 4. 裸 `except` 与静默吞错

### 4.1 裸 `except` 等价于抓 `BaseException`

实测：一个脚本 `raise SystemExit(3)`，意思是"我要带退出码 3 退出"。

```text
  裸 except 抓 SystemExit: 退出码=0，输出='裸 except 抓到了，程序继续\n这一行还会执行'
  except Exception 抓 SystemExit: 退出码=3，输出=''
```

两行对照说明：

- 裸 `except:` 把 `SystemExit` 也抓了，于是"本该退出"变成了"继续跑"，退出码从 3 变成 0。自动化脚本会因为退出码 0 误判成功。
- `except Exception:` 不会抓 `SystemExit`，程序按原意退出（退出码 3）。

`BaseException` 家族里有几个"不该被普通代码拦"的东西：`SystemExit`（退出）、`KeyboardInterrupt`（用户按 `Ctrl+C`）、`GeneratorExit`。裸 `except` 会把它们全吞掉。

### 4.2 `except: pass` 的后果

比"抓太宽"更糟的是"抓了还不管"：

```python
try:
    do_something()
except:
    pass
```

这段代码把错误变成"什么都没发生"。结果是：数据少了一行、文件没写成功、配置没读到，程序继续跑，直到很久以后在别的地方出问题——而那时你已经失去了第一条线索。

真的决定忽略某个异常时，也至少写一行日志说明为什么忽略。

### 4.3 最小捕获原则

```python
try:
    with open(path, encoding="utf-8") as f:
        text = f.read()
except FileNotFoundError:
    text = ""          # 明确：文件不存在时用空内容
```

三条实践：

1. `try` 里只放会抛异常的那几行（这里是 `open` 与 `read`）；
2. `except` 只写你知道怎么处理的那一类；
3. 处理不了的就让它往上抛——**崩得清楚**比**悄悄错**好。

捕获范围讲完，下一节看 `finally` 与 `with` 的分工。

## 5. `finally` 与 `with`

### 5.1 `finally` 一定执行

第 2 节的实测已经证明：正常路径与异常路径都会走到 `finally`。它的典型用途是收尾：

```python
lock = acquire()
try:
    do_work()
finally:
    lock.release()
```

不管 `do_work` 成没成，锁都会被释放。这就是"资源必须回收"的保证。

### 5.2 `finally` 里写 `return` 会出大事

实测两个函数：

```text
  正常路径: tricky() = 'finally 的返回值'
  异常路径: tricky2() = '错误被吞掉了'
```

第一个：`try` 里 `return "try 的返回值"`，`finally` 里 `return "finally 的返回值"`，结果返回的是 **finally 的**——`finally` 的 `return` 覆盖了 `try` 的返回值。

第二个：`try` 里抛了 `ValueError`，`finally` 里 `return`，结果异常被**吞掉**，函数正常返回字符串。

这两条足够得出结论：**`finally` 里不要写 `return`**（也不要写 `break` / `continue`）。它只该用来"收尾"，不该用来"决定结果"。

### 5.3 收尾优先用 `with`

`with` 是"自动收尾"：离开代码块时一定执行清理（第 19 讲讲文件时会展开）。能用 `with` 就不用 `try/finally`：

```python
with open(path, encoding="utf-8") as f:
    text = f.read()
```

文件一定被关闭，而且不会踩上面那个 `return` 的坑。自己写的资源类也可以支持 `with`（第 21 讲的上下文管理器）。

收尾讲完，下一节看 `raise` 与异常链。

## 6. `raise` 与异常链

### 6.1 重新抛出

```python
except ValueError:
    log("解析失败")
    raise          # 原样抛出，保留原始 traceback
```

`raise` 不带参数表示"把当前这个异常继续往上抛"。常用于"我记了日志，但我不处理"。

### 6.2 `raise ... from ...`：保留原始原因

```python
def parse_age(text):
    try:
        return int(text)
    except ValueError as exc:
        raise ValueError(f"年龄必须是整数，收到 {text!r}") from exc
```

实测：

```text
  捕获到: 年龄必须是整数，收到 'abc'
  __cause__ 是原始异常吗 = True
```

`from exc` 把原始异常挂在 `__cause__` 上，`traceback` 里会显示"The above exception was the direct cause of the following exception"——两层原因都看得到。

什么时候该包一层？当你把底层的技术错误转换成**对调用方有意义**的错误时。比如"解析 JSON 失败"对用户没意义，但"配置文件格式有误，第 3 行缺少引号"有意义——这时包一层，用 `from` 留住原始错误备查。

### 6.3 别用 `raise` 换掉信息

反面写法：

```python
except ValueError:
    raise Exception("出错了")     # 原始信息全丢
```

这样做的后果是：你只知道"出错了"，不知道哪个值、哪一行、什么原因。`from` 或者 `raise` 原样抛出，都比这强。

异常链清楚了，下一节看自定义异常。

## 7. 自定义异常

### 7.1 什么时候值得写

```python
class ConfigError(Exception):
    """配置有问题时抛出。"""

class MissingKey(ConfigError):
    """配置里缺了必填项。"""
```

实测：调用方 `except MissingKey` 能精确捕到"缺配置项"这一类，而不用去猜 `KeyError` 是字典的、还是配置的。

值得写的信号：

- 同一个错误在多个地方出现，你想统一处理；
- 你想让调用方**只捕这一类**，而不是捕 `Exception`；
- 你想在异常上带额外信息（比如"缺的是哪个键"）。

不值得写的信号：只是为了换个名字好看。`raise ValueError("年龄必须是整数")` 已经足够清楚。

### 7.2 继承谁、怎么命名

- 继承 `Exception`（或你自己的异常基类），**不要继承 `BaseException`**——那是给"退出/中断"这类系统级事件用的；
- 类名以 `Error` 结尾（`ConfigError`、`MissingKeyError`），跟标准库一致；
- 给一个基类（`ConfigError`），下面挂具体子类，调用方可以"捕大类"也可以"捕小类"。

自定义异常会写了，下一节看两种风格：EAFP 与 LBYL。

## 8. EAFP 与 LBYL

两种风格，名字来自两句英语：

- **LBYL**（Look Before You Leap）：先检查，再动手；
- **EAFP**（Easier to Ask Forgiveness than Permission）：先动手，出错再处理。

同一个需求（取字典里可能不存在的键）两种写法：

```text
  LBYL 结果 = '默认值'；EAFP 结果 = '默认值'
```

| 场景 | 推荐 | 理由 |
|---|---|---|
| 字典取键、可能缺 | `d.get(k, 默认)` | 两种风格都有更简写法，不必二选一 |
| 检查与使用之间可能被改（文件、并发） | EAFP | 检查完文件还在，不代表打开时还在 |
| 检查成本很高、失败结果简单 | LBYL | 提前拦住更省事 |
| 异常代表"不该发生" | 让它抛 | 不要用异常代替普通分支 |

最后一条值得强调：**异常是给"意外"用的，不是给"常规分支"用的。** 用异常做正常流程控制（比如"用异常判断循环结束"）会让代码难读、也慢。第 14 讲的 `StopIteration` 是语言内部用法，不是鼓励你这么写业务逻辑。

两种风格分清了，下一节列一张常见异常对照表。

## 9. 常见内置异常对照

| 异常 | 典型触发 |
|---|---|
| `KeyError` | 字典取不存在的键 |
| `IndexError` | 列表/字符串下标越界 |
| `ValueError` | 类型对但值不对，如 `int("abc")` |
| `TypeError` | 类型不对，如 `"a" + 1` |
| `ZeroDivisionError` | 除以零 |
| `AttributeError` | 对象没有这个属性/方法，如 `"abc".nonexistent()` |
| `FileNotFoundError` | 打开不存在的文件 |
| `NameError` | 用了没定义的名字 |
| `ImportError` / `ModuleNotFoundError` | 导入失败（第 17 讲） |

实测九条里有七条在本讲脚本里逐个触发过，类型名与预期一致。记住"哪个操作会抛哪个异常"，写 `except` 才不会捕错。

对照表列完，下一节把本讲收起来。

## 10. 这一讲留下的东西

- `traceback` 从下往上读：最后一行是类型+消息，最下面那块是出错位置，上面是调用链。
- `try` 四段：`try` 放可能出错的几行、`except` 处理、`else` 放成功后的动作、`finally` 收尾。
- `except` 从上往下匹配，子类写在父类前；捕宽了掩盖 bug，捕窄了漏错。
- 裸 `except` 会抓 `BaseException`，连 `SystemExit` / `KeyboardInterrupt` 都吞；`except: pass` 更糟。
- `finally` 里写 `return` 会覆盖返回值、甚至吞掉异常；收尾优先用 `with`。
- `raise` 重新抛出保留 traceback；`raise ... from ...` 保留原始原因。
- 自定义异常用于"让调用方能分类捕获"，继承 `Exception`、名字以 `Error` 结尾。
- 异常用于意外，不用于常规分支；EAFP 与 LBYL 各有适用。

## 本讲小结

- 实测 traceback：三层调用 + `FileNotFoundError: [Errno 2] No such file or directory: 'config.ini'`。
- 四段顺序实测：正常 `['try','else','finally']`，出错 `['try','except','finally']`。
- `except` 匹配实测：`KeyError`→KeyError 分支、`IndexError`→LookupError 分支、`ValueError`→Exception 分支。
- 裸 `except` 抓 `SystemExit(3)` 后退出码变 0；`except Exception` 不抓，退出码保持 3。
- `finally` 里的 `return` 覆盖返回值（`'finally 的返回值'`），并把 `ValueError` 吞成正常返回（`'错误被吞掉了'`）。
- `raise ... from exc` 后 `exc.__cause__` 不为 `None`，两层原因都留得住。
- 自定义 `MissingKey(ConfigError)` 能被精确捕获。
- 九种内置异常逐个触发，类型与预期一致。

**Q1.** 下面代码有什么问题？给出更合适的写法。

```python
try:
    n = int(input("请输入数字: "))
    print(100 / n)
except:
    pass
```

**参考答案：** 两个问题：裸 `except` 会吞掉一切（包括 `Ctrl+C` 和 `SystemExit`），`pass` 又让错误完全消失。用户输入 `abc` 或 `0` 时程序什么也不说，看起来"没事"。

更合适的写法：

```python
try:
    n = int(input("请输入数字: "))
    print(100 / n)
except ValueError:
    print("请输入一个整数")
except ZeroDivisionError:
    print("不能除以 0")
```

两类错误分开处理、给出明确提示。剩下的异常（比如真的出现了意料之外的问题）就让它抛出来——崩得清楚比悄悄错好。

**Q2.** 下面两个函数，`f()` 返回什么？`g()` 返回什么？为什么？

```python
def f():
    try:
        return "A"
    finally:
        return "B"

def g():
    try:
        raise ValueError("x")
    finally:
        return "B"
```

**参考答案：** `f()` 返回 `"B"`，`g()` 也返回 `"B"`。

原因：`finally` 里的 `return` 会覆盖 `try` 的返回值；在 `g()` 里它还会把 `ValueError` 直接吞掉——函数正常返回，调用方完全不知道出过错。

这就是"`finally` 里不要写 `return`"的原因。`finally` 只该做收尾（关文件、释放资源），不该决定函数返回什么。

**Q3.** 写一个函数 `load_config(path)`：文件不存在时返回空字典 `{}`，JSON 格式错误时抛出一个自定义异常 `ConfigFormatError`，并保留原始的解析错误。

**参考答案：** 两个分支分别处理，再用 `from` 保留原始错误：

```python
import json

class ConfigFormatError(Exception):
    """配置文件格式不对。"""

def load_config(path):
    try:
        with open(path, encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        return {}
    except json.JSONDecodeError as exc:
        raise ConfigFormatError(f"配置文件格式错误: {path}") from exc
```

三个要点：文件不存在是"正常情况"，返回空字典；格式错误是"异常情况"，抛自定义异常；用 `from exc` 保留原始 `JSONDecodeError`，traceback 里能看到真正的出错位置。

注意 `try` 只包住 `open` 与 `json.load`，没有把调用方的事也包进来。

**Q4.** 为什么 `except LookupError:` 写在 `except KeyError:` 前面会让后者失效？给出正确顺序。

**参考答案：** 因为 `KeyError` 是 `LookupError` 的子类，`except` 从上往下匹配、命中即停，所以父类 `LookupError` 会先把 `KeyError` 吃掉，后面的分支成了死代码。

正确顺序是从具体到宽泛：

```python
except KeyError:
    ...
except LookupError:
    ...
except Exception:
    ...
```

判据：**能捕到的东西越少的分支越靠前。**

**Q5.** 一个脚本用 `except:` 包住了主循环，另一个人用 `Ctrl+C` 想停下它，发现停不了。解释原因，并给出修法。

**参考答案：** `Ctrl+C` 在 Python 里会抛 `KeyboardInterrupt`，它继承自 `BaseException` 而不是 `Exception`；裸 `except:` 等价于 `except BaseException:`，所以把这个中断信号也抓走了，循环继续跑。

修法：把裸 `except` 改成 `except Exception:`（这样 `KeyboardInterrupt` 与 `SystemExit` 都能正常穿过），并且尽量只捕你知道怎么处理的那几类。

顺带：如果确实需要在退出前做清理，用 `try/finally` 或 `with`，不要靠"抓所有异常再判断类型"。

**Q6.** 判断对错并说明理由：
(a) 异常处理的目标是让程序永不崩溃；(b) `finally` 一定执行；(c) 自定义异常必须继承 `BaseException`；(d) `with` 可以替代大部分 `try/finally`。

**参考答案：** 四条逐一看：

- (a) 错。目标是"让意外有名字、有位置、有处理方式"。有些错误就该让程序停下来（配置缺失、磁盘满），继续跑只会产生更坏的结果。
- (b) 对。无论正常结束、异常、还是 `return`，`finally` 都会执行——这也正是它在里面写 `return` 会出问题的原因。
- (c) 错。应该继承 `Exception`。`BaseException` 是留给 `SystemExit`、`KeyboardInterrupt` 这类系统级事件的。
- (d) 对（针对"资源收尾"这一用途）。`with` 在离开代码块时自动调用清理逻辑，比自己写 `try/finally` 更不容易漏；但 `with` 只覆盖"进入/退出"这一对动作，`finally` 还能表达更一般的"无论如何都要做的事"。
