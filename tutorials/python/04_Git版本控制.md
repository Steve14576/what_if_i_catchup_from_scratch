# 第 04 讲 Git：把版本变成可回退的结构

> **前置**：第 02 讲（命令行、当前目录、路径）。不需要任何 git 基础。
> **预计时间**：约 2.5 小时（第 3、5、7 节必须跟着敲一遍，只看会记不住）。
> **本讲回答**：git 存的是"差异"还是"快照"？工作区、暂存区、提交历史为什么要有中间那一层？`add` 之后又改了文件，提交进去的是哪一份？提交消息写给谁看？改坏了怎么退，`restore` 和 `revert` 差在哪？分支是不是把代码复制了一份？哪些东西绝对不能提交？
> **本讲结束你能做到**：在一个空目录建仓库，做三次有意义的提交，看懂 `git status` 的两个字符，改坏后准确回退，用分支做一个隔离的改动，配好 `.gitignore`。

## 0. 这一讲要解决的麻烦

你写作业的习惯是：`作业.docx`、`作业-改.docx`、`作业-真的最后一版.docx`、`作业-最后一版-导师看过.docx`。三天后你想知道"上周三那版里那段话到底怎么写的"，只能一个个打开比对，还比不出来。

git 解决的就是这件事，而且解决得比"多存几份"彻底：它给每一次保存留一个**带说明的快照**，你能随时回到任何一个快照，能看出两次之间改了哪几行，还能从历史中间分出一条线去试新想法，试失败了直接扔掉，原线不受影响。

## 1. git 到底存什么

### 1.1 快照，不是"增量备份"

一个常见误解：git 每次只存"这次改的那几行"。这个说法在**效果**上不算错（它内部确实对相同内容去重），但它会误导你对行为的预期。正确的理解是：**每个提交都是一份完整的快照**，你可以从任何一个提交里取出任何一个文件的完整内容。

这条有实测支撑。下面这段是一次真实运行的节选（脚本 `scripts/lec04-01_demo_git.py`）：

```text
$ git show HEAD:hello.py
  print("hello, git")
  print("version 1")
```

`git show HEAD:hello.py` 的意思是"把当前提交里的 `hello.py` 整份打印出来"。整份都能取出来，说明提交里存的不是"补丁"，而是那一刻文件的完整状态。

顺带说清两个词：

- **提交**（commit）：一次保存动作的产物，包含当时的完整文件树、作者、时间、一句说明，以及一个由内容算出来的**哈希值**（一长串十六进制，例如 `88f58f5`）。哈希用来唯一标识这个提交，改了任何内容哈希就会变。
- **HEAD**：一个指针，指向"你现在所在的那个提交"。`HEAD:hello.py` 就是"取当前提交里的这个文件"。

本讲后面出现的哈希都是某次真实运行的例子，**你敲出来的会不一样**，这不影响结果。

### 1.2 装 git 与第一次配置

Windows 上三条路，选一条：

- 官网 `git-scm.com` 下载安装器，一路默认即可；
- `winget install Git.Git`；
- 便携版 PortableGit（解压即用，适合机房）。

macOS 通常自带；没有就 `brew install git`。Linux 用发行版的包管理器。

装完验证：

```powershell
git --version
```

```text
git version 2.55.0.windows.2
```

第一次使用前必须告诉 git 你是谁，因为每个提交都会记下作者：

```powershell
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

`--global` 表示写进你的用户配置文件（Windows 上是 `C:\Users\你\.gitconfig`），以后所有仓库都用这套身份。**这是整个课程里唯一一处需要修改全局配置的地方**，因为提交必须署名。想给某个仓库用别的身份，去那个仓库里不带 `--global` 再设一次，覆盖全局。

查看当前配置：

```powershell
git config --list
```

### 1.3 建仓库：`git init`

在项目目录里执行：

```powershell
git init -b main
```

```text
Initialized empty Git repository in C:/Users/.../demo-repo/.git/
```

`-b main` 指定初始分支名叫 `main`（老教程里叫 `master`，只是名字不同）。

执行完目录里多了一个 `.git` 文件夹，实测 `(repo / ".git").is_dir()` 为 `True`。这个目录就是仓库本体：**所有历史、所有提交、所有分支都装在里面**。删掉它，这个目录就退回一个普通文件夹（历史全没了，但工作区的文件还在）。

一条纪律：**不要在仓库里再建仓库**。把项目 A 放在项目 B 的目录里，两边都会把对方的文件当自己的，`status` 会变得难以理解。

## 2. 三区模型：为什么要有暂存区

git 把你的文件分成三个位置：

```text
  工作区                  暂存区                    提交历史
（你在编辑的文件）      （下一次提交的内容）        （只读的快照链）

  工作区  --git add-->  暂存区  --git commit-->  提交历史
  工作区  <--git restore--  暂存区
  暂存区  <--git restore --staged--  提交历史
```

- **工作区**（working tree）：你打开、编辑的那些文件，就是硬盘上的真文件。
- **暂存区**（staging area / index）：一份"下一次提交要包含什么"的清单。
- **提交历史**：已经保存下来的快照链，只追加、不改写。

为什么要有中间那一层？两个实际理由：

1. **你能挑**。今天顺手改了三处，其中两处是完整的功能、第三处是调试时临时加的 `print`。有暂存区，你可以只把前两处 `add` 进去提交，第三处留在工作区继续用。
2. **提交前有一次预览**。`git status` 与 `git diff --staged` 让你先看清"这次到底要提交什么"，再按回车。没有这一层，`commit` 就等于"把所有改动一把交上去"。

### 2.1 `git status` 的两个字符在读什么

新建文件后的第一次查看（实测）：

```text
$ git status --short
  ?? hello.py
```

`??` 两个问号的意思是"这个文件 git 从来没管过"（untracked）。`add` 之后：

```text
$ git add hello.py
$ git status --short
  A  hello.py
```

变成 `A`（added，已暂存待提交）。注意这里**只有两个字符位，分别代表两边**：第一位是暂存区相对上次提交的状态，第二位是工作区相对暂存区的状态。

| 显示 | 第一位（暂存区） | 第二位（工作区） | 含义 |
|---|---|---|---|
| `??` | ? | ? | 新文件，git 没管过 |
| `A ` | A | 空格 | 新增，已暂存 |
| ` M` | 空格 | M | 已跟踪，工作区改过，未暂存 |
| `M ` | M | 空格 | 改动已暂存，待提交 |
| `MM` | M | M | 暂存了一份，之后又改了 |
| `UU` | U | U | 合并冲突，两边都改了同一处 |

记住"两位分别读"，`status` 就不会再让你迷惑。

### 2.2 关键实验：`add` 之后又改，提交进去的是哪一份

这是本讲最重要的一个实验，因为它决定了你对"暂存"的理解是不是真的。

步骤：先把 v1 `add` 进暂存区，然后**不提交**，把文件改成 v2，再提交。实测结果：

```text
$ git commit -m "加入问候与版本号"
  [main (root-commit) 88f58f5] 加入问候与版本号
   1 file changed, 2 insertions(+)

$ git show HEAD:hello.py
  print("hello, git")
  print("version 1")

$ git status --short
   M hello.py
```

三件事同时成立：

1. 提交里是 **v1**（没有 `version 2` 那行）；
2. 工作区里文件已经是 **v2**；
3. `status` 显示出 ` M`——v2 还没被暂存。

结论：**`commit` 提交的是暂存区里的内容，不是你此刻屏幕上的文件。** 这条一旦记住，就不会再出现"我明明改了，怎么提交上去还是旧的"这种事。

### 2.3 三种 diff 各看哪一段

`git diff` 不是只有一个版本，它比的是"两个位置之间"：

- `git diff`：工作区 vs 暂存区（**还没暂存**的改动）
- `git diff --staged`：暂存区 vs 当前提交（**这次将要提交**的改动）
- `git diff HEAD`：工作区 vs 当前提交（两边合起来看）

实测三段，正好把它们串起来：

```text
# 文件改到 v2，还没 add
$ git diff
  @@ -1,2 +1,3 @@
   print("hello, git")
   print("version 1")
  +print("version 2")

# 此时暂存区还是 v1，所以与已提交内容没有差别
$ git diff --staged
  (无输出)

# add 之后
$ git diff
  (无输出)

$ git diff --staged
  @@ -1,2 +1,3 @@
   print("hello, git")
   print("version 1")
  +print("version 2")
```

读 diff 只需要四个记号：`---` 是旧文件，`+++` 是新文件，`-` 开头的行是删掉的，`+` 开头的行是新加的。`@@ -1,2 +1,3 @@` 是"旧文件第 1 行起 2 行、新文件第 1 行起 3 行"，行号对不上时看它。

## 3. 提交：消息是写给谁看的

提交记录实测长这样：

```text
$ git log --oneline
  a754490 补上版本号第二行
  88f58f5 加入问候与版本号
```

每一行是"短哈希 + 消息"。消息的读者不是 git，是**三个月后的你**，以及和你一起干活的人（包括 AI 工具——它读历史时只能看到这些消息）。

| 坏消息 | 为什么坏 | 好消息 | 为什么好 |
|---|---|---|---|
| `update` | 更新了什么？范围多大？ | `修复读取 CSV 时空行导致的 IndexError` | 说清改了什么、为什么改 |
| `修改` | 和没写一样 | `把成绩计算拆成 total 与 average 两个函数` | 能对应到具体结构变化 |
| `111` | 只有你当时的脑子懂 | `补上 .gitignore，忽略 .venv 与 __pycache__` | 一眼知道涉及哪些文件 |

两条习惯：

- **一次提交只做一件事**。把"修 bug"和"重排格式"混在一个提交里，将来想单独撤销其中一件就做不到。
- **小步提交**。一天一次大提交，等于没有历史；每完成一个能说清的小改动就提交一次。

## 4. 回退：三个层次，别用错工具

回退的关键是"你要退哪一层"。按严重程度从轻到重：

| 你想退的东西 | 命令 | 结果 |
|---|---|---|
| 工作区里还没 `add` 的改动 | `git restore 文件名` | 文件恢复成暂存区里的样子，改动**丢失** |
| 已经 `add` 进暂存区、但还没提交 | `git restore --staged 文件名` | 取消暂存，工作区不变（改动还在） |
| 已经提交、想撤掉这次提交 | `git revert 哈希` | 生成一条**新的**提交，内容是把那次改动反向抵消 |

### 4.1 先看 diff，再动手

改坏之后的第一件事永远是 `git diff` 或 `git status`，先确认"坏在哪、范围多大"，再决定退哪一层。

实测：把一个能跑的文件改成少右括号、少引号的坏文件，并 `add` 进去：

```text
$ git diff --staged
  @@ -1,3 +1,2 @@
  -print("hello, git")
  -print("version 1")
  -print("version 2")
  +print("hello, git"
  +print("version 1"
```

diff 一眼就能看出三行被替换成两行残缺的代码。

### 4.2 取消暂存，再决定是否丢弃

```text
$ git restore --staged hello.py
$ git status --short
   M hello.py
```

暂存区干净了，但工作区还是坏的——这一步只"撤回暂存"，没有动你的文件。然后运行确认它确实坏了：

```text
  运行 hello.py: 退出码=1  最后一行=SyntaxError: '(' was never closed
```

再丢弃工作区的坏改动：

```text
$ git restore hello.py
  运行 hello.py: 退出码=0  最后一行=version 2
```

两步分开做的好处是：**你始终有一次反悔的机会**。如果先 `restore` 再发现"其实我改对了一半"，那一半也没了。

### 4.3 已经提交了怎么办

已经进了历史的提交，不要试图"让它没发生过"。正确做法是 `git revert 哈希`：它读那次提交的内容，算出"把它反向抵消"的改动，然后**生成一条新的提交**。历史只增不改，别人拉取时不会乱。

新手常见的危险动作是"改写历史"，例如强行把分支指针往回挪并丢弃工作区。这类命令一旦敲错，未提交的改动会直接消失且无法恢复。本课程不要求你用它：**要撤销已提交的东西，用 `revert`；要丢弃未提交的改动，用 `restore`；两者都不涉及"抹掉历史"。**

## 5. 分支：一条可以分叉的历史

### 5.1 分支不是复制代码

建一个分支、在上面加一行、提交，然后切回 `main` 看文件内容：

```text
$ git switch -c feature
  Switched to a new branch 'feature'

$ git switch main
  Switched to branch 'main'

  hello.py 现在的内容：
  print("hello, git")
  print("version 1")
  print("version 2")
```

那行"只在分支上加的"消失了。这个过程没有复制任何文件夹——**分支只是一个指向某个提交的名字**，切换分支就是让 `HEAD` 指向另一个名字，然后把工作区的文件换成那个提交的样子。

这解释了两件事：

1. 建分支是瞬间完成的，不管项目多大；
2. 切分支会改变你看到的文件内容，所以切换前要保证工作区的改动已经提交或暂存（否则 git 会拦你或把改动带过去）。

### 5.2 合并：快进与真正的合并

把 `feature` 合回 `main`：

```text
$ git merge feature
  Updating a754490..e6a91ed
  Fast-forward
   hello.py | 1 +
   1 file changed, 1 insertion(+)
```

这次是**快进**（fast-forward）：`main` 在分叉后没有新提交，所以 git 只需把 `main` 的名字往前挪一格，不用真的"合并"。

看一下图形化的历史：

```text
$ git log --oneline --graph --all --decorate
  * e6a91ed (HEAD -> main, feature) 分支上增加一行说明
  * a754490 补上版本号第二行
  * 88f58f5 加入问候与版本号
```

`(HEAD -> main, feature)` 表示三个东西此刻都指向同一个提交——因为快进之后，`main` 和 `feature` 是同一条线的同一个点。

### 5.3 冲突：两边改了同一处

如果两个分支改了同一行，git 不会替你猜。实测（`main` 与 `side` 都改了第一行）：

```text
$ git merge side
  Auto-merging hello.py
  CONFLICT (content): Merge conflict in hello.py
  Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
  UU hello.py
```

`UU` 就是我们前面表格里那个状态。此时打开文件，会看到这样的标记：

```text
<<<<<<< HEAD
print("main 改的第一行")
=======
print("side 改的第一行")
>>>>>>> side
print("version 1")
...
```

规则很直白：`<<<<<<< HEAD` 到 `=======` 之间是**当前分支**的内容，`=======` 到 `>>>>>>>` 之间是**对方分支**的内容。解决办法是手工改成你想要的样子（可以取一边，也可以两边合成一句），删掉三行标记，然后：

```text
$ git add hello.py
$ git commit -m "解决冲突：合并两边的第一行"
```

冲突不是错误，它只是 git 在说"这里需要人的判断"。整场冲突里最费时间的是**想清楚最终要什么**，命令只有三步。

## 6. `.gitignore`：哪些东西不该进仓库

仓库只该装"换台机器也需要的、人写的"东西。实测在一个仓库里放上这四类文件后：

```text
$ git status --short
  ?? .gitignore
  ?? data.csv
```

`.venv/`、`__pycache__/`、`debug.log` 三个都不见了。原因是 `.gitignore` 里写了三条规则：

```text
.venv/
__pycache__/
*.log
```

想确认某条规则为什么生效，用：

```text
$ git check-ignore -v debug.log
  .gitignore:3:*.log	debug.log
```

它指到"第 3 行、`*.log` 这条规则"。

| 该进仓库 | 不该进仓库 | 理由 |
|---|---|---|
| 源码 `.py` | `.venv/` | 环境可重建（第 03 讲），体积大且与机器绑定 |
| `README.md` | `__pycache__/` | 解释器自动生成的缓存（第 01 讲讲过的字节码） |
| 依赖清单 `requirements.txt` / `pyproject.toml` | 数据大文件 | 会让仓库变得极慢，且无法有效比对差异 |
| `.gitignore` 本身 | 密钥、令牌、`.env` | 一旦推送到公开仓库，等于公开泄露，且历史里很难彻底清除 |

一条容易踩的坑：**已经被提交过的文件，后来加进 `.gitignore` 不会自动消失**。规则只对"未被跟踪"的文件生效。要让它退出仓库，得先把它从跟踪列表里移除（保留本地文件），再提交一次。这个操作等你真遇到再查，不必现在记。

## 7. 远程仓库：知道存在就够

前面所有操作都只发生在你本机，**没有网络也能完整使用 git**。远程仓库（GitHub、Gitee、学校自建 Git 服务）是额外一层"备份 + 协作"：

- `git clone 地址`：把远程仓库整份拉到本地（含历史）；
- `git push`：把本地的提交送上去；
- `git pull`：把别人的提交拉下来并合入。

本讲不展开远程操作，因为在你还没写顺本地提交之前，远程只会增加变量。第 26 讲做小项目收尾时会再提一次。

一条纪律现在就要立：**先确认 `.gitignore` 生效，再第一次 `push`**。密钥一旦进了远程历史，删掉文件并不等于删除历史记录。

## 8. 日常工作流：五步

实际写代码时，这个循环会重复几百次：

```powershell
git status          # 我现在有什么改动
git diff            # 具体改了什么
git add 文件名      # 挑选这次要提交的部分
git commit -m "做了什么"
git log --oneline   # 确认历史长什么样
```

再补两条习惯：

- 开始干活前先 `git status`，确保工作区是干净的（没有昨天遗留的半成品改动）；
- 每天收工前提交一次能跑通的版本。**"能跑通"比"写完了"重要**——历史的价值在于能回到一个可用状态。

## 9. 这一讲留下的东西

- 每个提交是一份完整快照，`git show HEAD:文件` 能取出整份内容。
- 三区模型决定了 `commit` 提交的是**暂存区**，不是你此刻的文件；`status` 两个字符位分别读。
- 回退分三层：`restore`（丢工作区改动）、`restore --staged`（取消暂存）、`revert`（抵消一次已提交的改动）。
- 分支是指向提交的名字，不是复制代码；冲突是两边改同一处，解决方式是手工定稿 + `add` + `commit`。
- `.gitignore` 决定什么不进仓库；`.venv/`、`__pycache__/`、数据大文件、密钥都不进。

下一讲换个更大的视角：工具那么多，到底该怎么面对它们。

## 小结

- `git init -b main` 在目录里建出 `.git`，历史全在里面；删掉 `.git` 就不是仓库了。
- 提交前必须配置 `user.name` 与 `user.email`，这是唯一需要改全局配置的地方。
- 三区：工作区、暂存区、提交历史；`add` 把改动搬进暂存区，`commit` 把暂存区固化成快照。
- `add` 之后再改文件，提交进去的是**暂存区那一份**（实测提交里没有后加的那行）。
- `status` 两个字符位：第一位是暂存区状态，第二位是工作区状态；`??`、`A `、` M`、`MM`、`UU` 各有明确含义。
- `git diff` 看未暂存改动，`git diff --staged` 看将要提交的改动。
- 提交消息写"改了什么、为什么"，一次提交只做一件事，小步提交。
- 回退分三层：`restore`、`restore --staged`、`revert`；不要用"改写历史"的方式抹掉提交。
- 分支是指针不是副本；合并可能是快进；冲突用 `<<<<<<<` / `=======` / `>>>>>>>` 标出两边，手工定稿后再提交。
- `.gitignore` 让环境目录、缓存、日志、数据、密钥不进仓库；已被跟踪的文件加规则不会自动退出。

## 作业

**Q1.** 你写了 `a.py` 并执行了 `git add a.py`，随后又改了 `a.py` 的一行，然后直接 `git commit -m "改了一行"`。这次提交里包含你最后改的那一行吗？为什么？怎么补救？

**参考答案：** 不包含。`commit` 提交的是暂存区的内容，而暂存区是在 `add` 那一刻生成的快照；`add` 之后的修改只存在于工作区，`git status --short` 会显示 `MM`（暂存了一份，工作区又改了）。

补救：再执行一次 `git add a.py`，然后 `git commit -m "补上后改的那一行"`。或者——更符合"一次提交一件事"的做法——用 `git commit -m "..."` 前先 `git diff --staged` 确认这次要提交的内容。

**Q2.** 下面的 `git status --short` 输出，逐行解释每个符号的意思：

```text
 M report.py
A  notes.md
?? data/tmp.csv
UU merge_test.py
```

**参考答案：** 四种状态依次对应：

- ` M report.py`：文件已被跟踪，工作区改过但还没暂存（第一位空格=暂存区无差别，第二位 M=工作区有改动）。
- `A  notes.md`：新文件已加入暂存区，等待提交（第一位 A，第二位空格）。
- `?? data/tmp.csv`：全新文件，git 从未跟踪过。
- `UU merge_test.py`：合并冲突，两边都改了同一处，需要手工解决后 `add`。

**Q3.** 你把 `hello.py` 改坏了，但已经 `git add` 了。现在想"先退掉暂存、确认一下哪里坏了、再决定是否丢弃"。写出两条命令并说明每一步之后的状态。

**参考答案：** 先执行下面两条，再决定是否丢弃：

```powershell
git restore --staged hello.py
git status --short
```

第一条把文件从暂存区撤出，暂存区回到上次提交的状态，**工作区文件不变**（还是坏的）；此时 `git status --short` 显示 ` M hello.py`。确认坏在哪之后，如果决定丢弃这次修改：

```powershell
git restore hello.py
```

工作区文件恢复成暂存区（也就是上次提交）的样子，坏改动消失。如果不想丢弃，就不要执行第二条，继续在坏文件上修。

**Q4.** `git restore` 和 `git revert` 都在"撤销"，它们的区别是什么？各自适用于什么情况？

**参考答案：** `git restore` 撤销的是**还没提交**的改动，它直接用暂存区（或指定提交）的内容覆盖工作区文件，改动直接消失、不可恢复。适用于"我这段改坏了，退回上次提交的样子"。

`git revert` 撤销的是**已经提交**的改动，它不改写历史，而是生成一条新提交，内容是把目标提交的改动反向抵消。适用于"这次提交有问题，但我不想让历史消失"（尤其是已经推送到远程、别人可能拉过的情况）。

**Q5.** 你在 `feature` 分支上加了功能、提交了；`main` 在这期间没有新提交。此时 `git merge feature` 会发生什么？如果 `main` 期间也提交了别的内容，又会怎样？

**参考答案：** `main` 没有新提交时，合并是**快进**（fast-forward）：git 只是把 `main` 的指针向前挪到 `feature` 的位置，不产生新的合并提交。实测输出为 `Fast-forward`，合并后 `main` 与 `feature` 指向同一个提交。

如果 `main` 期间也有新提交，两边就分叉了，git 需要做一次真正的合并：能自动合并的部分直接合并，产生一个合并提交；如果两边改了同一行，就会报冲突（`UU`），需要手工定稿后 `add` + `commit`。

**Q6.** 你的项目里有一个 `.venv` 目录、一个 `__pycache__` 目录、一个 `debug.log`、一个 `data.csv`。哪些应该提交，哪些应该忽略？写出 `.gitignore` 的相应内容，并说明为什么。

**参考答案：** `.venv` 与 `__pycache__` 应该忽略：前者是虚拟环境，可由 `requirements.txt` 或 `pyproject.toml` 重建，体积大且与机器绑定（第 03 讲）；后者是解释器生成的字节码缓存（第 01 讲），每次运行都可能变。`debug.log` 是运行产生的日志，也不该提交。`data.csv` 要看情况：小规模示例数据可以提交（方便别人复现），大型数据文件应该忽略并在 README 里说明来源。

`.gitignore` 内容：

```text
.venv/
__pycache__/
*.log
```

验证方式：`git status --short` 里看不到这三类文件，`git check-ignore -v debug.log` 能指出是哪条规则命中的，实测输出形如 `.gitignore:3:*.log	debug.log`。
