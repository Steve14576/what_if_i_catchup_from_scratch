# 第 05 讲 工程素养：工具学不完，那你学什么

> **前置**：第 01–04 讲（程序怎么被执行、命令行、环境、git）。这一讲不要求动手，但建议边读边在自己机器上找对应位置。
> **预计时间**：约 2 小时（不背东西；目标是建立索引，不是记住按钮）。
> **本讲回答**：工科生到底要面对多少类工具？为什么永远学不完？面对一个陌生工具，先问哪四个问题？什么时候该想到用哪个？做笔记、问问题、信任抽象层级、给 AI 权限、版本保护这些事，最容易栽在哪？
> **本讲结束你能做到**：把任意一个新工具放进地图的某一格；用四个问题判断它值不值得现在学；说出八类会反复踩的坑，并为每一类给出自己的动作。

## 0. 场景：装了十二个工具，一个都没用起来

你的电脑上可能已经装了这些：VS Code、PyCharm、Cursor、Anaconda、Git、Node、Obsidian、Docker……每个都点开过一次，界面上有几十个按钮，看不懂；遇到问题还是只会把报错复制到搜索框里碰运气。

问题不是"工具不够"，也不是"你笨"。问题是**没有索引**：你不知道这些工具各自站在哪个位置、解决哪一类问题，所以每次遇到问题都无法把"症状"翻译成"该找谁"。

这一讲就是建这张索引。它不教你快捷键，也不教你点哪几个菜单——那些东西查文档比记笔记可靠得多，而且三个月不用就会忘。这一讲教的是**不会忘的部分**。

和前面四讲一样，这一讲属于素养卷：看不懂的地方可以先跳过，第 09 讲开始写 Python 不依赖这里的任何内容。但你越往后写，越会频繁回头用它。

## 1. 先承认一件事：工具学不完

这不是悲观，是事实，而且必须先把这件事接受下来，否则你会一直处于"等我学完工具再开始"的状态。

三个具体事实：

- **同一类工具永远有十几个竞品**。编辑器有 VS Code、PyCharm、Sublime、Vim；包管理有 pip、uv、conda、poetry；笔记有 Obsidian、Notion、Logseq。你不可能都学，也不需要。
- **工具会死**。你今天花两周学的某个软件，两年后可能停止维护。依附于具体按钮的知识，寿命最短。
- **能力不会死**。知道"依赖冲突是什么、怎么隔离"，换任何工具都能用；知道"改动要可回退"，换任何语言都成立。

所以学习目标要换成三层，从低到高：

1. **索引**：知道存在这么一类东西，以及它大概管什么事。
2. **判断**：遇到一个问题时，能用四个问题判断"该不该现在学它"。
3. **迁移**：真正需要时，能在几天内上手一个同类新工具。

这一讲主要建第 1、2 层。第 3 层靠你后面每次真用它时练。

## 2. 一张工具地图：按"它替你解决什么"分类

不要按厂商分，也不要按"难易"分。按**它解决什么问题**分，你才能在遇到问题时反向找到它。

| 类别 | 解决什么问题 | 你迟早会遇到的东西 | 什么时候会想到它 |
|---|---|---|---|
| 运行与依赖 | 让代码能跑起来、能装上别人写的包 | Python 解释器、`venv`、`pip`、`uv`、Anaconda / conda | 装完用不了、换台机器跑不起来、两个项目打架 |
| 写代码的地方 | 编辑、运行、看报错、调试 | VS Code、PyCharm、Cursor / Qoder（带 AI 的编辑器）、Jupyter | 打开文件发现没有高亮、运行按钮点了没反应 |
| 版本与协作 | 改动可回退、和别人一起改 | git、GitHub、GitLab | 改坏了、想知道上周改了哪行、要和同学合并 |
| 命令行与系统 | 批量操作、装系统级软件 | PowerShell / bash、`winget` / `brew` / `apt` | 教程让你"运行一条命令"、要装 Git 或 Python |
| 查资料 | 看懂报错、查某个函数怎么用 | 官方文档、Stack Overflow、GitHub Issues、Reddit | 报错看不懂、搜到的答案和你版本不一样 |
| 模型与数据 | 找现成的模型与数据集 | Hugging Face、Kaggle | 要做分类/生成任务，不想从零训练 |
| 笔记与知识管理 | 留住结论、下次能查回来 | Obsidian、Notion | 同一个坑踩第二次、想整理学习记录 |
| AI 助手 | 写代码、解释代码、改代码 | 聊天式、编辑器内联、命令行代理（Claude Code / Codex 类） | 卡住、想快速写样板、想读懂别人的代码 |

这张表最重要的用法是**反向查**：先有症状，再回到表里找类别。第 4 节会把常见症状直接列出来。

三类 AI 工具的差别和用法，第 06、07 讲专门说；这一讲只在地图上标出位置。

## 3. 四个问题：把一个陌生工具放回地图

遇到任何新工具（教程里提到的、同学推荐的、招聘要求里的），先问这四个问题。四个都答不上来，就先别装。

1. **它替我解决什么问题？不用它会怎样？**
   答不出"不用会怎样"，说明你现在不需要它。
2. **输入是什么，输出是什么？**
   给它代码？给它一个网址？给它一个文件夹？它产出文件、产出网页、还是只产出文字？
3. **它改的是哪一层？**
   只读文件？改你的项目文件？改你的环境（装包、改 `PATH`）？改远端仓库？改的是别人服务器上的东西？
   **这一问直接决定风险等级**：改环境的要能回退，改远端的要能撤销，改别人服务器的要格外小心。
4. **出问题时我去哪看证据？**
   日志在哪、退出码怎么看、配置文件在哪、版本号怎么查。答不出这一问的工具，出问题就只能靠猜。

### 3.1 演示一：uv（第 03 讲见过，这里用四问回收）

- 解决什么：建虚拟环境、装包，比 `venv` + `pip` 快一个量级。不用它会怎样？慢一些，但没有功能缺失——所以它是"加速器"不是"必需品"。
- 输入输出：输入一条命令（`uv venv`、`uv run`），输出是磁盘上的一个环境目录，或一次命令的执行结果。
- 改哪一层：改你的项目目录（建 `.venv`）与本地缓存，不改远端。
- 证据在哪：`uv --version`、`python -c "import sys; print(sys.prefix)"`（第 03 讲）、出错时的完整报错。

四问下来结论很清楚：**可以放心试，失败成本就是删掉一个目录**。这就是"判断"。

### 3.2 演示二：Obsidian（完全不同的类别）

- 解决什么：把结论留成可检索的本地笔记。不用会怎样？你会第二次踩同一个坑，且想不起来上次怎么解决的。
- 输入输出：输入你写的 markdown 文本，输出是一堆 `.md` 文件和一个可视化关系图。
- 改哪一层：只改你自己的笔记文件夹，不碰代码、不碰环境。
- 证据在哪：文件本身。它是纯文本，可以用 git 管、可以用任何编辑器打开——这一点比"某个云笔记软件"重要得多。

四问下来结论：**风险极低，但收益取决于你写什么**（见第 6.1 节的笔记陷阱）。

### 3.3 演示三：Hugging Face

- 解决什么：托管与分发训练好的模型、数据集、演示应用。不用会怎样？你要自己找模型权重、自己写下载脚本。
- 输入输出：输入任务类型（文本分类、语音识别…），输出一个可下载的模型仓库与说明页。
- 改哪一层：只在你主动下载时，往你的磁盘写文件；不碰你的项目结构。
- 证据在哪：模型说明页（model card）里的指标、许可证、更新时间与下载量。

四问下来结论：**现在只需要知道它存在**。等你真要做一个模型任务时再回来，那时四问会帮你判断"这个模型能不能用"。

## 4. 按症状索引：什么时候想到用哪个

新手最缺的不是知识，是"卡住时的第一反应"。下面这张表可以直接抄进你的笔记首页。

| 你的症状 | 先想到哪一类 | 本课程哪一讲 |
|---|---|---|
| 敲命令说"不是内部或外部命令" | 环境与 `PATH` | 02、03 |
| 装完了还是用不了、报 `ModuleNotFoundError` | 环境与依赖 | 03 |
| 改坏了、想回到上一版 | 版本控制 | 04 |
| 报错看不懂、程序跑到一半崩 | 调试与异常 | 18、24 |
| 不知道某个函数怎么用、参数什么意思 | 官方文档 | 一直 |
| 搜到的答案和我的版本对不上 | 查资料的方法 | 本讲 5.3 |
| 要读表格、算统计、导出结果 | 文件与数据 | 19、23 |
| 文件越写越大、改一处牵连一片 | 结构与模块 | 15、17、26 |

这张表的价值在于：**它把"我该干什么"从情绪问题变成查表问题**。卡住时先查表，比坐在那里怀疑自己有用得多。

## 5. 地图上的常客：是什么、怎么用、怎么对待

这一节是一份小词典，每条只说到"够你判断"的程度。

### 5.1 包与环境：pip、uv、conda / Anaconda

- **pip**：Python 官方生态的包安装器，第 03 讲用过。够用、通用、机房一定认它。
- **uv**：用 Rust 写的替代品，建环境和装包快很多，第 03 讲实测 `uv venv` 0.1 秒、`python -m venv` 4 秒级。本课程推荐但不强制。
- **conda / Anaconda**：Anaconda 是一个"发行版"，装完自带 Python、conda 包管理器、几百个科学计算包，以及 Spyder、Jupyter 这些界面。conda 与 pip 的关键区别是：**conda 能管理非 Python 的依赖**（比如某个 C 库、某个编译好的二进制），pip 只管 Python 包。
- 怎么对待：课程或实验室指定哪个就用哪个；**同一个项目里不要混用 conda 与 venv**，否则"包到底装哪了"会变成一个查不清的问题；Anaconda 体积有几 GB，磁盘紧张时别装。

### 5.2 代码托管：GitHub（以及 GitLab）

- **是什么**：放 git 仓库的网站。除了存代码，还有三样你现在就该知道的东西：
  - **README**：仓库首页的说明文件，通常写"这是什么、怎么装、怎么用"；
  - **Issue**：别人报的 bug 或提问，作者在这里回复；
  - **Pull Request（PR）**：别人改好了代码，请求合并进主仓库。
- **怎么用**：找到一个项目后，按顺序看四样——README、最近一次提交时间、Issue 里有没有人在回、许可证（License）。
- **怎么对待**：README 是作者的自我陈述，不是保证；"最后一次提交是三年前"通常意味着它已经不维护了；**永远不要在 Issue 里贴密钥、令牌或隐私数据**，那是公开的。

### 5.3 问答：Stack Overflow

- **是什么**：程序员问答站，答案可以投票、可以被别人编辑修订。
- **怎么用**：把**英文报错的原文**粘进搜索框，加版本号（例如 `Python 3.12`）；看被采纳的答案，也要看它下面的评论——评论里经常有"这个写法在新版本已失效"。
- **怎么对待**：高票不等于适用于你的版本，看日期；提问被 downvote（点踩）通常是因为没先搜、没给最小复现、没贴报错原文。这一条和第 6.4 节是同一件事。

### 5.4 社区：Reddit（例如 r/learnpython）

- **是什么**：论坛，口语化，回答质量参差。
- **怎么对待**：它适合回答"这条路值不值得走""大家都用什么"，不适合查精确的 API 用法；看到"某某最好"先看年份，再看有没有人反驳。

### 5.5 模型与数据：Hugging Face

- **是什么**：模型、数据集、演示应用（Spaces）的托管平台。
- **怎么用**：按任务类型搜 → 看模型说明页（model card）里的任务、指标、许可证、更新时间与下载量。
- **怎么对待**：现在只需要知道它存在。真正要用时，先看许可证与数据来源，再看指标是不是在你关心的场景上测的。

### 5.6 笔记：Obsidian（以及 Notion）

- **是什么**：Obsidian 是"本地 markdown 文件 + 双向链接"的笔记工具；Notion 是云端的文档数据库。
- **怎么用**：建一个文件夹，写 `.md` 文件，用 `[[文件名]]` 互相链接。因为就是纯文本，所以能进 git（第 04 讲）。
- **怎么对待**：工具本身不产生价值，**写什么**才产生价值。这一条在第 6.1 节展开。

### 5.7 AI 助手的三种形态

| 形态 | 你在哪遇到 | 它能做什么 | 主要风险 |
|---|---|---|---|
| 聊天式 | 网页/桌面对话窗口 | 解释代码、生成片段、改一段贴进去的代码 | 它看不到你的项目，容易给出"局部合理、整体不对"的答案 |
| 编辑器内联 | 编辑器里补全、选中改写 | 在当前文件上下文里改代码 | 改动范围小但频繁，容易一路 Tab 接受，最后不知道自己改了什么 |
| 命令行代理 | 终端里运行的助手（Claude Code、Codex 一类） | 读你的文件、跑命令、一次改多个文件 | 权限最大：能删文件、能装包、能改配置 |

怎么对待：**能力越强，边界越要自己划**。第 06 讲讲它为什么会犯错，第 07 讲讲怎么装怎么用，第 08 讲讲动完代码之后怎么审、权限怎么给。

## 6. 八类会反复踩的坑

这一节是这一讲真正值钱的部分。每条给三样：症状、为什么会这样、你能立刻做的动作。

### 6.1 笔记退化成手账

- **症状**：笔记有五颜六色的标题、贴纸、漂亮的目录，甚至有时间轴；但一周后你想不起"当时那个报错是怎么解决的"，因为笔记里只有抄来的概念，没有你自己的卡点。
- **为什么**：抄写有即时满足感，实操会挫败。人会自动选择前者。
- **动作**：给"笔记"设一条硬标准——**一页笔记里至少要有一条可执行的东西**：一条命令、一个复现步骤、一个判据（例如"退出码应为 0"）。做不到就不算笔记，只算摘抄。

### 6.2 怕笔记做不完，所以不敢动手

- **症状**：觉得"等我先把这套教程完整整理成笔记再开始练"，于是一直在整理。
- **为什么**：整理笔记是安全的，动手会暴露"我不会"。
- **动作**：先跑通，再记；允许笔记残缺、允许丑。**笔记记录的是"我在哪卡住、怎么判断它过去了"，不是教程的副本。**

### 6.3 忘了自己学的是工科

- **症状**：看完一段讲解，觉得"懂了"，但一动手就写不出来；或者写出来了，但说不清它对不对。
- **判据**：工科的"会"是**能跑、能测、能量、能复现**。看懂不算，能向别人复述也不算——能在一个新输入上得到正确结果才算。
- **动作**：每学一个东西，给自己出一道"换个输入还能不能对"的题（这也是本课程每讲留作业的原因）。

### 6.4 不会问问题（问人，也问 AI）

- **症状**：贴一张截图加一句"为什么不行"；或者反过来，把整个项目贴出去，让对方自己找。
- **四件套**：目标是什么；期望什么、实际什么；已经试过什么；环境与版本（操作系统、Python 版本、相关库版本）。
- **反面例子**："我的代码报错了，怎么改？"
- **正面例子**："运行 `python main.py` 时报 `FileNotFoundError: 'scores.csv'`（完整报错已附）。文件确实在 `data/scores.csv`。我试过改成绝对路径，能跑但我不想写死路径。Python 3.12，Windows。想让脚本在项目根目录运行时不依赖当前目录。"
- 为什么有效：前三句就把"最小复现"给出来了，对方（或 AI）不需要猜。

### 6.5 不信任抽象层级：要么全信，要么全疑

- **症状**：对某个库要么"它写什么我就照抄"，要么"这玩意儿肯定有坑，我不敢用"。
- **正确的分法**：
  - **底层**（语言语义、文件系统、编码）：要真懂，因为所有上层都建在它上面；
  - **中层**（标准库、常用第三方库）：看文档 + 做小实验，用到哪查到哪；
  - **高层**（框架、AI 代理）：先用起来，但**保留回退手段**，并且知道它坏了会怎样。
- **动作**：对任何一层，问一句"我怎么知道它做对了"。答得出来，就可以信任到那个程度；答不出来，就降一层去查。

### 6.6 把"炸库级"权限交给 AI

- **症状**：允许它访问整个用户目录、允许它删文件、允许它装全局依赖、允许它 `sudo`。
- **为什么**：权限提示弹出来时，人倾向于点"允许"把事做完。
- **动作**：能限目录就限目录；动手前先 `git commit`；危险命令先找预演形式（第 08 讲）；不确定时要求它先给方案、不执行。

### 6.7 没有版本保护、冻结与回退的概念

- **症状**：改到一半发现还不如昨天，但没有"昨天"可以回去；或者交付物已经交给老师/客户，又随手改了，结果说不清哪个是最终版。
- **动作**：动手前提交（第 04 讲）；**已交付的东西视为冻结**，要改先复制一份再改；重要文件至少有两个位置。

### 6.8 写巨无霸单文件

- **症状**：一个 `.py` 文件两千行，改一个函数要上下翻十屏，复制粘贴的代码出现三次。
- **为什么**：一开始只是"先写在这"，然后就没有然后了。
- **动作**：先按"这件事由几步组成"拆函数（第 15 讲），再按"哪几件事属于同一类"拆文件（第 17 讲）。经验阈值：一个文件超过几百行，或者你要用滚动条找东西，就该拆了。

## 7. 工程素养的三条底线

后面每一讲都会回扣这三条。记住它们，比记住任何工具名都值钱。

1. **可重复**：换台机器、换个人，按你写下的步骤能跑出一样的结果。对应第 03 讲（环境）、第 26 讲（依赖声明）。
2. **可回退**：任何改动都能退回去。对应第 04 讲（git）。
3. **可验证**：你说"它对"，要能给出判据。对应第 08 讲（审查与验证）、第 24 讲（调试）、第 25 讲（测试）。

## 8. 这一讲留下的东西

- 工具按"解决什么问题"分类，不按厂商分类；遇到陌生工具先问四个问题。
- 判断"要不要现在学"的标准是：不用它会怎样、它改哪一层、出问题你能不能看到证据。
- 三类 AI 工具的风险随能力上升：聊天式 < 编辑器内联 < 命令行代理。
- 八类坑里最值得先治的两条：笔记必须有可执行的一步；动手前先提交。
- 工程素养的三条底线：可重复、可回退、可验证。

接下来的三讲把地图上的"AI 助手"和"写代码的地方"展开：第 06 讲大模型到底怎么工作、为什么会犯错；第 07 讲编辑器怎么装怎么配；第 08 讲它动完代码之后怎么审。

## 小结

- 工具学不完，目标从"学完"改成"建索引 + 会判断 + 能迁移"。
- 地图按问题分类：运行与依赖、写代码的地方、版本与协作、命令行与系统、查资料、模型与数据、笔记、AI 助手。
- 四个问题：解决什么问题、输入输出是什么、改哪一层、证据在哪。四问答不上来就先别装。
- 卡住时先查"症状 → 类别"表，比自我怀疑有效。
- pip / uv / conda 的分工：pip 通用、uv 快、conda 能管非 Python 依赖；同一项目不要混用 conda 与 venv。
- GitHub 看四样：README、最近提交、Issue 活跃度、许可证；Stack Overflow 看版本与日期，别只看票数。
- 八类坑：笔记手账化、怕不完整不敢动手、忘了工科判据、不会提问、不信任抽象层级、给 AI 过大权限、没有版本保护、巨无霸单文件。
- 三条底线：可重复、可回退、可验证。

## 作业

**Q1.** 下面三个症状，分别该先想到地图上的哪一类工具？各给出一个具体动作。

(a) 敲 `python` 提示"不是内部或外部命令"；
(b) 你不小心删掉了 `main.py` 的一半内容，而且没有备份；
(c) 你想知道某个第三方库的函数参数是什么意思。

**参考答案：** 三个症状分别对应下面三类工具与动作：

(a) 运行与依赖（具体是 `PATH`）。动作：回第 02 讲 5.5 节，先 `where.exe python` 确认它在不在 `PATH` 里，再决定重装还是手动加路径。

(b) 版本与协作。动作：如果项目进过 git（第 04 讲），`git status` 看改动、`git restore main.py` 恢复；如果没进过 git，这次事故本身就说明下一步该做什么——以后动手前先提交。文件管理器里的"以前的版本"或回收站是最后的补救。

(c) 查资料（官方文档优先）。动作：先查该库官方文档的函数签名，再在 REPL 里试一次（第 01 讲讲过的交互式解释器）；不要先搜二手博客。

**Q2.** 用四个问题分析一个你从没用过的工具（可以是同学提到的、招聘要求里的、或本讲地图上任意一个）。写出四问的答案，并给出一句结论："现在学 / 知道就好 / 先别碰"。

**参考答案：** 以 Docker 为例（你可以换成任何工具）：

- 解决什么：把程序连同它的运行环境一起打包，保证"在我机器上能跑"到哪都能跑。不用会怎样？你仍然可以用虚拟环境解决大部分问题，只是"换台机器"时更麻烦。
- 输入输出：输入一个配置文件（Dockerfile）和一条命令，输出一个可运行的镜像/容器。
- 改哪一层：改本机的容器运行时与磁盘，不直接改你的项目文件。
- 证据在哪：`docker ps` / `docker logs` / 构建时的报错。

结论：**知道就好**。本课程第 26 讲用 `pyproject.toml` + 虚拟环境已经能解决"环境可重复"，Docker 是下一步的工程化工具，现在学收益不大。

判分要点：四问答得具体（不是"很有用""很方便"），结论与四问一致。

**Q3.** 写一条"合格笔记"，内容是你在第 01–04 讲里遇到的任意一个卡点。要求包含：你当时的预期、实际发生了什么、一条可执行的验证命令、一句判据。

**参考答案：** 示例（关于"文件明明在，脚本却找不到"）：

- 预期：在项目根目录运行 `python show.py`，脚本里写 `Path("data/a.csv")` 应该能读到文件。
- 实际：报 `FileNotFoundError: [Errno 2] No such file or directory: 'data\\a.csv'`。
- 验证命令：`python -c "from pathlib import Path; print(Path.cwd())"`，看当前目录是不是项目根。
- 判据：打印出来的目录里，`data/a.csv` 这一层确实存在，才算找对了位置；否则先用 `cd` 回到正确目录。

判分要点：有可执行命令、有客观判据、写的是自己的卡点而不是抄来的概念。

**Q4.** 下面四个操作，哪些必须先提交（`git commit`）再做？说明理由。

(a) 让 AI 一次改五个文件；(b) 在 REPL 里算 `2 ** 10`；(c) 重命名项目里的 30 个文件；(d) 打开一个文件读一遍。

**参考答案：** (a) 必须先提交：改动范围大、不易人工恢复。(c) 必须先提交：批量改名一旦改错，靠记忆恢复不现实。(b) 不需要：REPL 不碰文件。(d) 不需要：只读操作。

判据可以概括成一句：**这个操作会不会不可逆地改变磁盘上的东西**。会，就先提交。

**Q5.** 一个 800 行的 `main.py` 里同时做了四件事：读配置、读 CSV、算统计、打印报告。给出一个拆分方案（不用真写代码），并说明先拆什么、后拆什么。

**参考答案：** 先拆函数、再拆文件，理由是函数拆分风险最小（同一个文件内移动代码，容易对照），文件拆分涉及 import（第 17 讲）才需要。

方案：先按四件事在 `main.py` 内部拆成四个函数：`load_config()`、`read_rows()`、`summarize(rows)`、`print_report(summary)`；主流程保留一个 `main()` 按顺序调用它们。等四个函数各自稳定、彼此不再互相引用内部变量后，再把它们移到 `config.py`、`data.py`、`report.py`，`main.py` 只留入口和调度。

判分要点：先拆职责再拆文件；能说出"为什么这个顺序"（拆分难度与依赖方向）。

**Q6.** 你在网上看到一句话："所有项目都该用 Docker，虚拟环境已经过时了。" 用本讲的分层信任方法，说说你会怎么处理这条信息。

**参考答案：** 先分层：这句话属于"高层工具主张"，不是底层事实。处理步骤：(1) 问它解决什么问题、不用会怎样——Docker 解决的是"环境整体打包与分发"，虚拟环境解决的是"依赖隔离"，两者不是替代关系；(2) 看它有没有给出适用条件（团队规模、部署方式、操作系统）；(3) 找反例：本课程第 03 讲实测过虚拟环境能隔离依赖，且成本只有几秒；(4) 结论：把它当作"某个场景下的建议"，而不是"必须遵守的规则"，等你真的遇到"换机器跑不起来"的痛点再引入。

判分要点：不因为来源权威就接受，也不因为陌生就拒绝；落到"适用条件 + 我能否验证"。
