## 0. 场景：三件"把动作当数据"的事

- 同一份成绩表，这次按分数排，下次按名字排，再下次按"分数降序、同分按名字"排——排序逻辑变了，数据没变；
- 想知道某个函数跑了多久，但不想在每个函数体里都塞两行计时代码；
- 一个 2 GB 的日志文件要逐行统计，不能整个读进内存。

三件事的共同点是：**需要把"做什么"当参数传出去**，而不是把"做什么"写死在函数里。这一讲就是这条线的完整形态。

下一节先把函数当值用：传给 `sorted` 的 `key`。

## 1. 函数是值

第 15 讲结尾提过：`f = add` 之后 `f` 和 `add` 指向同一个函数对象。既然函数是对象，它就能当参数传。

### 1.1 把函数传给 `sorted`

```text
  sorted(words)               = ['Banana', 'Cherry', 'apple']
  sorted(words, key=len)      = ['apple', 'Banana', 'Cherry']
  sorted(words, key=str.lower) = ['apple', 'Banana', 'Cherry']
```

三行说明三件事：

- 默认排序按字符编码比较，所以大写字母排在前面（`Banana`、`Cherry` 在 `apple` 前）；
- `key=len` 让排序按"长度"比较，于是最短的在最前；
- `key=str.lower` 先把每个词转小写再比较，于是忽略大小写。

`key` 的语义是：**对每个元素先调用一次这个函数，用返回值去比较**。原数据不会被改，也不会被替换成返回值。

### 1.2 多级排序：key 返回元组

```text
  按分数降序、同分按名字升序 = [('bob', 95), ('alice', 90), ('carol', 90)]
```

写法是：

```python
sorted(rows, key=lambda r: (-r[1], r[0]))
```

读法：每个元素是一个 `(名字, 分数)` 元组；key 返回 `(负分数, 名字)`。

- 负分数实现"降序"——因为排序总是升序，把数值取负就反过来了；
- 元组比较是**先比第一项，相同再比第二项**（第 12 讲），所以同分的 alice 和 carol 按名字排。

这是实际工作里最常用的排序技巧，比写自定义比较函数简单得多。

### 1.3 `key` 的两个边界

- **key 会被调用多次吗？** 每个元素只调用一次，结果被缓存用于比较；所以 key 里可以放稍贵的计算。
- **key 能改原元素吗？** 能，但不要——排序过程中修改被排序的数据，行为不可预期。key 应该是"纯函数"：给同样的输入返回同样的输出，不产生副作用。

`key` 会用了，下一节看 `lambda` 的边界。

## 2. `lambda`：只能写一个表达式

### 2.1 实测

```text
  lambda x: x * 2   -> double(5) = 10
  double.__name__ = '<lambda>'
  lambda 里写赋值 -> SyntaxError: cannot assign to lambda
```

`lambda` 是"没有名字的短函数"，语法是 `lambda 参数: 表达式`。它有两个硬限制：

- 函数体只能是**一个表达式**，不能写语句（赋值、`print`、`return`、`for` 都不行）；
- 名字固定是 `'<lambda>'`，调试时看不出是哪个，报错栈里也难认。

### 2.2 什么时候用、什么时候别用

| 场景 | 建议 | 理由 |
|---|---|---|
| 传给 `key=` 的一行逻辑 | 用 `lambda` | 就地写完，不必起名 |
| 逻辑超过一行 | 用 `def` | `lambda` 写不了 |
| 需要在报错栈里认出它 | 用 `def` | `'<lambda>'` 无法定位 |
| 同一个逻辑用两次以上 | 用 `def` | 避免重复，也能被测试 |
| 想给它写文档字符串 | 用 `def` | `lambda` 没有 docstring |

一句话：**`lambda` 是"临时用完就扔"，不是"函数应该短"的证明。**

边界清楚了，下一节看 `map` / `filter` / `reduce` 的定位。

## 3. `map` / `filter` / `reduce`

### 3.1 `map` 与 `filter` 返回迭代器

```text
  map 第一次遍历: [10, 20, 30, 40]
  map 第二次遍历: []
  filter 结果: [2, 4]
  用推导式做同一件事: [10, 20, 30, 40]
```

`map(函数, 可迭代对象)` 对每个元素应用函数，`filter(函数, 可迭代对象)` 保留函数返回真的元素。两者返回的都是**迭代器**，不是列表——所以第二次遍历拿到空（第 14 讲的迭代协议：迭代器记着"走到哪了"，走完就没了）。

### 3.2 日常优先用推导式

```text
  用推导式做同一件事: [10, 20, 30, 40]
```

列表推导式 `[x * 10 for x in nums]` 更直接，而且结果是列表、可以反复用。`map` 的优势只在"函数已经存在、不想写 lambda"时：

```python
list(map(str, [1, 2, 3]))     # ['1', '2', '3']，比 [str(x) for x in ...] 略短
```

`filter` 基本可以直接换成 `[x for x in xs if 条件]`。

### 3.3 `reduce`：知道存在

`functools.reduce(函数, 序列)` 把序列"折叠"成一个值，例如累加、连乘。它可读性差（尤其带初始值时），日常用 `sum`、`max`、循环都更清楚。知道它存在即可，见到别人的代码能认出来。

迭代器用法清楚了，下一节看闭包：捕获的是变量还是值。

## 4. 闭包：捕获的是变量，不是值

### 4.1 一个能记住状态的函数

```python
def make_counter():
    count = 0
    def bump():
        nonlocal count
        count += 1
        return count
    return bump
```

```text
  第一次调用 1，第二次 2，第三次 3
```

`bump` 里用了外层的 `count`，这叫**闭包**：内层函数记住了外层函数的变量。`nonlocal` 声明"我要改的是外层那个 `count`"，不写它就会被当成局部变量（第 15 讲的规则）。

这给了一个不用类就能保存状态的方案，后面第 20 讲会看到用类做同样的事更清楚。

### 4.2 循环里造函数：晚期绑定的坑

```text
  循环里造三个 lambda（buggy）= [2, 2, 2]
  用默认参数固定住 i      = [0, 1, 2]
```

```python
funcs = []
for i in range(3):
    funcs.append(lambda: i)     # 三个 lambda 都返回 2
```

原因：闭包捕获的是**变量 `i` 本身**，不是"那一轮的值"。循环结束后 `i` 是 2，三个函数去读同一个 `i`，于是都返回 2。

修法是用默认参数把当时的值"存下来"：

```python
funcs.append(lambda i=i: i)     # 默认值在创建时求值（第 15 讲）
```

这条和第 15 讲的"默认参数只在定义时求值一次"是同一件事的两面：一次是坑，一次是解药。

闭包讲透，下一节看装饰器：它到底替换了什么。

## 5. 装饰器：把一个函数换成另一个函数

### 5.1 手工理解

```python
def plain():
    return "原函数"

def loud(func):
    def wrapper():
        return "【" + func() + "】"
    return wrapper

wrapped = loud(plain)
```

```text
  loud(plain)() = 【原函数】
  原函数还在吗 = 原函数
```

`loud` 收一个函数、返回一个新函数 `wrapper`；`wrapper` 里调用原来的 `func` 并加上装饰。`plain` 本身没变，`wrapped` 是一个新函数。

### 5.2 `@` 只是语法糖

```python
@loud
def plain():
    ...
```

等价于 `plain = loud(plain)`。**名字 `plain` 现在指向 `wrapper`**，原来的函数对象只被 `wrapper` 的闭包引用着。这就是"装饰器替换了什么"的准确答案：它替换了**名字的绑定**。

### 5.3 `functools.wraps`：保住函数身份

```text
  没加 wraps 时 __name__ = 'wrapper'
  装饰后 __name__ = 'slow_sum'（functools.wraps 保住了原名）
```

不加 `wraps`，装饰后的函数名变成 `'wrapper'`——报错栈、日志、调试器里看到的都是 `wrapper`，你根本不知道是哪个函数出的问题。`@functools.wraps(func)` 把原名、文档字符串等信息复制到 `wrapper` 上。

### 5.4 被装饰的函数有参数怎么办

用第 15 讲的 `*args` / `**kwargs` 原样转交：

```python
def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"[{func.__name__}] {time.perf_counter() - t0:.6f} 秒")
        return result
    return wrapper
```

```text
    [slow_sum] 耗时 0.013567 秒
  @timer 装饰后的 slow_sum(1e6) = 499999500000
```

实测里那行耗时是 `sum(range(1_000_000))` 的实际用时。注意 `wrapper` 必须 `return result`——忘了返回，被装饰的函数就会变成"算完但返回 `None`"（第 15 讲的"不写 return 就返回 None"在这里会变成静默 bug）。

### 5.5 什么时候别用装饰器

- **叠太多层**：一个函数被三四个装饰器套着，报错栈会很难读，执行顺序也容易搞混。超过两层就该考虑合并或改写。
- **藏在装饰器里的副作用**：比如"每次调用都写数据库"，这应该是函数体里明写的事，不该藏在装饰器里。
- **为了少写一行**：装饰器适合"横切关注点"（计时、日志、重试、权限检查），不适合"这段逻辑我想复用一下"——那应该拆普通函数。

装饰器会写了，下一节看递归：什么时候干净、什么时候爆炸。

## 6. 递归

### 6.1 终止条件是命门

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)
```

```text
  factorial(5) = 120
```

递归函数必须满足两条：**有一个不需要再递归的终止情况**，并且**每次递归都在向它靠近**（这里是 `n - 1`）。少任何一条就是无限递归。

### 6.2 重复子问题会指数爆炸

```text
  fib_naive(20) = 6765  耗时 0.0005 秒
  fib_naive(25) = 75025  耗时 0.0103 秒
  fib_naive(30) = 832040  耗时 0.0717 秒
```

每增加 5，耗时涨约 5–20 倍（不同机器与负载下比例会浮动）。原因是 `fib(n-1)` 和 `fib(n-2)` 会重复计算大量相同的子问题：`fib(30)` 里 `fib(20)` 被算了上千次。

这不是递归本身慢，是**没有记住算过的结果**。

### 6.3 `lru_cache`：一行加缓存

```text
  fib_memo(30) = 832040（带 lru_cache）
```

```python
@functools.lru_cache(maxsize=None)
def fib_memo(n):
    ...
```

`lru_cache` 把"参数 → 返回值"存起来，同一个参数第二次调用直接返回缓存。`fib(30)` 的耗时从可见的毫秒级降到几乎测不出。

代价：它会占内存，且要求参数可哈希（第 12 讲）；`maxsize` 可以限制缓存条数。

### 6.4 递归深度有上限

```text
  递归上限 sys.getrecursionlimit() = 1000
  无限递归 -> RecursionError: maximum recursion depth exceeded
```

Python 默认允许约 1000 层。超过就抛 `RecursionError`——这是保护，不是 bug：每层递归都占栈空间，不设限会直接崩掉解释器。

所以处理"几千层深"的问题（深目录遍历、长链表）时，递归不合适，该换成迭代或显式栈。

### 6.5 递归与迭代怎么选

| 场景 | 推荐 | 理由 |
|---|---|---|
| 树/目录结构遍历 | 递归 | 结构本身就是递归的，写起来最直 |
| 简单计数、累加 | 迭代（`for`） | 没有栈开销，也不怕深 |
| 能拆成"同种子问题"且规模不大 | 递归 | 代码短、易读 |
| 可能很深（> 几百层） | 迭代 | 会撞 `RecursionError` |
| 有大量重复子问题 | 递归 + 缓存，或迭代 + 表 | 否则指数爆炸 |

判据一句话：**递归写"结构"，迭代写"过程"。**

递归的风险清楚了，下一节看生成器：省内存的代价是什么。

## 7. 生成器

### 7.1 `yield`：产出一个，暂停一下

```python
def countdown(n):
    while n > 0:
        yield n
        n -= 1
```

```text
  第一次遍历: [3, 2, 1]
  第二次遍历: []
```

函数体里出现 `yield`，这个函数就变成**生成器函数**：调用它不执行函数体，而是返回一个生成器；每次 `next()` 才往下跑到下一个 `yield`，然后暂停。

第 14 讲说过"生成器只能遍历一次"——实测第二遍是空列表，因为迭代器已经走完了。

### 7.2 省内存：一个数量级的差别

```text
    list  = 800984 字节（元素另算）
    gen   = 192 字节
```

10 万个元素的列表，光结构体就约 800 KB（这还没算每个整数对象本身）；同样逻辑的生成器只有 192 字节——因为它**不存元素**，只存"我算到哪了"。

这不是微优化。处理 2 GB 日志时，列表方案会直接吃满内存；生成器方案只占常数内存，边读边处理。

### 7.3 生成器表达式：把推导式的方括号换成圆括号

```python
total = sum(x * x for x in range(1_000_000))
```

`(x * x for x in ...)` 是生成器表达式，不建列表，直接喂给 `sum`。这种"流水线"写法在数据处理里很常见：一步产出、一步消费，中间不落地。

### 7.4 列表还是生成器

| 你的需求 | 用哪个 | 理由 |
|---|---|---|
| 要用两遍、要索引、要看长度 | 列表 | 生成器只能一次、没有 `len` |
| 只要遍历一遍就完事 | 生成器 | 省内存 |
| 数据量很小（几十个） | 列表 | 差别可忽略，列表更灵活 |
| 数据来自大文件/网络流 | 生成器 | 不能一次读进内存（第 19 讲） |

生成器的代价说清了，下一节把本讲收起来。

## 8. 这一讲留下的东西

- 函数是值：能当参数传，`sorted(key=...)` 就是最常用的场合；多级排序用元组 key + 负号。
- `lambda` 只写一个表达式；超过一行、要名字、要文档字符串，一律 `def`。
- `map` / `filter` 返回迭代器，只能遍历一次；日常优先推导式。
- 闭包捕获变量不捕获值；循环里造函数用默认参数固定当轮的值。
- 装饰器替换的是名字绑定；`functools.wraps` 保住 `__name__`；`wrapper` 记得 `return`。
- 递归要有终止条件，会撞 1000 层的上限；重复子问题用 `lru_cache`。
- 生成器省内存、只能遍历一次；大文件处理的标准做法。

下一讲换个层面：把函数从"一个文件里的东西"变成"可以被别的文件引用的模块"，你会看到 `import` 到底做了什么、`if __name__ == "__main__"` 为什么必须写、以及标准库里到底有什么。

## 本讲小结

- `sorted(words)` 得 `['Banana','Cherry','apple']`；`key=len` 与 `key=str.lower` 都得 `['apple','Banana','Cherry']`。
- 多级排序 `key=lambda r: (-r[1], r[0])` 得 `[('bob',95),('alice',90),('carol',90)]`。
- `lambda` 的名字固定是 `'<lambda>'`；里面写赋值抛 `SyntaxError: cannot assign to lambda`。
- `map` 第一次 `[10,20,30,40]`、第二次 `[]`；`filter` 得 `[2,4]`。
- 闭包计数器 1/2/3；循环里造 lambda 得 `[2,2,2]`，用 `i=i` 得 `[0,1,2]`。
- 装饰器：`loud(plain)()` 得 `【原函数】`；不加 `wraps` 时 `__name__` 是 `'wrapper'`，加了才是 `'slow_sum'`。
- 递归：`fib_naive` 三个规模 0.0005 / 0.0103 / 0.0717 秒；`lru_cache` 后 30 几乎瞬时；上限 1000 层，超了抛 `RecursionError: maximum recursion depth exceeded`。
- 生成器：第二遍遍历为空；10 万元素 list 800984 字节 vs gen 192 字节。

## 作业

**Q1.** 有一份记录 `[("alice", 90, 20), ("bob", 90, 18), ("carol", 85, 25)]`，格式是 `(名字, 分数, 年龄)`。写出：按分数降序、同分按年龄升序、再同则按名字升序的排序代码。

**参考答案：** 三个排序条件放进同一个元组：

```python
rows = [("alice", 90, 20), ("bob", 90, 18), ("carol", 85, 25)]
result = sorted(rows, key=lambda r: (-r[1], r[2], r[0]))
print(result)   # [('bob', 90, 18), ('alice', 90, 20), ('carol', 85, 25)]
```

关键点：排序只支持升序，所以"降序"用负号；多个排序条件放进元组，按从左到右的优先级比较；元组里出现字符串也没问题（字符串可比大小），但同一位置上类型必须一致。

**Q2.** 下面代码输出的三个函数都返回 2，为什么？给出两种修法。

```python
funcs = []
for i in range(3):
    funcs.append(lambda: i)
print([f() for f in funcs])
```

**参考答案：** 因为闭包捕获的是**变量 `i` 本身**，不是每一轮的值。循环结束时 `i` 是 2，三个 lambda 都去读同一个 `i`，所以都返回 2。

修法一：默认参数固定当轮的值。

```python
funcs.append(lambda i=i: i)      # 默认值在创建时求值
```

修法二：写一个工厂函数，把 `i` 变成那个函数作用域里的局部变量。

```python
def make(i):
    return lambda: i

funcs = [make(i) for i in range(3)]
```

两种都能得 `[0, 1, 2]`；第二种在需要传多个参数时更清楚。

**Q3.** 写一个装饰器 `trace`，让被装饰的函数每次调用前打印它的名字与参数，调用后打印返回值。

**参考答案：** 两层 `@functools.wraps` + `*args/**kwargs`：

```python
import functools

def trace(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}，args={args} kwargs={kwargs}")
        result = func(*args, **kwargs)
        print(f"{func.__name__} 返回 {result!r}")
        return result
    return wrapper

@trace
def add(a, b):
    return a + b

add(1, 2)
```

三个要点：用 `*args, **kwargs` 原样转交参数（第 15 讲）；`functools.wraps` 保住原名；`return result` 不能漏，否则被装饰的函数就变成返回 `None`。

**Q4.** `fib_naive(30)` 要 0.07 秒左右，而 `fib_naive(35)` 会明显更久。解释原因，并说出两种改进方式。

**参考答案：** 朴素递归的调用次数随 n 指数增长：`fib(n)` 会重复计算 `fib(n-1)`、`fib(n-2)` 的整棵子树，其中大量子问题被反复求解（`fib(30)` 里 `fib(20)` 被算了上千次）。所以每加 5，耗时涨几倍到十几倍。

两种改进：

1. 加缓存 `@functools.lru_cache(maxsize=None)`，把"参数 → 结果"记住，同一参数只算一次；
2. 改成迭代：从 `fib(0)`、`fib(1)` 往上推，两个变量滚动，时间与空间都是线性的。

改进后 `fib(35)` 也是瞬间完成。

**Q5.** 一个 2 GB 的日志文件要统计每行长度之和。用"读成列表再处理"和"生成器逐行处理"各有什么后果？

**参考答案：** 读成列表：`lines = f.readlines()` 会把 2 GB 内容连同每行对象的开销一起装进内存，多半直接 `MemoryError`；即便内存够，也会让整台机器变慢。

用生成器：文件对象本身就是迭代器，`for line in f:` 每次只读一行进内存，占用量基本恒定；`sum(len(line) for line in f)` 就是一行代码。代价是只能遍历一次（本讲实测：第二次为空），如果要读两遍，就得重新打开文件。

这正是第 19 讲"大文件逐行处理"的依据。

**Q6.** 判断对错并说明理由：
(a) `lambda` 里可以写 `print`；(b) 装饰器会修改原函数的代码；(c) 生成器可以用 `len()` 求长度；(d) `map` 的返回值可以直接遍历两次。

**参考答案：** 四条逐一看，其中 (a) 最容易判错：

- (a) **对，但要把边界说清**。`lambda x: print(x)` 是合法的，因为 `print(x)` 是函数调用、属于表达式；不能写的是赋值、`return`、`for` 这类**语句**。容易记错的是"`lambda` 只能算出一个值、不能有副作用"——`print` 确实是副作用，但它仍然是表达式，所以能写。实际代码里不建议这么用：有副作用的逻辑写成 `def` 更好读。
- (b) 错。装饰器不改原函数一行代码，它返回一个新函数并让你用原来的名字指向它（`plain = loud(plain)`）。原函数对象还在，只是名字被替换了。
- (c) 错。生成器没有 `len()`，它不知道总长度（边算边产出）；要长度只能先 `list(...)`，那就失去省内存的意义了。
- (d) 错。`map` 返回迭代器，第一次遍历后就用完了，第二次得到空（本讲实测）。
