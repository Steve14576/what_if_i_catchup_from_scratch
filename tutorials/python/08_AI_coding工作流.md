## 0. 这一讲只处理"它动完代码之后"

第 06 讲说了这类工具怎么生成、上下文是什么；第 07 讲说了你在哪儿遇到它（聊天窗口、编辑器内联、命令行代理）。这一讲不重复那些，只回答一件事：**它动过你的文件之后，你怎么管。**

第 04 讲刚建立的 git 能力，正好是这套管理的地基：**任何改动都可以被看见（`diff`）、被拒绝（`restore`）、被隔离（分支）**。有了这层，AI 才从"风险"变成"加速器"。

三个场景先摆在这里，全部由本讲脚本 `scripts/lec08-01_demo_verify.py` 实跑得到，你可以自己复现：

1. 它说"这条规则已经忽略虚拟环境了"——实际没忽略。
2. 它说"只改了一行"——实际改了两个文件、三处。
3. 它让你"清理一下没用的文件"——这条命令会删掉什么，你最好先看一眼。

下一节先把三类失败列出来，后面所有方法都是针对它们。

## 1. 三类典型失败

不是"偶尔抽风"，而是结构性的，会反复出现：

| 失败类型 | 表现 | 为什么会发生 | 怎么防 |
|---|---|---|---|
| 编造 | 给出不存在的函数名、参数、配置项 | 它按"看起来像"来生成，不会去查证 | 跑一遍；查官方文档；用 `--help` 看参数是否存在 |
| 只覆盖例子 | 你举的例子过了，换个输入就错 | 它优化的是"符合你的描述"，不是"覆盖所有情况" | 自己造边界输入（空、0、负数、超大） |
| 越界修改 | 顺手重排格式、删注释、改无关文件 | 它认为"让代码更好"是分内事 | 先 `git diff --stat` 看规模，再逐处看 diff |

这三类里，**第三类最容易造成真实损失**，因为它往往伴随"看起来更整洁"的改动，你一旦接受，别人（或三个月后的你）就再也不知道原来那行注释为什么存在。

命令行代理（第 07 讲）会把第三类放大：它有权限一次改十个文件、跑命令、装包。所以对它要额外设边界，见第 6 节。

三类失败清楚了，下一节说上下文：它看不见什么、你要补什么。

## 2. 上下文：它看不见的东西，你得说

一句"帮我改改这个脚本"，它能给出东西，但基本是猜的。有效的请求包含四件事：

1. **目标**：要达成什么可观察的结果（"读 `scores.csv`，输出每个班的平均分"）。
2. **现状**：现在是什么样（贴相关代码、贴完整报错、说明版本）。
3. **约束**：不能动什么（"不要改函数签名""只用标准库""不要引入新依赖"）。
4. **验收**：怎么算完成（"对这三行输入，输出应该是这两个数"）。

对照一下：

| 模糊请求 | 四要素请求 |
|---|---|
| "帮我看看这段代码为什么报错" | "运行 `python main.py` 报 `FileNotFoundError: 'scores.csv'`。文件其实在 `data/` 下，程序从项目根目录运行。请把读取路径改成相对项目根，不要硬编码绝对路径；改完我用 `python main.py` 在项目根目录验证。" |
| "优化一下这个函数" | "`total()` 现在对空列表返回 0。我要它遇到空列表时抛出 `ValueError`，其他行为不变。验证：空列表抛错；`[1,2]` 返回 3。" |

两条经验：

- **一次只改一件事**。让它同时"修 bug + 重命名 + 换风格"，你审不动，出问题也定位不了。
- **贴原文，不要转述**。报错要从第一行贴到最后一行，代码要贴完整片段（含函数定义那一行），不要用"就是那个循环"来代替。

四要素讲完，下一节开始核验：先看它说的"已经忽略了"是真是假。

## 3. 核验一：它说"已经忽略了"，真的忽略了吗

场景：项目里有 `.venv/`（虚拟环境）、`logs/`、`data.csv`。它给你一份 `.gitignore`：

```text
venv/
*.log
```

并说"已经忽略了虚拟环境和日志"。

先看现状：

```text
$ git status --short
  ?? .gitignore
  ?? .venv/
  ?? data.csv
```

`.venv/` 仍然躺在未跟踪列表里——如果真忽略了，它不该出现。再看逐条判据：

```text
$ git check-ignore -v .venv/lib/x.py
  (无输出)                                   ← 退出码 1

$ git check-ignore -v venv/bin/y.py
  .gitignore:1:venv/	venv/bin/y.py          ← 退出码 0

$ git check-ignore -v logs/run.log
  .gitignore:2:*.log	logs/run.log           ← 退出码 0
```

结论很清楚：它写的是 `venv/`，而项目的目录叫 `.venv`。**它忽略了一个不存在的目录**，同时对真实存在的那个毫无作用。

改成正确的两行之后：

```text
$ git status --short
  ?? .gitignore
  ?? data.csv

$ git check-ignore -v .venv/lib/x.py
  .gitignore:1:.venv/	.venv/lib/x.py
```

这里最值得学的不是"`.venv` 前面有点"，而是**验证方式**：不去问它"你确定吗"（它会说确定），而是找一个能独立回答"是/否"的外部判据——`check-ignore` 的退出码。

### 3.1 验证的本质：找一个会失败的外部判据

| 它的断言 | 可用判据 | 判据给出的形式 |
|---|---|---|
| "这条规则已经忽略 X 了" | `git check-ignore -v X` | 退出码 0 / 1，命中哪条规则 |
| "这个命令能这么用" | 直接跑；或 `命令 --help` | 真实报错 / 参数列表 |
| "改动很小" | `git diff --stat` | 文件数、增删行数 |
| "处理了空列表" | 自己造一个空列表跑一次 | 退出码、输出 |
| "这个版本支持某参数" | 查该版本的官方文档；或看 `--version` 后试跑 | 文档条目 / 报错 |

判据的共同点：**它不依赖对方的说法**。凡是要靠"再问它一遍"来确认的，都不算验证。

忽略规则核完，下一节核"只改了一行"。

## 4. 核验二：它说"只改了一行"

同一次改动，它说"只在 `a.py` 里改了一行"。核对：

```text
$ git status --short
   M a.py
   M b.py
  ?? util.py

$ git diff --stat
   a.py | 3 ++-
   b.py | 2 +-
   2 files changed, 3 insertions(+), 2 deletions(-)
```

三件事当场暴露：改了**两个**文件、新增了一个**没被提到**的 `util.py`、总增删是 3 加 2 减。这和"只改了一行"完全对不上。

再看逐行 diff：

```text
$ git diff
  diff --git a/a.py b/a.py
  @@ -1,2 +1,3 @@
   def area(r):
  -    return 3.14 * r * r
  +    s = 3.14159 * r * r
  +    return round(s, 2)
  diff --git a/b.py b/b.py
  @@ -1,2 +1,2 @@
   def perimeter(r):
  -    return 2 * 3.14 * r
  +    return 2 * 3.14159 * r
```

（这段代码里 `def`、`return`、`round` 的语法你还没学，第 15 讲才讲函数。这里只需要看两件事：哪几行被划掉、哪几行被加上。）

### 4.1 读 diff，看三样

| 看什么 | 命令 | 判断标准 |
|---|---|---|
| 规模 | `git diff --stat` | 文件数与增删行数，是否与你的要求相称 |
| 内容 | `git diff` | 每一处 `-` / `+` 是否都是你要的 |
| 越界 | `git diff` 里与任务无关的段落 | 有没有顺手重排、删注释、改依赖、加新文件 |

发现越界之后的处置只有三种，别犹豫：

- **全部接受**：符合要求，`git add` + `git commit`。
- **部分接受**：只 `add` 你要的那几个文件或那几段，剩下的 `git restore` 掉。这也是第 04 讲暂存区存在的意义。
- **全部拒绝**：`git restore` 一条命令回到干净状态（实测见第 5 节）。

改动规模核完，下一节核危险操作：先看它要删什么。

## 5. 核验三：危险操作先看它要做什么

它会说"清理一下没用的文件"，然后给你一条删除命令。这类请求的正确处理是：**先找这条命令的"预演"形式**。

`git clean` 会删掉未跟踪的文件，加 `-n` 就只报告不动手（`-d` 表示连同目录一起看）：

```text
$ git clean -nd
  Would remove util.py

$ git clean -ndX
  Would remove .venv/
  Would remove logs/
  Would remove venv/
```

两种预演的区别很关键：`-nd` 看的是**未跟踪**的文件（这里只有 `util.py`），`-ndX` 看的是**被忽略**的文件（`.venv/`、`venv/`、`logs/`）。**两条都是 dry-run，仓库此刻一个文件都没被删。**

如果它给的是一条没有预演形式的命令（例如直接覆盖文件、批量改名、装全局依赖），那你至少要先做一件事：**把当前状态提交一次**。有提交，最坏情况也能回来；没有提交，你就只能靠记忆。

| 危险动作 | 先做什么 | 你能得到什么 |
|---|---|---|
| 删除文件 / 目录 | 找 dry-run（如 `git clean -nd`），或先 `git status` 看清楚 | 一份"将被删"的清单 |
| 覆盖已有文件 | 先提交；或先复制一份 | 可回退点 |
| 批量改名 / 移动 | 先在副本上跑；或先提交 | 可回退点 |
| 装 / 升级依赖 | 看清单变化（`pip list` 前后对比），记下旧版本 | 可还原的版本号 |
| 改配置（`PATH`、`.gitignore`、`pyproject.toml`） | 先看 diff；先提交 | 能看到改了什么 |

危险操作会预演了，下一节给代理式工具划权限。

## 6. 给代理式工具划权限

命令行代理与聊天式工具的区别只有一条：**它能动手**。能动手就意味着"权限"成为一个必须自己决定的事，不能交给它决定。

按"它要动什么"分三档：

| 动作 | 可以放开 | 需要你盯着 | 不要给 |
|---|---|---|---|
| 读文件 | 项目目录内 | 项目外的个人目录 | 密钥文件、浏览器配置、别的项目 |
| 写文件 | 项目目录内、可回退（已提交） | 项目配置、依赖清单 | 系统目录、用户主目录根下 |
| 执行命令 | 只读命令、测试、格式化 | 装包、批量改名、`git` 写操作 | 递归删除、改系统设置、`sudo` / 管理员权限、任何带凭据的命令 |

再加三条纪律：

- **先提交，再让它动手**。没有干净基线，就没有"后悔"这个选项。
- **能限目录就限目录**。让它只在一个项目文件夹里工作，而不是"整台机器"。
- **不确定就让它先给方案、别执行**。"列出你打算改哪些文件、为什么"这一步几乎不要成本，却能省掉一次事故。

权限划完，下一节把动作固定成五步。

## 7. 与 git 的固定配合：五步

这套流程把上面的判断固定成动作，写代码时每天都会重复：

```text
1. 先提交            → 有一个干净的基线，随时能回来
2. 让它改 / 让它写    → 一次一件事，四要素说清楚
3. git status + diff  → 看规模、看内容、看越界
4. 验证              → 跑一遍 / 造边界输入 / 用 check-ignore 之类的判据
5. 通过就提交，不通过就 restore
```

第 5 步的实测：

```text
$ git restore a.py b.py
$ git status --short
  ?? util.py
```

一条命令回到上次提交，未跟踪的 `util.py` 仍然在（它本来就不属于任何提交）。**回退是分得清的**：改过的文件回到干净状态，新增的文件不自动消失——所以"清理"这一步仍然需要你自己判断。

为什么强调"先提交"？因为没有它，第 5 步就做不了。你会变成"要么接受，要么手工恢复"，而手工恢复是最容易出错的一步。

五步定了，下一节说清什么不能交给它。

## 8. 什么不能交给它

三类，没有例外：

- **凭据与隐私**：密钥、令牌、密码、身份证号、成绩单、他人的个人信息、未公开的实验数据。一旦贴出去，你就失去了对它的控制，删除对话也不等于删除记录。
- **唯一的副本**：还没备份、没提交的重要文件。让 AI 处理之前先复制或提交，理由和第 5 节一样。
- **有规定的场合**：课程作业、考试、论文、公司代码，是否允许使用、允许到什么程度，有明确规定。这条不是技术问题，但后果比技术问题严重。

一条工程上的补充：**不确定某个文件能不能贴，就先假定不能**。需要它理解代码时，可以只贴相关的那一个函数，而不是整个项目。

边界清楚了，下一节说什么时候根本不该用它。

## 9. 什么时候不该用它

四种情形，用它反而更慢或更有害：

- **你完全看不懂它给出的结果**。看不懂就无法验收，等于把签字权交出去了。学习阶段尤其危险：你会失去"卡住—查资料—想通"那一段，而那一段才是真正长本事的部分。
- **没有可观察的验收方式**。如果你的任务既没有输出、也没有测试、也没法手动检查，那它的"应该没问题"就和没有一样。
- **只需要三五行代码**。写一段清楚的需求描述，往往比手写那三五行更费时间。
- **它要动的是你不能验证的领域**（比如"优化这段不熟悉的数据库查询"）。这时先让它在旁边解释，而不是直接改。

该不该用判断完，下一节把本讲收起来。

## 10. 这一讲留下的东西

- 三类结构性失败：编造、只覆盖例子、越界修改；代理式工具会把"越界"放大。
- 请求四要素：目标、现状、约束、验收；一次只改一件事；贴原文不转述。
- 验证 = 找一个不依赖它说法的外部判据（退出码、`diff --stat`、`--help`、自己造的边界输入）。
- 危险操作先找预演形式；找不到就先提交。
- 代理式工具的权限按"读 / 写 / 执行"分档，能限目录就限目录，不确定就先要方案。
- 固定五步：先提交 → 让它改 → 看 status/diff → 验证 → 提交或 restore。

下一讲开始写 Python 本身。那时你会带着这些东西进场：知道程序怎么被执行（01）、知道文件在哪（02）、知道环境怎么搭（03）、改坏了能退回（04）、知道工具地图该往哪找（05）、知道大模型怎么工作（06）、知道在哪个编辑器里写（07）、知道它动完代码后怎么审（08）。

## 本讲小结

- 这类工具根据上下文预测代码，**没有运行过你的程序**；它的确定语气不构成证据。
- 三类典型失败：编造不存在的 API 或参数；只对你举的例子成立；越界修改无关文件。
- 有效请求的四要素是目标、现状、约束、验收；一次只改一件事，贴完整报错与相关代码原文。
- 验证的关键是外部判据：`git check-ignore` 的退出码、`git diff --stat` 的规模、`--help` 的参数表、自己造的边界输入。
- 审查改动的顺序：`status`（改了哪些文件）→ `diff --stat`（规模）→ `diff`（逐处内容与越界）。
- 危险命令先找 dry-run（如 `git clean -nd` / `-ndX`）；没有预演形式的，先提交再动。
- 代理式工具按读 / 写 / 执行三档给权限，能限目录就限目录。
- 五步流程：先提交 → 让它改 → 看 diff → 验证 → 提交或 `restore` 回退。
- 不能交出去的三类：凭据与隐私、唯一副本、有明确规定的场合。

**Q1.** 把下面这句请求补成四要素版本："帮我把这个读文件的函数改一下，它老报错。"

**参考答案：** 四要素分别补上（具体内容按你的实际情况填）：

- **目标**：让函数能正确读到 `data/scores.csv` 并返回行数。
- **现状**：现在运行报 `FileNotFoundError: [Errno 2] No such file or directory: 'scores.csv'`；文件实际在 `data/` 目录下；我在项目根目录运行 `python main.py`。
- **约束**：只改路径的构造方式，不要改函数名与返回值类型，不要引入第三方库。
- **验收**：改完在项目根目录运行 `python main.py` 应该输出 `120`（行数）；如果文件不存在，应该给出明确的提示而不是直接崩。

一条完整示例："函数 `load_rows()` 运行时报 `FileNotFoundError: 'scores.csv'`。文件实际在 `data/scores.csv`，我从项目根目录运行 `python main.py`。请只修正路径构造，不要改函数签名、不引入第三方库。验收：从项目根运行输出 `120`；文件缺失时打印提示并以非 0 退出码结束。"

**Q2.** 它说"我已经测试过了，可以正常运行"。这句话能作为验收吗？为什么？

**参考答案：** 不能。它没有运行你的程序的条件（看不到你的文件、你的环境、你的数据），"测试过了"是生成出来的说法，不是观测结果。

能作为验收的，是**你自己**跑出来的结果：`python main.py` 的退出码、输出内容、报错的原文；或者你写的测试跑出来的通过/失败。即使它给出了测试代码，你也要自己跑一遍——测试本身也可能是错的。

**Q3.** 你让它改一个小功能，它回答"已完成"。你打开终端，应该依次敲哪三条命令？各自看什么？

**参考答案：** 按下面三条顺序来：

```powershell
git status --short      # 改了哪些文件、有没有未提到的新文件
git diff --stat         # 改动规模：几个文件、增删多少行
git diff                # 逐处内容：每一处 -/+ 是否都是你要的，有没有越界
```

三条的顺序不能反：先看范围，再看规模，最后看细节。如果 `status` 里出现你没预期的文件，直接停下来问清楚，不要先看 diff。

**Q4.** 它说"这个函数处理空列表不会报错"。设计一个验证，并说明"通过"和"不通过"分别长什么样。

**参考答案：** 造一个空列表，直接调用并观察：

```powershell
python -c "from main import total; print(total([]))"
```

- 通过：命令正常结束，退出码 `0`，输出是一个合理的值（例如 `0`）。
- 不通过：打印 `Traceback ...`，退出码非 `0`（例如 `IndexError` 或 `ValueError`）。

还可以补两个边界：只有一个元素的列表、全部为 0 的列表。**只测空列表**这一步就已经比"它说没问题"强得多，因为退出码是客观的。

**Q5.** 一个命令行代理请求"允许我在你的机器上执行命令来完成这个任务"。你会怎么设边界？至少说三条。

**参考答案：** (1) 把工作目录限制在这个项目里，不让它碰用户主目录与其他项目；(2) 先提交一次，保证有干净基线可以回退；(3) 明确禁止的动作：递归删除、改系统设置、安装全局依赖、任何带密钥或令牌的命令；(4) 要求它在执行破坏性操作前先给出"将要执行什么、影响哪些文件"的清单，你确认后再放行。

一条补充：如果工具提供"只读模式"或"需要逐条确认"的选项，先从这个模式开始，摸清它一次会做什么再放宽。

**Q6.** 下面四样东西，哪些不能贴给 AI，为什么？(a) 一段自己写的循环 (b) `.env` 文件内容 (c) 实验原始数据 (d) 报错截图

**参考答案：** 逐个判断：

- (a) 可以贴，这是你自己的代码，不涉及他人信息。
- (b) 不能贴。`.env` 通常存放密钥与令牌，一旦泄露等于把账号交出去；需要它理解配置结构时，把值改成占位符（如 `API_KEY=***`）再贴。
- (c) 视规定与数据性质而定。未公开的实验数据、含个人信息的成绩单不能贴；公开数据集的一小段样例可以。
- (d) 可以贴，但要把窗口标题、路径里的用户名、可能出现的令牌遮掉；更好的做法是直接贴文本，报错文本比截图更容易被准确阅读。
