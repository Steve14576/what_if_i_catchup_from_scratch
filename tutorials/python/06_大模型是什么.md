# 第 06 讲 大模型是什么

> **前置**：第 05 讲（工具地图与四问）。不需要任何 Python 语法。
> **预计时间**：约 2 小时（第 2、4 节要拿自己的文件算一算）。
> **本讲回答**：它凭什么能写代码？"预测下一个 token"到底是什么意思？上下文窗口是什么、超了会怎样？它为什么编造，还那么确定？同一个问题为什么两次回答不一样？我该贴什么、贴多少？什么时候该新开一个会话？
> **本讲结束你能做到**：用自己的话解释它为什么可能错、错在哪一类地方；给一次任务估算上下文预算；按四要素写请求；判断什么时候该换新会话。

## 0. 先把期待放对

你可能已经见过这种场面：你描述需求，它一口气写出两百行，结构完整、注释齐全、看起来非常专业。你贴进项目，运行，报错；再让它修，它改了三个地方，又冒出两个新错误；来回五轮，你已经不知道这段代码究竟该长什么样了。

另一种场面：你问一个很偏的库函数，它给出一段语法完美的调用，参数名也像模像样；你照着写，运行报 `AttributeError`——那个参数根本不存在。

这两种场面都不是"它今天状态不好"，而是它的工作方式决定的。这一讲把工作方式讲清楚，你就知道该在哪一步防它。

## 1. 它是怎么生成文本的

### 1.1 一个 token 一个 token 地猜

这类模型的输出过程可以粗线概括成三步，循环执行：

1. 把你给的**全部文本**读进去（这份文本叫**上下文**，context）；
2. 算出"下一个**token**最可能是什么"，得到一个概率分布；
3. 按这个分布挑一个 token，接上去；然后回到第 1 步，直到停下来。

**token**（词元）是模型处理文本的基本单位。它不是"字"，也不是"词"，而是介于两者之间的碎片：常见词可能整体是一个 token，生僻词可能被切成两三个，一个汉字可能占一到两个 token。模型不认识"字符"，只认识 token 的编号。

由此可以推出四件事，每一件都直接决定你怎么用它：

- **它没有"查事实"这一步**。它做的是一次次"最像什么"的选择，不是查数据库。所以"某个函数有没有这个参数"这种问题，它可能给出一个"非常像"但并不存在的答案。
- **它没有"运行"这一步**。它写 `print` 不代表执行过；它说"这样就能跑通"，是续写，不是观测。
- **它不会回头自检**。单次生成是一条向前的流水线，生成完就结束了。你看到的"我再检查一下"，仍然是续写出来的一段文字，不是真的重新执行了一遍。
- **同样的上下文，两次结果可能不同**。因为第 3 步是"按概率分布挑一个"，这个挑选带有随机性。控制随机程度的参数叫**温度**（temperature）：越低越倾向于选最可能的那个，越高越发散。即使把温度调到很低，多数实现也不保证逐字相同。这一条只要求知道存在，不需要调。

### 1.2 为什么它看起来"懂"

因为训练时它读过海量的代码、文档、问答和教程。它学到的不是"事实表"，而是**模式**：什么样的需求通常对应什么样的代码、什么样的报错通常对应什么原因、什么样的函数名通常配什么参数。

这解释了它的能力分布：

| 它通常做得好 | 它通常做不好 |
|---|---|
| 常见 API 的样板代码（读写文件、发请求、解析 JSON） | 冷门库的细节参数、刚发布的版本变化 |
| 把一种格式转成另一种（CSV 转 JSON、SQL 转 pandas） | 你项目里独有的约定（命名、目录、已有工具函数） |
| 解释常见概念、给报错一个方向 | 需要运行才知道的数值（性能、精度、边界行为） |
| 补全"看起来就该这么写"的重复结构 | 跨十个文件的一致性修改（它看不到全貌，除非你全贴） |

一句话：**它擅长"常见模式的复制与变形"，不擅长"必须核对事实与运行结果的部分"。**

## 2. 上下文：它能看见的全部世界

### 2.1 上下文窗口是什么

**上下文窗口**（context window）指一次请求里模型能读到的 token 总量上限。注意"全部"两个字，它包含：

- 系统提示（产品方预置的说明，你看不到但占预算）；
- 你这次输入的全部内容（问题、贴的代码、贴的报错、贴的文件）；
- **同一会话里之前的所有对话**（包括它自己说过的错话）；
- 它这次要生成的回答（输出也算）。

超出上限时，不同产品的表现不同：有的直接报错，有的悄悄截断最早的内容，有的自动做摘要。**共同点是：你不能假定"我贴了它就读到了"。**

还有一条比窗口更容易被忽略：**上下文不是记忆**。新开一个会话，它对你之前说过的任何话一无所知；反过来，同一个会话里所有旧内容都会一直背着，包括你早先那句错误的判断。

### 2.2 先算一笔账：你的文件到底有多大

脚本 `scripts/lec06-01_demo_context.py` 实测了三种典型输入（token 数是按"中文字符 ×1.5 + 其余字符 ÷4"折算的量级估计，不同分词器差异可达两倍，要精确值必须用对应模型的 tokenizer）：

```text
样本            字符   CJK    其余     字节    token(估)
中文句           27    27     0     81        40.5
英文句           79     0    79     79        19.8
两行代码          32     0    32     32         8.0
```

三行数据说明两件事：

- 同样的"长度"，中文比英文更费 token：27 个汉字约 40 token，79 个英文字符才约 20 token。
- 代码最"便宜"：32 个字符约 8 token，因为符号和短单词在分词器里往往能合并。

再看真实文件的体量（本课程已交付的几讲）：

```text
文件                              字符   token(估)    占 8k   占 32k   占 200k
00_导览.md                      3324       3415     43%     11%     1.7%
01_一台机器到底在跑什么.md             12094      10920    136%     34%     5.5%
02_命令行与文件系统.md               13921      11096    139%     35%     5.5%
03_装Python与配环境.md            13210      10284    129%     32%     5.1%
04_Git版本控制.md               12530      10185    127%     32%     5.1%
05_工程素养与工具地图.md              10912      11619    145%     36%     5.8%
08_AI_coding工作流.md            9302       8666    108%     27%     4.3%
```

读法：

- **一讲大约 1 万 token**，占 32k 窗口的三分之一上下；
- 三讲连同你的问题与它要生成的回答，就会挤满 32k；
- 8k 窗口连一讲都放不下（136%）。

所以"把我的项目都贴给它"在多数情况下不是一个可行的策略：一个中等项目的源码轻松几十万字符，远超任何窗口。**你必须自己决定贴哪一部分。**

### 2.3 截断的算术：贴最后一段会丢掉什么

还是用第 01 讲的文件做实验：假设你只保留最后 4000 字符（大约相当于"只贴最后一段代码"），会发生什么？

```text
  原文: 01_一台机器到底在跑什么.md
  总字符 12094，只保留最后 4000 字符
  被丢掉的比例 = 66.9%
  被丢掉部分的第一句: 这是素养卷的第一讲。它属于"先见个面、混个脸熟"的范畴…
  被保留部分的第一句: oding="utf-8")…
```

两件事当场看清：

1. **67% 的内容被丢掉了**，包括"这一讲要解决什么问题"——也就是目标。
2. 保留部分从一行的**中间**开始（`oding="utf-8")`），连代码块都是断的。

这正是普通人最容易犯的错：把最贵的预算花在一大段代码上，却把"我要什么、不能动什么"省掉了。而后者往往只需要几十到几百个 token。

## 3. 为什么会编造，而且很确定

### 3.1 机制：它在续写"最像答案的东西"

模型的训练材料里有海量"人写得很确定的解释"。所以当它不知道时，它仍然会生成一段**像答案的文本**：结构完整、术语齐全、语气笃定。这不是它在骗你，而是"生成最像的内容"这个机制在正常工作的结果。

三类高发区：

- **API 与参数**：函数名像、参数名像，但那个参数不存在，或者顺序不对；
- **版本行为**：把一个旧版本的特性说成新版本还在，或者反过来；
- **"我跑过了"**：它没有运行环境，这句话是续写，不是日志。

### 3.2 语气不构成证据

人的表达里，"我不确定"是一个真实的信号；在这类工具里，"非常确定"不携带任何关于正确性的信息。判断它是否可信，只能靠**外部判据**（这是第 08 讲的核心）：

| 它的断言 | 可用判据 |
|---|---|
| "这个参数存在" | 官方文档的参数表；或直接跑一次看报错 |
| "这样改就能跑" | 你自己运行，看退出码与输出 |
| "只改了一处" | `git diff --stat` 看文件数与增删行数 |
| "这个函数对空列表不报错" | 自己造一个空列表调用一次 |
| "这个版本支持某写法" | 查对应版本文档，或 `--version` 后试跑 |

### 3.3 为什么必须由你来验证

因为**它不承担后果**。它给完就走，报错、数据错、作业被判错，都落在你身上。第 05 讲说的"工科判据是能跑、能测"，在 AI 这里尤其成立：它产出的是**候选**，不是**结果**。

## 4. 上下文工程：贴什么、怎么贴

"上下文工程"这个词听起来玄，其实只回答一个问题：**在有限的预算里，放哪些信息能让它做出你要的东西。**

### 4.1 四要素

1. **目标**：要达成什么可观察的结果。
2. **现状**：现在是什么样（完整报错、相关代码、数据样例、版本）。
3. **约束**：不能动什么（不改签名、不引依赖、不改格式）。
4. **验收**：怎么算完成（跑哪条命令、期望什么输出）。

脚本第 4 节把两种写法摆在一起做了对照（人工标注，不是模型测的）：

```text
要素                    模糊请求            四要素请求
目标（要什么结果）             改到不报错           从项目根运行能读到 data/scores.csv
现状（错在哪、环境）            未说明             报错原文 + 文件位置 + 运行目录
约束（不能动什么）             未说明             不改函数签名
验收（怎么算完成）             未说明             输出 120

  长度对比: 模糊 13 字 / 四要素 122 字
```

多写一百来个字，换来的是四个**可判定项**。这一百来个字是整个请求里最值的 token。

### 4.2 贴什么、不贴什么

| 该贴 | 为什么 | 不该贴 | 为什么 |
|---|---|---|---|
| 完整的报错（第一行到最后一行） | 类型、消息、行号、调用链都在里面 | 整个仓库 | 超出窗口，且大部分内容与问题无关 |
| 出错函数及其直接依赖（完整函数体） | 它需要看到上下文才能改对 | 截图（能贴文本就贴文本） | 文本可检索、可复制、不丢字符 |
| 数据样例 3–5 行 | 让它知道列名与格式 | 密钥、令牌、个人信息 | 一旦贴出就失去控制（第 08 讲） |
| 版本号与运行方式 | 不同版本行为不同 | 与问题无关的日志 | 占预算，还会干扰判断 |

### 4.3 先给地图，再给细节

如果任务涉及多个文件，先用三五句话说清结构：

```text
项目结构：main.py 是入口；data.py 负责读 CSV；report.py 负责输出。
现在的问题是 data.py 的 read_rows() 在空文件上报 IndexError。
下面是 data.py 里这个函数（第 12–30 行）与完整报错。
```

这段"地图"只花几十个 token，却能让它不去猜"这个函数在项目里怎么被调用"。

### 4.4 一次一件事

同时让它"修 bug + 重命名 + 补注释 + 换风格"，你会得到一大段混在一起的改动：既难审查（第 08 讲的 diff 三看会失效），出问题时也无法定位是哪一项引起的。

### 4.5 什么时候该新开会话

四个判据，命中任意一个就换：

- **话题换了**：上一个任务已经结束，旧代码只会干扰；
- **前面的结论被你推翻了**：它仍会按旧结论续写（上下文里没有"作废"这个机制）；
- **它开始"忘"约束**：反复破坏你早先说过的规则，说明关键信息被挤到后面去了；
- **预算快满了**：继续同一会话，它只能靠截断来腾地方。

换会话的代价是"它忘了之前的一切"，所以换之前把**已确认的结论**写进新会话的第一段。这与第 04 讲"提交一次再继续"是同一个思路：先固化，再前进。

## 5. 三种常见用法，各自的坑

| 用法 | 怎么问 | 怎么验 | 常见坑 |
|---|---|---|---|
| 解释代码 | 贴完整函数 + 问"它做了什么、输入输出是什么" | 对照运行结果；自己复述一遍 | 它会把"没做的事"也说成做了；解释听起来通顺但与你代码不符 |
| 生成样板 | 说清输入输出、给一两个例子、限定不用第三方库 | 跑一个最小例子；再造一个边界输入 | 只覆盖你给的例子；偷偷引入依赖 |
| 改 bug | 完整报错 + 相关函数 + 你的猜测 | 复现 → 改 → 再复现；看 diff | 顺手"优化"无关代码；把根因绕过去而不是修掉 |

三个用法有一个共同前提：**你能验收**。第 05 讲说"你不该用它的情形"里，"完全看不懂结果"排在第一条，原因就在这里。

## 6. 这一讲留下的东西

- 它是"按概率猜下一个 token"，不查事实、不运行、不自检；所以它的产出是候选，不是结果。
- 上下文 = 系统提示 + 历史对话 + 你贴的全部内容 + 它的输出；窗口有限，超出会截断或报错。
- 一讲 1 万 token 量级；三讲就能挤满 32k。**预算要优先花在"目标与约束"上，而不是贴一大段代码。**
- 它编造的三类高发区：API/参数、版本行为、"我跑过了"；语气不构成证据。
- 上下文工程的实操：四要素 + 贴原文 + 先给地图 + 一次一件事 + 该换会话时换。

下一讲把地图上"写代码的地方"展开：编辑器怎么装、解释器怎么选、断点在哪儿点，以及命令行代理到底是个什么东西。

## 小结

- 模型按 token 生成，token 是介于字与词之间的碎片；中文通常比英文更费 token。
- 它擅长常见模式的复制与变形，不擅长核对事实与运行结果。
- 上下文窗口包含系统提示、历史、你的输入与它的输出；上下文不等于记忆。
- 实测：本课程一讲约 1 万 token，占 32k 窗口三分之一；三讲即满。
- 只贴最后 4000 字符，实测丢掉 67% 的内容，且从一行中间切断——丢的往往是"目标"。
- 编造的机制是"生成最像答案的文本"；判别只能靠外部判据，不能靠语气。
- 上下文工程 = 在有限预算里放对信息：四要素、贴原文、先给地图、一次一件事、及时换会话。

## 作业

**Q1.** 用自己的话解释：为什么它说"我已经测试过了"不能当作验证？（不超过三句）

**参考答案：** 因为它生成的是"最像答案的文本"，而不是在某个环境里真的执行了一遍；它既没有你的文件，也没有你的依赖。它说的"测试过了"是续写出来的一句话，不携带任何观测结果。验证只能由你自己跑出来（退出码、输出、报错原文）。

**Q2.** 你的一个 `.py` 文件有 3 万字符，全是英文代码与注释。按本讲的量级系数估算它大约多少 token，占 32k 窗口多少；如果你还想贴 2000 字的完整报错（中文），还剩多少空间？

**参考答案：** 代码基本是 ASCII，按"其余字符 ÷4"估算：30000 ÷ 4 = 7500 token 量级。

中文报错按"中文字符 ×1.5"估算：2000 × 1.5 = 3000 token 量级。

合计约 10500 token，占 32k 的 33% 左右，还剩约 2.1 万 token 给系统提示、历史对话与它的回答。

提醒：这是量级估计，真实值取决于分词器，可能上下差一倍；结论（"还放得下，但不能再来三份"）不受影响。

**Q3.** 下面这份请求缺哪几个要素？补全它。

```text
我的程序报错了，帮我看看：
Traceback (most recent call last):
  File "main.py", line 8, in <module>
    rows = read_rows("scores.csv")
FileNotFoundError: [Errno 2] No such file or directory: 'scores.csv'
```

**参考答案：** 已有"现状"的一半（报错原文），缺三样：

- **现状补充**：文件实际在哪（例如 `data/scores.csv`）、你从哪个目录运行（项目根？`data/`？）、Python 版本；
- **目标**：希望它怎么读（"从项目根运行时应能读到 `data/scores.csv`"）；
- **约束**：不要硬编码绝对路径、不改函数签名、不引入第三方库；
- **验收**：从项目根运行 `python main.py` 输出 120 行。

补全示例："报错如上。文件实际在 `data/scores.csv`，我从项目根运行 `python main.py`，Python 3.12。请只改路径构造，不要硬编码绝对路径、不改 `read_rows` 的签名、不引入第三方库。验收：从项目根运行输出 120。"

**Q4.** 什么情况下应该新开一个会话？给三个具体信号，并说明新会话第一段该写什么。

**参考答案：** 三个信号：(1) 上一个任务已经结束、要开始一个不相干的任务；(2) 你之前给过一个后来被推翻的判断（它仍会按旧判断续写）；(3) 它开始反复破坏你早先说过的约束，说明关键信息被挤掉或淹没了。

新会话第一段写"已确认的结论"：项目结构、已经排除的方案、当前要解决的问题、验收方式。这相当于把上一轮的成果固化下来，避免重新踩坑。

**Q5.** 为什么"把整个项目贴进去"通常不是好策略？给出一个用本讲数据支撑的理由。

**参考答案：** 因为上下文窗口有限，而项目体量远大于窗口。本讲实测：本课程一讲约 1 万 token，占 32k 窗口三分之一；一个中等项目几十万字符就是几十万 token 量级，远超任何常见窗口。结果是：要么报错，要么被截断——而被截断的往往是你最需要的"目标与约束"（第 3 节实测：只贴最后 4000 字符丢掉 67% 的内容，还从一行中间切断）。

正确做法是先给结构地图，再贴与问题直接相关的那个文件/函数，并把验收方式写清楚。

**Q6.** 有人告诉你："这个模型的上下文有 20 万 token，所以我可以把整本书贴进去问细节。"这句话哪里对、哪里不对？

**参考答案：** 对的部分：窗口确实更大，能放下的内容更多；对于"通读并回答全书性问题"，大窗口确实有用。

不对或不完整的部分有三点：(1) 20 万 token 是**上限**，你还要留出系统提示、历史对话与回答的空间；(2) 放得下不等于"读得准"——信息越多，越容易出现"看到了但没用上"（关键细节被淹没）；(3) 精确性要求高的任务（某个具体参数是否存在）仍然需要外部判据，窗口大小不改变这一点。

结论：大窗口扩大了可行范围，但没有取消"挑重点 + 给验收标准"的必要性。
