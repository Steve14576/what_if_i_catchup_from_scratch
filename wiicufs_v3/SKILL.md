# WIICUFS — 写"说人话"的技术课程文档

> **WIICUFS** = What If I Catch Up From Scratch
> 一套让"没学过的人"也能看懂的技术教程写作方法。

## 两份文件怎么用（先读这个，再干活）

| 文件               | 存什么                                         | 什么时候读                 |
| ------------------ | ---------------------------------------------- | -------------------------- |
| SKILL.md（本文件） | 判据、流程、执行清单、结构契约                 | 执行全程照着走             |
| reference.md       | 正反例、完整案例、模板全文、事故实录、踩坑全表 | 写作/回查中按 →R 指针跳转 |

**唯一权威出处规则**：一条规则只允许一个全量版本。判据住本文件（一句话 + →R 指针），全量住 reference.md 的对应 R 节；R 节标题标注对应的 P 号，两文件编号一一互指。补丁永远打在权威出处上，**不允许在第二个地方换个说法再写一遍**——想引用就写"见 →R13"，不抄。发现两边口径冲突，修权威出处那一侧。

对照关系：P1–P14 ↔ R1–R14；数值验证全量 →R15；预写偏差案例 →R16；结构模板 →R17；踩坑全表 →R18；适用边界 →R19。

## 什么时候用

当你需要写一套**多讲次的技术教程**（如"从零学 X"系列），面向**没学过这个领域**的读者，要求他们能看懂、能练手、能信任内容正确性、能单纯凭借它通过正经的诸如考试，考核，科研等实际应用考验时。

典型场景：

- 给自己补一门没上过的课
- 给团队写技术入门系列
- 从零开始恶补一门甚至"不知道自己不知道什么"但又对当前极其重要的领域或课程
- 给社区写开源教程
- 期末考试(绝望)(绝对不能想当然，绝对不能漏或跳知识点)(不能口语和散装到完全用不了)(要前因后果但是不要像写小说一样卖关子讲口水话)(要系统地组织)

## 核心原则（违反即 bug）

**P1 说人话**：不用官话、不堆砌不知所云的术语。能用大白话说清的概念不用学术黑话。判断标准与正反例见 →R1。

**P2 严禁空降概念**：新术语第一次出现，当场给三样之一——① 完整解释；② 一句话"它是干啥的 + 现在只需知道这么多 + 第 N 讲细讲"；③ 明确标注"这个词现在可以跳过"。缩写首次出现给全称；公式符号逐个说是什么；术语给动机；记号给读音——高危类型全表见 →R2。**写作时作者脑里有上下文会无意识跳过定义，读者第一次见没有这个上下文**——这是长篇教程最易违反的一条。之前出现过直接写 C 语言的 `float` 的一堆性质但从来不说它是个什么。跨讲引用要回追根：第 03 讲用了第 01 讲没定义的缩写，回第 01 讲补。**不要因为它解释起来复杂就直接避开不讲，不然会漏知识点。**

**P3 配全四件套，不藏着掖着**：列出的每样东西至少配全四件套——① 它长这样（形态/例子）；② 这意味着什么；③ 怎么对待它（理解层次，按 P7 标注）；④ 现在记下来还是先跳过。不要甩一堆没解释的东西让读者自己观察，也不要因为后面会细讲就在前面故意藏着不说。不要把前面的知识点藏进作业——前面的知识点要完备，作业过饱和是正常的。讲到投入的地方，可以提炼心智模型、总结干货就做：不因为前文讲过了就不给总结，也不因为要给总结就故意把前文讲薄；讲内总结要比 AA_一览更细更全（两者不矛盾，见结构契约节）。正反例见 →R3。

**P4 字典陷阱（方向感）**：教一个东西，不能只教"是什么"，有时还要给**方向感**——什么时候会用到它、和同类怎么选、好坏的判断标准是什么。否则教程退化成让人无所措的字典：读者每个词都查得到，拼起来还是不会用。典型反例：Python 的语法语义都教了，学生写起来却瞎试拼凑、组合爆炸，不知道哪种写法好、标准在哪。正反例见 →R4。

**P5 丰富具体例子**：倾向工程/数值计算方向，能跑的代码优先。抽象概念用数值实验坐实。**已知公式/规则的问题不要用 ML 去学**——白费力气还引入误差，直接用物理/公式更精确。案例见 →R5。

**P6 每讲结尾留作业，可自验证**：数值题附答案和验算方法，代码题附能跑的验证。两条硬约束：① 答案只能用**已教过的概念**——答案里出现未教语法＝隐形空降（C++ 课程曾犯：第 05 讲答案用了第 07 讲才教的数组）；② 答案块**一律平铺**为"**参考答案**："段写在题下（先独立做再对照），**禁用 `<details>`/HTML 折叠**——折叠答案在部分渲染环境整体报错，未闭合会吞掉后续内容，曾把线代课程 01–08 全部 70 个答案块从折叠改平铺。题型展开见 →R6。

**P7 标明理解角度与深度**：每个概念不只说"是什么"，还要告诉读者"从什么角度理解、到什么程度就够"。统一四档枚举（全教程与 AA_一览共用这一套）：**要会用** / **要能推导** / **知道有这回事 + 什么时候找它** / **要建立直觉**。案例：向量空间八条公理——不背，知道是"打勾清单"，理解到"能加能缩放还在里面"的直觉就够；单纯形法——不手算，知道"顶点之间跳"+ 什么时候用它；SVD——知道"旋转-缩放-旋转"的几何直觉，不背公式。四档表与案例见 →R7。

**P8 任务驱动、应用出发**（C++ 课程血泪教训）：每讲围绕一个**能跑的小任务**展开，概念只在"任务卡壳"的那一刻引入，**不上来罗列原理**。三个配套：① 每讲开头一张"本讲怎么走"脉络图 + 每节末尾一句"下一站"；② 每讲一个可立即编译运行的成品程序开场；③ 同一课程多讲串成故事线（如 C++ 课程的"温度装置"：自检报告→存读数→超温报警）。反面症状：读者抱怨"先入为主背概念""不知道学的哪里是哪里""连要干啥都不知道就糊一脸概念"。完整重写案例见 →R8。

**P9 解释的位置和解释本身同样重要**：概念的解释如果放在读者产生疑问的位置**之后**，效果等于空降——审查时按"读者第一次遇到的顺序"走一遍，不按作者的知识组织顺序。读者自然产生的疑问（"分号干啥的""main 干啥的"）必须在疑问产生的当页或前一页就有答案。案例见 →R9。

**P10 地毯式覆盖优先于组织优雅**（C++ 课程 A36–A42 血泪教训）：写一个概念时，主线任务只决定"必须讲什么"，读者要的是"这个东西的**完整形态**"。**先地毯式列出完整形态再组织**，不许只写主线需要的部分，不许把规范/边界/习惯当"讲外内容"默认略去，更不许等读者问一个补一个。**判断"这里先理解即可后面会讲"的时机是写到具体那一讲的时候，不是现在**——现在只有"写全"和"不写（并给出理由）"两个选项，没有"故意藏一半"。也要防另一个极端：钻进特别细的特性点而忽视主干和全面性。

**完整形态六问**（每个新机制第一次教时逐问过，这是 C++ 课程被读者连环追问后总结的清单）：

| 问                             | 内容                                                     | C++ 课程被漏的实例                                    |
| ------------------------------ | -------------------------------------------------------- | ----------------------------------------------------- |
| ① 标准形态 + 每一部分的自由度 | 标准写法是什么；每一段/每个位置能不能换成别的、空着      | for 三段全是自由位（i+=2 / 多条件 / for(;;)）         |
| ② 嵌套与组合                  | 能不能嵌套自己；能不能和别的结构混着套；什么绝对不能嵌套 | if/for/while 可随意嵌套，唯独函数定义不能             |
| ③ 被控与外部打断              | 能不能被外部逻辑控制；谁让它变假/停；被控形态叫什么      | while 的标志驱动/忙等，循环体不自己前进               |
| ④ 重复与共存                  | 重复写会怎样；能不能改名复用；听谁的                     | 声明/定义/赋值三件套、遮蔽、重载、ODR                 |
| ⑤ 规范：好习惯/坏习惯         | 怎么用是对的；怎么用会埋坑                               | 循环/函数的习惯表、垃圾值纪律                         |
| ⑥ 相邻边界与对比              | 和相邻概念的区分；和读者旧语言（如 Python）的行为差异    | 函数不能嵌套 vs 控制流可嵌套；Python 参数也改不动外面 |

六问的答案不一定都进正文（有些标"认识即可"），但**必须逐问过并做出决定**——"决定不写（理由：第 X 讲再展开）"和"没想到"是两回事，决定记录在 PLAN.md。A36–A42 实录见 →R10。

**心智模型对账（防漏的根）**：作者易犯"主线任务 = 本讲内容"——任务跑通需要的才写，规范/边界/习惯被自动归为"讲外"；专家视角默认过滤"显然的东西"，但读者问的恰恰是"就这些吗？只能这样吗？"。读者不知道边界，且**不知道自己不知道什么**——没写出来的地方他问不出来，只能靠地毯式覆盖兜底；还很可能问些"没有概念""天马行空""其实不是这么讲"的问题，这很正常，要做好准备。纪律：每写完一个机制，默念"读者会问：只有这一种形态吗？"——凡答不了"它的完整形态是什么"的机制，就是漏了。

**P11 先定读者心智模型再动笔**：写作前先明确假想读者是哪一种（要简明手册的 / 完全踏入陌生领域不知道自己不知道什么的 / 基本覆盖的技术入门 / 带旧语言经验来的）。每讲写一条**认知思维链条**：学习者第一人称的自我梳理（"我以为……等等，那岂不是……"），五段骨架——① 我带着什么来；② 第一反应；③ 我会**依次**卡住的疑问（4–8 个、按遇到顺序、每个具体可答，四类必含：元问题迷失 / 旧直觉冲突 / 边界 / 防错）；④ 学完后；⑤ 钩子。每问标注由正文哪部分回答，全条约 6–14 行，具体而不嘴碎。链条是参考不是圣经：不因为迁就读者发散的思维就放弃系统化的知识组织（迁就混乱的结果是更多的混乱），但正文要顺着一条健康的认知链条走。五段写法、代入法、好坏对照见 →R11。

**P12 PLAN 是防漏的兜底**：漏知识点防不住"写的时候小心"，防得住"对着清单打勾"。所以动笔前先建 PLAN.md，把领域知识清单**穷举**（宁多勿少），每项要么分到讲次、要么写明"不写 + 理由"；之后逐讲写作、交付回查，都**反复对照这份清单**——它是防漏的兜底，不是写完就扔的草稿。不能因为说人话就漏知识点。清单模板见 →R12。

**P13 问答/破误段不是教学容器**：任何新知识（定义、定理、记号、结论）必须**先由正文系统节完整教过**；"想当然/常见问法"类段落只做**对答案与校准表态**，首句声明"本节零新知识"，逐条锚定正文系统小节；问法数量**由内容决定**，禁止固定套路数字（如一律三个、"三连击"式命名）。就地破误按 P9 守在疑问自然产生的位置附近，不攒成一节逃避。同类红线：答疑卡片（如 QnAnExperience）里解释过的内容，正文有漏必须回填正文——卡片是索引，不是正文的替身。事故实录与写法见 →R13。

**P14 口水话陷阱**：这意味着可能退化成博物馆导游。能不卖关子就不卖关子，永远有清晰的主线意识。不一定要强行编一个故事入戏（翻手册的时候很痛苦），但也不能字典式地不符合认知规律。两头极端长这样：一头是**念字典念经**——知识点按体系罗列、顺序是知识的顺序不是认知的顺序、每条自足但读者不知道自己在哪；另一头是**口水稿**——铺垫冗长、卖关子、隐喻套隐喻，读完记不住任何能动手的东西。尝试简明扼要且全面易懂，这里的 trade-off 按每讲的实际情况拿捏，但不能走极端，且要对照PLAN来防漏。边界案例见 →R14。

## 数值验证闭环（判据）

- **每一讲含数值实验的，必须跑脚本验证**——不能只靠"我觉得这个结论对"。
- 用 `uv run --with numpy python`（或 `--with scipy`）执行；非 Python 课程用等价闭环（生成源码→编译→运行→对照预期输出，C/C++ 变体见 →R15）。
- 脚本开头写"规模纪律"注释（目标 < X 秒）；纯 numpy/scipy，不依赖重型框架；每个实验 print 标题 + 实测数据 + 一句结论；print 里不用 Unicode 符号（GBK 控制台会崩，详见 →R18）。
- **多尺度**：含复杂度的结论（"X 比 Y 快"之类）至少测三个规模点，单点下不了结论。
- **重复实验**：含随机性的实验重复多次（如 50 次）取均值看趋势，单次可能是幸运/不幸。
- **跑完不删，编号归档**：移入课程 scripts/，文件名"讲次-序号_原名"（如 `lec03-01_verify_gd_loss.py`），讲义里每个实测数字都对应一个归档脚本；`__pycache__`、编译输出等中间产物跑完即删。
- 验证脚本完整范例与规范全文见 →R15。

## 预写偏差修正（判据）

预写结论 ≠ 实测结果时，不要偷偷改掉——**诚实记录**：插入"我说过头了"或"一个诚实的修正"段，三要素：① 偏差描述（预想什么、实测什么）；② 实测数据（具体数字）；③ 根本原因（为什么预想错了）。透明化偏差是教学可信度的核心——读者看到"作者也会错、错了会纠正"，比看到"永远正确"更可信。完整案例见 →R16。

## 结构契约

### 课程目录

```
课程目录/
├── PLAN.md             agent 自用的写作计划（目标/读者画像/大纲/知识清单/六问决定/每讲思维链条），
│                       不给读者，但必须先于一切存在（P12）
├── 00_导览.md          课程大纲、讲次列表、前置、学完能做什么、达标判据
├── 01_xxx.md           第一讲
├── ...
├── scripts/            验证脚本归档：文件名 = 讲次-序号_原名（见数值验证闭环）
├── NN_与X的接口.md     固定的最后一讲：和后续/应用的连接点
└── AA_一览.md          全课程附录：概念/公式/中英对照的严谨字典（编号用 AA，永不重排）
```

### AA_一览（判据）

它是**附录、字典，不是速查清单**——不必像正文那样循循善诱从头讲，但**必须和正文同样严谨：每条都要说清"是什么"**（完整、自足的定义，读者翻回来能重新明白这东西是什么）；**只说"怎么样/怎么用"不说"是什么"是鬼话，禁止**。收两类：① 关键概念/术语/缩写（中文名 + 英文/缩写 + "是什么"定义 + 首次出现讲次 + 理解层次，层次用 P7 四档枚举）；② 关键公式（符号各指什么 + 适用条件 + 出处讲次）。编号固定 `AA_` 不用数字，永不重排。首次出现的叙述性教学（动机、例子、推导）仍在对应讲正文里（P2），AA 提供措辞严谨的字典形态；P4 字典陷阱约束的是正文不许退化成甩条目，不约束 AA，但 AA 同样不许退化成只甩名字。维护：每讲交付后补入本讲新条目；第 2 遍回查时批量对账去重。模板全文见 →R17。

### 每讲的固定结构（简版）

```
# 第 N 讲：讲名
> 前置：第几讲 ｜ 预计时间 ｜ 本讲回答什么问题
> 本讲目标（学完你能）：行为化目标 2–3 条 + "目标达成 = 掌握度自测全打勾"
> 怎么学这一讲：成品→拆解→实验→作业→自测的固定循环

正文（任务驱动的成品开场，说人话，概念不空降，例子偏工程/数值）

## 本讲小结        一页纸能说清的骨架（P3：讲内总结比 AA 细）
## 掌握度自测      行为化 checklist（与本讲目标一一对应）
## 作业            可自验证：数值题附答案，代码题附能跑的验证（P6）
```

**目标行不是可选项**：每讲开头必须让读者一眼看到"这讲结束我能做出什么、怎么判断我达标了"（指向末尾自测），否则课程退化成手册。目标用行为动词（能写出/能说出/能跑出），不用"理解/了解"。模板全文见 →R17。

## 格式契约

- 公式定界符：行内用 `$...$`，块级用 `$$...$$`（不用 `\(...\)` / `\[...\]`）。
- 答案平铺（判据在 P6）：交付前 grep `<details>` 计数必须为 0。
- 引号风格：新增内容前先采样文档现有风格（全角/半角），插入后专项核对。
- 编号体系单一：不混 ①②③ 与一、二、三；改编号时同步更新正文交叉引用，改完 grep 确认无残留。
- 表格列数对齐：交付前扫一遍表格行是否有多余/缺失的 `|`（编辑器"自动对齐"会弄坏表格）。
