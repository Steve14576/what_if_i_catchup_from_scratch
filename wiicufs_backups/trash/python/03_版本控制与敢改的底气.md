# 第 03 讲 版本控制与敢改的底气：git 与 AI 结对

> 本讲是开头三讲（计算机素养）的第三讲。它讲两件事：**git 让你改坏了能退回去**，**AI 会帮你写代码但也会一本正经地编**。两件事都要落到日常动作上，不追求把命令背全。命令整条给，卡住时回来查；不读前两讲也能跟着做。

## 这一讲解决什么

先看一个你大概经历过的场面。作业脚本叫 `grade.py`，你改一版、跑一次，不行再改。为了防止改坏，你开始另存：

```text
grade.py
grade_v2.py
grade_v2_真正最终版.py
grade_最终版_改.py
```

一周后你想知道"上周三交的那版，第 12 行写的是什么"，只能挨个双击打开看；想知道"这两版到底差在哪"，只能眼睛对。

第二个场面。你让 AI 帮你改一段代码，它说"已修复"，顺手还改了你没让它动的三个地方。你跑了一下，能跑，就交了；过两天发现某个功能坏了，想回到改之前，发现**没有改之前**——你只有一个已经被它改过的文件。

这一讲就做两件事：

1. 把一个目录变成**有历史的仓库**：每改一小步就存一次，改坏了能退回任意一次，并且能看出两次之间改了什么。
2. 让 AI 干活，但**先建可回退点、只接受你审过的改动**。

先把两个词落地：

- **仓库**（repository）：一个被 git 管理的目录。它除了放你的文件，还多了一个隐藏目录 `.git`，里面存着全部历史。
- **提交**（commit）：把"此刻这些文件的样子"存成一个带说明的快照（当时所有文件内容的一份记录），追加到历史里。

## 1. 另存为 final_v2 的最后，你分不清哪版是对的

### 1.1 git 存的是"每次的样子"，不是"每次的改动"

手工另存为的问题是：每个文件都是一份完整副本，但**它们之间没有关系**。你不知道谁先谁后，也不知道哪两份能直接比较。

git 换了一个做法：每次提交，它把当时的文件内容存成一份**快照**，并记下"这次的上一次是谁"。这些提交串成一条链，就是历史。

两个常见误会先说清：

- **"它只存改动吗？"** 你可以把它理解成"每次存一份完整快照"，但 git 内部会做压缩与复用，重复的内容不会真的存很多份。对你来说，效果是：任意一次提交都能完整取回，任意两次都能比较。
- **"要联网吗？"** 不需要。`git init` 在你自己的磁盘上建仓库，全部历史都在本地。联网只在你主动和远程仓库同步时才需要（第 5 节）。

还要分清一个很容易混的地方：**保存和提交不是一回事**。`Ctrl+S` 是把编辑器里的内容写回磁盘，git 完全不知道；`commit` 是把"当前所有被跟踪文件的样子"存进历史。所以你可以保存了十次，却一次都没提交。

### 1.2 先把 git 装上

先确认装没装。在任意黑窗口里敲：

```text
> git --version
git version 2.55.0.windows.2
```

版本号不必一样。如果出现的是"不是内部或外部命令"，说明没装，或者装了但没进 PATH（和第 02 讲 `python` 找不到是同一类问题）。

**方式一：官网安装器（推荐）。** 打开 git 的官网 `git-scm.com`，下载 Windows 版安装器。安装时有四屏值得停一下：

| 安装器问什么 | 选什么 | 为什么 |
|---|---|---|
| 默认编辑器 | "Use Notepad as Git's default editor" 或 Nano | 选 Vim 的话，写提交说明时不知道怎么退出（Vim 是一个老式文本编辑器，`:wq` 是它的保存退出命令，现在不用记） |
| PATH 选项 | "Git from the command line and also from 3rd-party software" | 这样 PowerShell、cmd、VS Code 里都能直接敲 `git` |
| 换行符 | "Checkout Windows-style, commit Unix-style"（默认） | 避免同一份文件在不同系统间来回显示"整文件都改了" |
| 其余 | 默认 | 终端模拟器、HTTPS 传输这些不用改 |

安装器界面会随版本略有差异，选项名大同小异。装完后**重新打开一个黑窗口**（旧窗口拿的是旧的 PATH），再敲 `git --version` 验证。

**方式二：命令行安装（机器上有 winget）。** winget 是 Windows 自带的软件安装器（较新的 Win10 与 Win11 有），用一行命令装，不用点安装界面：

```text
> winget install --id Git.Git -e
```

**方式三：没有管理员权限（机房、学校电脑）。** 在官网上找 PortableGit 自解压包（PortableGit 是 git 的免安装版，解压就能用，不写注册表），解压到你有写权限的目录，比如 `D:\tools\PortableGit`，再把它下面的 `cmd` 目录加进**用户** PATH（加用户 PATH 不需要管理员权限）。不想配 PATH 也行：直接用包里自带的 `git-bash.exe`（一个已经配好 git 的命令行窗口），或者每次写全路径 `D:\tools\PortableGit\cmd\git.exe`。

装好之后，下面所有命令都在普通黑窗口里敲；如果只装了便携版，就在它自带的 `git-bash.exe` 里敲，命令完全一样。

### 1.3 告诉 git 你是谁

git 每次提交都要记"这次是谁提交的"。所以第一次用之前要设两行：

```text
> git config --global user.name "你的名字"
> git config --global user.email "你的邮箱"
```

`--global` 表示"对这台机器上所有仓库生效"，只需要设一次。名字和邮箱会写进每一次提交，用真名或常用昵称都行，但**别用它记密码**。

### 1.4 把目录变成仓库

找一个你要练手的目录（比如 `E:\hw\grade`），在里面打开黑窗口，敲：

```text
> git init
Initialized empty Git repository in E:/hw/grade/.git/
```

这一行说：`E:/hw/grade` 现在是一个仓库了，历史存在 `.git` 里。`.git` 是个隐藏目录，不要手动改它。

### 1.5 第一次提交

假设目录里只有 `grade.py`。先看 git 现在怎么看你这些文件：

```text
> git status
On branch master

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        grade.py

nothing added to commit but untracked files present (use "git add" to track)
```

`Untracked files` 的意思是"这个文件我看见了，但还没纳入管理"。`No commits yet` 是说历史还是空的。

`master` 是默认分支名（有的机器是 `main`，含义一样）。**分支**可以理解成"指向某次提交的可移动标签"，现在你只需要知道它存在，第 5 节会再遇到。

接下来两步：

```text
> git add grade.py
> git commit -m "first: 成绩分档脚本"
[master (root-commit) 3f9c1a2] first: 成绩分档脚本
 1 file changed, 2 insertions(+)
```

（`root-commit` 表示这是第一次提交，没有父提交；`2 insertions(+)` 是新增了两行。）

- `git add 文件名`：告诉 git"这个文件的下一次提交要包含它"。
- `git commit -m "说明"`：把已经 `add` 的内容存成一次快照。`-m` 后面是这次提交的说明，写给人看。

`3f9c1a2` 是这次提交的编号（每次都不一样）。`1 file changed, 2 insertions(+)` 是这次改了多少。

到这里，你已经有了第一个可回退点。改坏了，随时能回到这一版。

## 2. 三个区域：为什么 add 和 commit 要分两步

### 2.1 三个区域各是什么

git 把一个文件的一生分成三段：

```text
工作区（你正在编辑的文件）
   │  git add
   ▼
暂存区（"下次提交要包含什么"的清单）
   │  git commit
   ▼
版本库（已经存下来的历史，HEAD 指向最新一次提交）
```

- **工作区**：你在记事本或编辑器里看到、正在改的那些文件。
- **暂存区**：一张待提交清单。`git add` 做的事就是"把这个文件当前的改动放进清单"。
- **版本库**：已经提交的历史。`HEAD` 是"当前所在的那次提交"的名字，方便你少打一串编号。

### 2.2 status 里那些符号

`git status --short` 每一行两个字符，第一个是暂存区，第二个是工作区：

| 你看到的 | 意思 |
|---|---|
| `?? hello.py` | 新文件，git 还没管它（未跟踪） |
| `A  hello.py` | 已经 `add`，下次提交会带上（A = added） |
| ` M hello.py` | 已跟踪的文件被改了，但还没 `add`（M = modified） |
| `M  hello.py` | 改动已经 `add` 进暂存区 |
| `UU hello.py` | 两边都改了同一处，冲突还没解决（第 5 节） |

默认的 `git status` 会用红字标"未暂存"、绿字标"已暂存"；`--short` 只是把这些信息压成每行两个字符，方便看。

实测一眼：

```text
status before add: '?? hello.py'
status after add : 'A  hello.py'
```

### 2.3 一次提交只装一件事

`add` 和 `commit` 分开，不是为了麻烦你，是为了让你**能挑**：这次只提交"修了分档边界"这一件事，不把旁边顺手改的实验代码一起塞进来。

看实测的三次提交：

```text
> git log --oneline
54b1dee add grade script
c1c52df add bye line
9284f4a first: print hello
```

每一次都只做一件事。好处是：以后某一版出了问题，你能一眼看出是哪次引入的，也能只退那一次。

反例是 `git add .` 一把梭：它会把当前目录所有改动都放进暂存区，包括你还没想清楚的半成品、临时数据、`.venv`。偶尔图快可以，但交作业前别这么干。

### 2.4 一定要敲命令吗

不必须。VS Code 的"源代码管理"面板、GitHub Desktop 这类图形界面，做的是同一批事（add / commit / push）。命令的好处是：能整条复制给别人、能在服务器上跑、报错时能搜到一模一样的字样。初学建议先用命令把"动作"和"名字"对上，再用图形界面省事。

### 2.5 一个可以照着做的例题

**题目**：目录 `E:\hw\grade` 里已有 `grade.py`，内容两行：`score = 85` 和 `print("A" if score >= 85 else "B")`。要求做出三次提交：第一次提交原样文件；第二次把判定从 85 改成 90；第三次新增 `README.md`。

**解**：

```text
> cd E:\hw\grade
> git init
> git add grade.py
> git commit -m "first: 成绩分档脚本"
> 把 85 改成 90（两个地方都要改）
> git add grade.py
> git commit -m "raise pass line to 90"
> 新建 README.md，写一行"成绩分档练习"
> git add README.md
> git commit -m "add readme"
> git log --oneline
```

**验证**：`git log --oneline` 应出现三行，最新的在最上面；`git status` 应显示 `nothing to commit, working tree clean`（`working tree clean` 表示工作区没有未提交的改动）。

## 3. 改坏了，到底敲哪条命令

### 3.1 先问三个问题

git 不只是"高级撤销键"。撤销只是它最常用的一面；它还能回答"这一行是谁什么时候改的""这两版差在哪"，也能让两条改动线并行开发（分支）。本讲先把"回退"这一面用熟。

git 的回退命令之所以让人晕，是因为"改坏了"有三种完全不同的处境。先按顺序问：

1. **这次改动提交了吗？**
2. **如果提交了，推到远程了吗？**
3. **你是想"当作没发生过"（撤销），还是"保留历史、再补一次反向改动"（revert）？**

对应四条路：

| 处境 | 用什么 | 结果 |
|---|---|---|
| 改了，还没 `add` 也没 `commit` | `git restore 文件名` | 文件回到上次提交的样子，改动丢弃 |
| 已经 `add`，还没 `commit` | `git restore --staged 文件名`，再 `git restore 文件名` | 先移出暂存区，再丢弃改动 |
| 已经 `commit`，还没 `push`（推到远程，第 5 节） | `git reset --hard HEAD~1`（危险） | 历史后退一次，那次提交从当前分支消失 |
| 已经 `push` | `git revert HEAD` | 新增一次"反向提交"，历史保留 |

`HEAD~1` 的意思是"当前提交的上一级"。`--hard` 的意思是"连工作区的文件一起改回去"——**它会永久丢弃你没提交的改动**，所以敲之前先 `git status` 看一眼。

### 3.2 没提交：restore

实测。把 `hello.py` 改坏（少了一个右括号），先看 diff（diff 是"这次改了什么"的逐行对照，`-` 是原来的行，`+` 是现在的行）：

```text
> git diff -- hello.py
diff --git a/hello.py b/hello.py
index 36af514..37f25b2 100644
--- a/hello.py
+++ b/hello.py
@@ -1,2 +1 @@
-print("hello")
-print("bye")
+print("broken"
```

`-` 开头是原来的行，`+` 开头是现在的行；`@@ -1,2 +1 @@` 是"这一段的定位"：原文件从第 1 行起 2 行，变成新文件第 1 行起 1 行。然后：

```text
> git restore hello.py
> 再看文件：print("hello") 和 print("bye") 都回来了
```

`git restore` 是 git 2.23 之后的新命令；老教程里的 `git checkout -- 文件名` 做的是同一件事。

### 3.3 已提交：revert

假设你把 `hello` 改成了 `A`，还提交了，现在后悔。`revert` 不删那次提交，而是**新增一次把改动反过来的提交**（`--no-edit` 表示沿用默认的提交说明，不再打开编辑器让你写）：

```text
> git revert --no-edit HEAD
> 文件内容回到 print("hello")
> git log --oneline -2
70fa324 Revert "change hello to A"
362f223 change hello to A
```

历史里两条都在。这就是"可回退"和"删掉"的区别：别人已经拉过你的提交时，删历史会让对方出错，反向提交不会。

### 3.4 已提交未推送：reset --hard

只在"这些提交还没给别人"时用。它会移动分支标签，让最近一次提交从分支上消失。敲之前一定先 `git status`，确认没有未提交的改动；有的话先 `git stash`（把没提交的改动收进一个临时栈，之后能 `git stash pop` 取回；本讲知道它存在即可）或先提交。

### 3.5 一张决策表

```text
改坏了
 ├─ 还没 commit
 │   ├─ 只是改了文件        → git restore 文件名
 │   └─ 已经 add 了         → git restore --staged 文件名，再 git restore 文件名
 └─ 已经 commit
     ├─ 还没 push           → git reset --hard HEAD~1（先 status 确认）
     └─ 已经 push           → git revert HEAD
```

## 4. 哪些东西绝不该进仓库

### 4.1 判断标准

仓库该存"**人和工具都能重新造出来的东西**"：源码、配置模板、说明。不该存两类：

- **能重造出来的**：`.venv/`（第 02 讲建的环境）、`__pycache__/`（字节码缓存）、`*.log`。它们又大又没用，还会和别人的环境打架。
- **不能公开的**：密码、密钥（登录服务器用的密码文件或字符串）、登录令牌（token，网站发给你、代表"已登录"的一串字符）、别人的个人数据。一旦提交并推上去，删文件也没用——历史里还在。

这份名单的机器可读形式，就是仓库根目录下的 `.gitignore` 文件。

### 4.2 写一份 .gitignore

```text
.venv/
__pycache__/
*.log
data/
```

- 一行一条规则，`/` 结尾表示目录。
- `*.log` 里的 `*` 是通配符，表示"任意名字"。
- `data/` 表示整个数据目录都不进仓库（数据太大，而且常常不该公开）。

实测效果：建了 `.venv/` 和 `x.log` 之后，`git status --short` 只列出真正该管的文件：

```text
untracked (with ignore): '?? .gitignore\n?? keep.py'
```

`.venv` 和 `x.log` 根本没出现——它们被忽略了。

### 4.3 已经提交了才想起来

`.gitignore` 只对"还没被跟踪"的文件有效。如果 `.venv` 已经被提交过，光加规则不会让它消失，要先从索引里删掉（文件本身保留）：

```text
> git rm -r --cached .venv
> git commit -m "stop tracking .venv"
```

（`--cached` 表示只从 git 的跟踪清单里删掉，磁盘上的文件保留；`-r` 表示目录递归。）

如果提交过的是密钥，处理顺序是：**先去服务商那里把密钥作废、换新的**，再清历史。只删文件、换历史，密钥本身已经泄露过了。

## 5. 远程仓库：一定要 GitHub 吗

### 5.1 远程是另一份完整历史

**远程仓库**是放在另一台机器（或服务器）上的同一份仓库。三个动作：

- `git clone 地址`：把远程整个复制下来，包括全部历史。
- `git push`：把自己新增的提交送到远程。
- `git pull`：把远程新增的提交取回来，并合并进当前分支。

**不一定要 GitHub。** 远程可以是一个 U 盘上的目录、学校服务器上的目录，甚至本机另一个文件夹。只要那是一个 git 仓库，就能当远程用。下面用本地目录模拟，不需要联网也不需要账号。

两个取回命令的区别先交代一句：`git fetch` 只把远程的新内容取下来、不动你的文件；`git pull` 等于先 `fetch` 再合并。日常用 `pull` 就够。

### 5.2 用本地目录模拟一次

实测（路径做了简化）：

```text
> git init --bare E:\hw\remote.git
> git remote add origin E:\hw\remote.git
> git push -u origin master
> git branch -r
origin/master
> git clone E:\hw\remote.git E:\hw\clone
```

- `--bare` 表示"只存历史、不放工作文件"，专门用来当远程。
- `remote add origin 地址`：给这个远程起个名字叫 `origin`（惯例名）。
- `-u` 表示"记住这次推的分支"，以后直接 `git push` 就行。

### 5.3 push 被拒：不是你错了，是别人先推了

两个人从同一个远程克隆，各自改同一行。一个人先推成功；另一个人再推，会被拒绝：

```text
> git push
 ! [rejected]        master -> master (fetch first)
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
```

意思是"远程有你本地没有的提交，先取回来"。按提示（`--no-rebase` 表示用合并的方式接上远程；另一种方式叫变基，本讲不展开）：

```text
> git pull --no-rebase
```

### 5.4 冲突：git 不知道你要哪一句

如果两边改的是**同一行**，`pull` 会停下来，把两种版本都写进文件，让你选：

```text
<<<<<<< HEAD
print("from clone")
=======
print("from repo")
>>>>>>> c5a6780b4c15e2084a2e072d077bd671e76faf41
```

- `<<<<<<< HEAD` 到 `=======` 之间：你本地这一版。
- `=======` 到 `>>>>>>>` 之间：远程那一版。

`git status --short` 这时显示 `UU hello.py`（两边都改过）。

**怎么解决**：把这三行标记删掉，只留下你想要的内容（也可以两句都要，改成两句）；然后 `git add hello.py`、`git commit`。实测解决后再推就成功了。

## 6. AI 写代码时，它在做什么

### 6.1 它不是在"查资料"，是在"接下一个词"

现在常见的 AI 编码工具，底层是一个**大语言模型**（large language model，LLM）。它的基本动作只有一个：**根据前面的内容，预测下一个最可能的词**（准确说是 token，可以理解成"词的一小段"）。一次一次接下去，就成了你看到的回答或代码。

由此推出三件你会实际遇到的事：

- **它会编。** 既然目标是"最像的下一段"，那么"看起来合理"和"真的存在"就是两件事。函数名、参数、文件路径都可能被编得很像。
- **它会忘。** 它能看到的只有塞进**上下文窗口**（context window，一次能装进去的文字量）里的内容。项目里没被读进去的文件，它不知道。
- **同一句话两次结果可能不同。** 预测带随机性。

### 6.2 会动手的工具：agent 多了一个循环

只会接词的模型不能改你的文件。**agent**（能自己动手的工具形态）在模型外面加了一个循环：

```text
你的话 + 读进来的文件片段
  → 模型决定下一步动作（读文件 / 改文件 / 跑命令）
  → 工具真的执行，把结果塞回上下文
  → 模型看结果，再决定下一步
  → 直到它认为完成
```

所以它的能力边界由两件事决定：**上下文里有什么**，以及**它能不能验证自己的改动**。你不能指望它知道你脑子里那个没写进项目的约定。

## 7. AI 说"已修复"，你凭什么相信

### 7.1 三种可识别的信号

| 信号 | 长什么样 | 怎么验 |
|---|---|---|
| 编造 API | 调用一个不存在的函数、参数或字段，写法还很像真的 | 查官方文档；在 REPL 里 `help(对象)`；直接跑 |
| 编造文件与路径 | 引用一个项目里根本没有的文件，或把路径写错一层 | `dir` / `ls` 看它在不在；看它有没有真的读过 |
| 声称"我已经运行并验证" | 说"测试通过""已确认无误"，但你没有看到任何命令输出 | 自己跑一遍；要求它贴出命令与输出 |

### 7.2 一条统一规则

**跑一遍、查文档、看 diff。** 三件事至少做一件，最好都做。

- 跑一遍：能跑不等于逻辑对，但跑不起来一定有问题。
- 查文档：编造的 API 在官方文档里查不到。
- 看 diff：它到底改了哪些行，是不是只改了你说的地方。

### 7.3 一个示例 diff（不是实测，是教学样例）

假设你让它"把分档边界从 85 改成 90"，它返回的 diff 是：

```diff
--- a/grade.py
+++ b/grade.py
@@ -1,4 +1,5 @@
-score = 85
-print("A" if score >= 85 else "B")
+import os
+score = 90
+print("A" if score >= 90 else "B")
+os.system("cls")
```

这段 diff 里有两处**你没要求**的改动：加了 `import os` 和清屏。能跑，但它顺手改了无关的东西。审查时要问的不是"能不能跑"，而是"这是不是我要的那一处"。

## 8. 和 AI 协作的动作纪律

### 8.1 六步，照着做

1. **先提交。** 在让它动手之前 `git add` + `git commit`，建立一个可回退点。
2. **把任务写清。** 至少四样：目标、约束、验收标准、不许动的东西。
3. **要它先给计划。** 让它说"打算改哪几个文件、每处改什么"，你同意再动手。
4. **只看 diff 决定接受与否。** 不看 diff 就等于把代码直接交给它。
5. **自己跑验证。** 跑脚本、跑测试；它说的不算。
6. **小步提交。** 一次只接受一件事，出问题能只退那一件。

### 8.2 同一个需求，两种说法

**模糊版**："帮我把成绩脚本改好一点。"

**带验收标准版**：

```text
目标：把 grade.py 的分档边界从 85 改成 90。
约束：只改 grade.py；不要新增 import；不要改输出格式。
验收：python grade.py 输出 A（score=90），输出 B（score=89）。
不许动：README.md、data/ 目录。
先给我计划，不要直接改。
```

后一版你才能审：diff 里只要出现 `import`，就是它越界了。

### 8.3 什么不该交给它

- **密钥、密码、个人数据**：贴进对话就等同于公开。
- **不可逆操作**：删库、改系统配置、强制推送。
- **没有验收标准的"重构"**：你无法判断它有没有改坏。
- **你自己还没读懂的代码**：它改错了你也看不出来。

## 小结

- git 存的是每次提交的完整快照和一条能回退的历史；`commit` 不等于上传，本地仓库不需要联网。
- `add` 选内容、`commit` 固化，两步分开是为了让一次提交只做一件事。
- 改坏了先问"提交了吗、推送了吗、要撤销还是反向"；未提交 `restore`，已推送 `revert`。
- `.gitignore` 挡住能重造的与不能公开的；已经提交过要先 `git rm --cached`。
- 远程可以不是 GitHub；`push` 被拒是远程更新了，先 `pull`；冲突就是两份都写进文件，删标记、留想要的、再提交。
- AI 在接下一个 token，agent 在"读—改—跑"的循环里；它会编、会忘。
- 信不信它，看三件事：跑一遍、查文档、看 diff。

## 作业

**Q1.** 用一句话说明 git 和网盘（OneDrive、百度网盘）的区别。为什么"我每周把文件夹压缩上传一次"不能替代 git？

**参考答案：**
网盘存的是"每次上传的一份份文件副本"，副本之间没有关系；git 存的是"每次提交的快照 + 它们之间的父子关系"，所以能取回任意一次、能比较任意两次、能看出是哪次引入的问题。每周压缩上传只能回答"这一周的样子"，回答不了"上周三第 12 行是什么"和"这两版差在哪"。

**Q2.** 你改了 `grade.py`，执行了 `git add grade.py`，然后又改了同一个文件。现在 `git commit` 会提交哪一版？

**参考答案：**
提交的是 `add` 那一刻放进暂存区的那一版，不是文件现在的最新版。第二次改动还在工作区，`git status --short` 会同时显示 `M  grade.py`（暂存区有改动）和 ` M grade.py`（工作区又有新改动）。要提交最新版，需要再 `git add` 一次。

**Q3.** `git status --short` 输出 `?? data.csv`、` M grade.py`、`A  README.md`。分别是什么意思？

**参考答案：**
`?? data.csv`：新文件，还没被 git 跟踪；` M grade.py`：已跟踪的文件被改了，改动还没放进暂存区；`A  README.md`：已经 `add`，下次提交会带上。

**Q4.** 下面三种"改坏了"，各应敲哪条命令？① 刚改完文件，还没 `add`；② 已经 `add`，还没 `commit`；③ 已经 `commit` 并 `push` 到远程。

**参考答案：**
① `git restore 文件名`；② 先 `git restore --staged 文件名`，再 `git restore 文件名`；③ `git revert HEAD`（新增一次反向提交，保留历史）。③ 不能用 `reset --hard`，那会让已经拉过你提交的人出错。

**Q5.** 为一个 Python 项目写 `.gitignore`，至少覆盖：虚拟环境、字节码缓存、日志、数据目录。写出四条规则并说明各自的含义。

**参考答案：**

```text
.venv/
__pycache__/
*.log
data/
```

`.venv/` 是第 02 讲建的项目环境，能重建且很大；`__pycache__/` 是字节码缓存，能自动重建；`*.log` 是运行日志，会不断变长；`data/` 是数据目录，通常很大且可能不该公开。四条都是"能重造"或"不该公开"的东西。

**Q6.** 你误把 `.venv` 提交并推送了。现在加 `.gitignore` 还有用吗？正确的补救步骤是什么？

**参考答案：**
对已经被跟踪的文件，后加 `.gitignore` 不起作用。要先从索引里删掉（文件本身保留）：`git rm -r --cached .venv`，然后 `git commit -m "stop tracking .venv"`，再 `git push`。如果误提交的是密钥，先去服务商处作废并更换密钥，因为历史里已经泄露过了。

**Q7.** 你 `git push` 得到 `! [rejected] master -> master (fetch first)`。这说明什么？下一步敲什么？

**参考答案：**
说明远程有你本地没有的提交（别人先推了）。下一步 `git pull --no-rebase` 把远程的取回来；若改的是不同文件会自动合并，若改到同一行会产生冲突，按第 5.4 节处理后再 `push`。不要用 `push -f`（`-f` 是强制推送，会用自己的历史覆盖远程，别人的提交可能丢）。

**Q8.** 冲突文件里出现 `<<<<<<< HEAD`、`=======`、`>>>>>>>` 三行。它们各表示什么？解决冲突的完整动作是什么？

**参考答案：**
`<<<<<<< HEAD` 之后到 `=======` 之前是你本地这一版；`=======` 到 `>>>>>>>` 之间是远程那一版。解决：删掉这三行标记，只留下你想要的内容（或把两边合并成想要的样子），保存；然后 `git add 文件名`、`git commit`，最后 `git push`。`git status --short` 在冲突未解决时显示 `UU 文件名`。

**Q9.** AI 说"我已经修好并测试通过了"。写出三种你能自己做的核验动作，并说明各自能抓到什么问题。

**参考答案：**
① 自己跑一遍：抓"根本跑不起来"和"输出不对"；② 查官方文档或 `help()`：抓编造的函数、参数、字段；③ 看 `git diff`：抓"顺手改了无关文件"和"没改到你说的地方"。三件事分别对应运行、事实、范围，缺一不可。

**Q10.** 把这句话改写成一份 AI 能照着做、你也能验收的任务描述："帮我把这个脚本整理一下。"

**参考答案：**
示例：目标——把 `grade.py` 里的分档逻辑抽成一个函数 `grade_of(score)`，输入分数、返回等级；约束——只改 `grade.py`，不改输出文字，不新增第三方包；验收——`python grade.py` 对 90 输出 A、对 89 输出 B、对 60 输出 C；不许动——`README.md`、`data/`；先给计划，不要直接改。关键是四样齐全：目标、约束、验收标准、不许动的东西。
