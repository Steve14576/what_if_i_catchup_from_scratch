# WIICUFS — 写“说人话”的技术课程文档

> **WIICUFS** = What If I Catch Up From Scratch。
> 它服务于多讲次的技术教程：让“没学过的人”也能看懂、能练手、能信任内容正确性，并能拿去应付考试、考核、科研或实际应用。

## 这两份文件分别干什么

- **SKILL.md（本文件）**：把写作思想、判断依据、格式与执行要求完整讲清。读完它，应当知道课程要怎么设计、每一讲要怎么写、PLAN 怎么填、怎样检查漏项；不需要跳到别处才能理解规则。
- **reference.md**：把这些要求做给你看。里面放正反例、已经填好的小片段、真实事故、验证脚本和环境踩坑。它不是把本文件换句话说一遍；读到“这到底长什么样”时去对照即可。

同一个意思在两份文件出现不是问题：本文件负责讲明白，reference 负责示范。不要为了形式整齐把当场能讲清的内容砍成编号和索引。

## 什么时候用

当你需要写一套**多讲次的技术教程**（如“从零学 X”系列），面向**没学过这个领域**的读者，要求他们能看懂、能练手、能信任内容正确性、能单纯凭借它通过正经的诸如考试，考核，科研等实际应用考验时。

典型场景：

- 给自己补一门没上过的课；
- 给团队写技术入门系列；
- 从零开始恶补一门甚至“不知道自己不知道什么”但又对当前极其重要的领域或课程；
- 给社区写开源教程；
- 期末考试（绝望）（绝对不能想当然，绝对不能漏或跳知识点）（不能口语和散装到完全用不了）（要前因后果但是不要像写小说一样卖关子讲口水话）（要系统地组织）。

## 核心原则（违反即 bug）

### 1. 说人话

不用官话，不堆砌不知所云的术语。能用大白话说清的概念不用学术黑话。

“说人话”不等于不正式，也不等于只讲感觉。正式文本仍须完备、自包含、边界清楚；只是要把读者真正会问的“它到底是什么”“我为什么现在要学它”说出来，而不是用一句标题式的学术话把问题盖过去。

不是说你用了比喻或者”你以为的意思到了“就是安全地”说人话了“，有时候那种极限失真浓缩动词名词的，人类压根不这么说的黑话比喻，仿佛只会说单字词，仿佛只会说口令的情况，更让人晕眩和反胃。你的听众是个活人，大概率还是个天真但认真的大学生乃至高中生，不是另一个agent或者某个执行器，更不是象征性接受信息的社畜，信息理解不到位吃亏和难受的是自己。那种极限浓缩黑话是绝对的反面教材，很多时候即使是真正的论文都不敢这么写，更何况我们这个的语言柔顺度和完备度几乎是要远高于论文，因为我们是教程。你想想那些天真但认真的高中生和大学生。[s]()

### 2. 严禁空降概念

新术语第一次出现，当场给三样之一：

1. 完整解释；
2. 一句话说明“它是干啥的 + 现在只需知道这么多 + 第 N 讲细讲”；
3. 明确标注“现在可以跳过”。

重要术语，重要专有名词，重要缩写，首次出现要给中英文全称；公式里每个符号要说是什么；术语不能只有名字，还要说为什么需要它；记号要给读音或可读的叫法。写作时作者脑里有上下文，会无意识跳过定义；读者第一次见没有这个上下文——这是长篇教程最易违反的一条。之前出现过直接写 C 语言的 `float` 一堆性质，却从来不说它是什么。

跨讲引用要回追根：第 03 讲用了第 01 讲没定义的缩写，就回第 01 讲补定义。不要因为一个概念解释起来复杂就直接避开不讲，不然会漏知识点。

### 3. 不藏着掖着，也不要无慈悲陈述

列出的每样东西至少要让读者得到四样东西：

- **它长这样**：给出标准形态、一个小例子或可观察的形式；
- **这意味着什么**：把形式翻译成人话，说明行为或后果；
- **怎么对待它**：它是工具、清单还是直觉，要会用、会推导还是先知道有这回事；
- **现在怎么办**：现在要记住、要动手，还是先放一个钩子后面再说。

不要直接甩一堆没解释的东西让读者自己观察。不要因为后面会细讲，就在前面故意藏着不说。不要把前面的知识点藏进作业：正文的知识点要尽可能完备，然后再进入作业。正文如果脱离实际例子不好讲的话那就实际例子多来几个讲出来，而不是藏进作业。例题是例题，作业是作业。作业过饱和了是正常的。

很多时候可以总结提炼心智模型、总结干货，那就做；不因为前文讲过了就不给，也不因为要给心智模型而故意把前文讲薄。讲内总结和 AA_一览不矛盾：因为它在讲内，应该更细、更全、更能串起这一讲。

### 4. 防止退化成字典：给知识方向感

很多东西出现时，不只是定义，还要出现方法论或心智模型：什么时候怎么用、和什么相邻、怎样判断好坏。否则会退化成让人无所适从的字典。

一个典型例子是 Python 这类语义基础：学生把变量、循环、函数都学过了，写起来还是瞎试拼凑，组合爆炸，不知道哪种写法好、标准在哪里。教程要帮助读者建立这种对知识的方向感，而不是只让他认识词条。

### 5. 丰富具体例子

倾向工程/数值计算方向，能跑的代码优先。抽象概念尽量用数值实验坐实。读者看到具体输入、输出、误差、反例，往往比看到“高复杂度方差大”这一句更明白。

能用物理或公式准确说明的地方，就用物理或公式。

### 6. 每讲结尾留作业，而且必须可自验证

数值题附答案和验算方法；代码题附能跑的验证；概念题给判断与解释；综合题给参考思路。题目尽量告诉读者“这在真实开发/计算里是干什么的”。

两条硬约束：

1. 答案只能用**已教过的概念**。答案里出现后面才教的语法，就是隐形空降；C++ 课程曾犯过第 05 讲答案用了第 07 讲才教的数组。
2. 答案块一律平铺为“**参考答案：**”段，写在题下，供读者独立做完后对照；**禁用 `<details>`/HTML 折叠**。折叠答案在部分渲染环境会整体报错，未闭合还会吞掉后续内容。线代课程 01–08 曾把 70 个答案块从折叠改成平铺。

### 7. 标明理解角度与深度

每个概念不只说“是什么”，还要告诉读者“从什么角度理解它”“理解到什么程度就够”。不要让读者看完后还在问：要背吗？要能推导吗？只要知道有这回事吗？

- **理解角度**：它是工具（要会用）、清单（遇到时打勾验证）还是直觉（建立感觉就行）？
- **理解深度**：要能推导？要能复述？只要知道“有这回事 + 什么时候找它”？
- **案例**：向量空间八条公理不必死背；知道它是一份“打勾清单”，并理解“能加、能缩放、而且操作后还在里面”的直觉即可。单纯形法不必手算，但要知道“在顶点之间跳”的直觉和什么时候会用。SVD 要知道“旋转—缩放—旋转”的几何直觉，不必背公式。

### 8. 鼓励任务驱动、应用出发

每讲可以**但不强求**围绕一个**能跑的小任务**展开。这个小任务可以人为构造一点，否则涵盖不到所有知识点。有时可以放掉这个小任务，或者把这个小任务放到后验的多个作业而不是一开始就围绕一个单一的小任务展开，否则单一的小任务很难涵盖到所有知识点。对于这个小任务概念只在“任务卡壳”的那一刻引入，**不上来罗列原理**。三个配套：

1. 每讲开头一张“本讲怎么走”脉络图；每节末尾一句“下一站”，让读者看漏了随时能定位；
2. 每讲先给一个可立即编译运行的成品，先看到“我能做出什么”，再拆零件；
3. 同一课程的多讲尽量串成一条故事线，例如 C++ 课程的“温度装置”：自检报告 → 存读数 → 超温报警。

反面症状是读者说：“先入为主背概念”“不知道学的哪里是哪里”“连要干啥都不知道就糊一脸概念”。
另一个反面症状是全面退化为“小任务冒险故事书”而完全丧失手册性质， 想要什么还得自己总结自己抓。这就是教程本身不到位，因为明明可以写清楚。

### 9. 解释的位置和解释本身同样重要

概念解释如果放在读者产生疑问的位置**之后**，效果等于空降。审查时按“读者第一次遇到的顺序”走一遍，不按作者的知识组织顺序走。读者自然产生的疑问，例如“分号干啥的”“main 干啥的”，必须在疑问产生的当页或前一页有答案。

### 10. 地毯式覆盖优先于组织优雅

主线任务只决定“必须讲什么”，但读者还要知道一个东西的**完整形态**：标准形式之外每段能不能换、能不能嵌套、能不能被外部控制、重复了会怎样、什么是好习惯坏习惯、和相邻概念边界在哪里。

先地毯式列出完整形态，再组织正文。不许只写主线需要的部分，不许把规范/边界/习惯当“讲外内容”默认略去，更不许等读者问一个补一个。判断“这里先理解即可、后面会讲”的时机，是写到具体那一讲时，不是现在；现在只有“写全”和“决定不写 + 写明理由”两个选项，没有“故意藏一半”。

也防另一个极端：钻特别细的特性点，反而忽视主干和全面性。

每个新机制（语法、概念、工具）第一次教时，逐项过**完整形态六问**：

| 问                             | 要问什么                                               | C++ 课程中曾被漏的形态                                  |
| ------------------------------ | ------------------------------------------------------ | ------------------------------------------------------- |
| ① 标准形态 + 每一部分的自由度 | 标准写法是什么；每一段/位置能不能换、能不能空着        | `for` 三段都是自由位：`i += 2`、多条件、`for(;;)` |
| ② 嵌套与组合                  | 能不能嵌套自己；能不能和别的结构混套；什么绝对不能嵌套 | `if/for/while` 可嵌套，函数定义不能                   |
| ③ 被控与外部打断              | 能否被外部逻辑控制；谁让它停；这种形态叫什么           | `while` 的标志驱动、忙等                              |
| ④ 重复与共存                  | 重复写会怎样；能否改名复用；听谁的                     | 声明/定义/赋值、遮蔽、重载、ODR                         |
| ⑤ 规范：好习惯/坏习惯         | 怎样用对；怎样用会埋坑                                 | 循环/函数习惯、垃圾值纪律                               |
| ⑥ 相邻边界与对比              | 与相邻概念如何区分；与读者旧语言行为有何不同           | 函数不能嵌套 vs 控制流可嵌套；Python 参数也改不动外面   |

六问的答案不一定都进正文，有些可以标“认识即可”；但写作时必须逐问过并做出决定。**“决定不写”和“没想到”是两回事。**决定记录在 PLAN.md。

作者最容易犯的错是“主线任务 = 本讲内容”：任务跑通需要的才写，规范/边界/习惯被自动归为“讲外”；专家也会默认过滤“显然的东西”。但读者恰恰会问“就这些吗？只能这样吗？”。而且读者不知道自己不知道什么，没写出来的地方他问不出来，只能靠地毯式覆盖兜底。很可能还会问“没有概念的”“天马行空的”“额话其实不是这么讲的”问题，这很正常，要做好准备。

### 11. 先定读者心智模型再动笔

写作前先明确假想读者是谁：要简明手册的、完全踏入陌生领域且不知道自己不知道什么的、需要基本覆盖的技术入门读者、还是带旧语言经验来的读者。

每一讲都写一条该讲假想学生的**认知思维链条**。它是学习者第一人称的自我梳理（“我以为……等等，那岂不是……”），不是作者用第三人称替他做总结。统一五段：

1. **我带着什么来**：旧心智模型 + 已有工具，写成“我以为 X 是……”式旧直觉，不是能力清单；
2. **第一反应**：看到任务时的期待/误判/抗拒，常含一个会错的直觉；正文要有对应的破误段；
3. **我会依次卡住的疑问**：4–8 个，按遇到顺序，每个具体可答；必须覆盖元问题迷失（“我该往哪想”）、旧直觉冲突（“加法逐元素，乘法凭什么不是”）、边界（“只能这样吗”）、防错（“我会不会栽在 X”）；每问标出正文哪一部分回答；
4. **学完后我的新心智模型**：学习者自己能说出口的一句话；
5. **还悬着的钩子**：通往下讲。

每问一行，全条约 6–14 行，具体而不嘴碎。思维链条是写作前的预测和写完后的对账工具，**不是要求正文按读者脑中每个跳跃逐问展开的脚本**。正文仍要系统地组织知识；任务主线决定读者先看到什么，完整形态六问决定一个机制该讲全什么。迁就混乱会制造更多混乱，但不照顾读者的认知链条又会空降。

对带旧语言经验的读者，PLAN 还要列“误会清单”：例如 Python 背景可能以为“参数能把值还回去”“同名函数后写覆盖前写”“for 是遍历不是三段式”。每条误会都应在课程正文有对应的打破误会段，不默认读者会自己纠正。

### 12. PLAN 是防漏的兜底

不能因为说人话就漏掉知识点。写前要有前置 PLAN，把领域知识清单尽可能穷举；写作时和交付前反复对照。PLAN 不是写完就扔的草稿，而是防漏的兜底。

### 13. 问答/破误段不是教学容器

任何新知识（定义、定理、记号、结论）必须先由正文系统节完整教过。“想当然/常见问法”类段落只做对答案与校准表态，首句声明“本节零新知识”，并逐条锚定正文系统小节。问法数量由内容决定，禁止固定套路数字，例如机械地凑“三连击”。

就地破误按原则 9 守在疑问自然产生的位置附近，不要攒成一节逃避。答疑卡片（如 QnAnExperience）里解释过的内容，如果正文有漏，必须回填正文；卡片是索引，不是正文的替身。

### 14. 口水话陷阱

这意味着可能退化成博物馆导游。永远记住，永远要系统，永远要不啰嗦。能不卖关子就不卖关子。永远有清晰的主线意识。不一定要强行编一个故事来入戏，这让翻手册的时候很痛苦，但是也不能字典式地不符合认知规律地直接强硬陈列。尝试做到简明扼要且全面易懂，这里面的 trade off 按每讲的实际情况拿捏，但不能走极端念字典念经或者极端口水稿。无论如何，要对照 PLAN 来防漏。

### 15. 台账陷阱

更加专注内容本身而不是指来指去，不是退化成对账。这只是你想着，能说清楚就说清楚，都不见得会把对账做这么多和乱。读者其实不关心你怎么对账的。重点在你写正文要说人话说清楚。读者不希望看到你写的教程正文里面，你忙前忙后的，然后一大堆对账一样的东西把知识内容淹没。这不是说禁止你引用索引指来指去(否则那些关于流程正义的要求就白写了)，而是说，并且在这个基础上，读者更关心的是”这是什么知识“、”ok既然指了引用那么这意味着什么“，而不是”我的agent做到了第几号引用好厉害啊“、”我的agent忙前忙后但是然后呢，到头来这个引用是什么意思我怎么看不懂“。能说人话，写清楚，才叫厉害。

```markdown
  我带着什么来 / 第一反应 / 我会依次卡住的 4–8 个具体疑问 [→答题位置] / 学完后 / 钩子
- 强制出现至少 1 条“不知道自己不知道”型问题，包括但不限于“没有概念”“天马行空的”“额话其实不是这么讲的”“一看就知道你没学过”的问题
- 强制出现至少 1 条“想当然归纳”型问题，例如“想当然地可以这么说吗”“我可以这么归纳吗”“可以但没必要”“你直接记住……就行”“对，你这个见解很独到但是要小心哪些边界不能用”“太小众了，我们不这么说”“你能记住就好”“别这么记，会绕晕的”

## 五、两遍走状态
- 第 1 遍逐讲：每讲的预写 / 实测 / 空降检查 / 格式自检状态
- 第 2 遍回查：地毯清单逐项打勾结果、读者顺序通读发现的漏、思维链条疑问答案核对结果
```

PLAN 里的两类问题只是在预测读者会怎样想、帮助正文补足边界与破误；**它们不授权把新知识塞进问答段。**正文的响应仍受原则 13 约束。

### 第 1 遍：逐讲写作

1. 预写讲义初稿：每讲先定“本讲的任务”再定内容；每个新机制按完整形态六问展开。
2. 写验证脚本，实跑验证预写结论。Python 之外同样成立：C/C++ 课程可走“生成源码 → 编译 → 运行 → 对照预期输出”。
3. 对照预想与实测：一致就嵌入实测数据；偏差就插入“我说过头了”段，必须写清偏差、实测和根因。
4. 概念空降检查：逐段回查新术语首次出现处是否给了定义；按读者顺序查解释是否放在疑问产生之后；检查作业答案是否用了未教概念。
5. 格式自检：`<details>` 残留计数为 0；引号风格一致；编号体系单一。
6. 数据维护检查：表格/实测值若有唯一总表，改动后确认小结、自测等引用它的位置没有留下旧数值。
7. 归档验证脚本（移入课程 `scripts/`，加编号前缀，不删）；把本讲新概念/公式补进 AA_一览；回填 PLAN.md 状态；同步导览页与系列总览（如果有）。

### 第 2 遍：交付前全课程回查

1. 对照 PLAN.md 地毯式覆盖清单逐项打勾；没写上的要么补，要么给出“不写”的理由。
2. 按读者顺序从头走一遍，查漏，尤其“规范/边界/习惯/被控形态”这类主线外内容。
3. 对照每讲思维链条：链条每一个疑问是否都能在正文找到答题小节，且答题位置不晚于疑问自然产生处；骨架是否齐全（第一人称 / 4–8 问 / 五段）。
4. 回查问答/破误段：其中每个结论是否已经由正文系统节完整教过；全文是否留下“三连击”式凑数命名。
5. AA_一览批量对账去重：每条“首次出现讲次”与正文交叉核对；脚本与讲义实测数字是否能互相回溯。
6. 大量写作后专项自查错别字；交付前 diff 扫一遍新增文本。

## 数值验证闭环

每一讲含数值实验的，必须跑脚本验证，不能只靠“我觉得这个结论对”。验证不是只验证最初预写的代码：重写、补漏、作业答案里新加的每一段代码也要实测。

脚本应当：

- 开头写“规模纪律”注释（目标 < X 秒）；
- 尽量纯 numpy/scipy，不依赖重型框架；
- 每个实验有 print 标题、实测数据和“→ 结论”一句话；
- 让“预期 vs 实测”写进 print，例如 `expect 5050`，跑完一目了然哪里偏差；
- 跑完不删，编号归档进课程 `scripts/`；文件名为“讲次-序号_原名”，例如 `lec03-01_verify_gd_loss.py`；同一讲内按编写顺序编号，原名完整保留；讲义每个实测数字都能对应一个归档脚本；
- `__pycache__`、编译输出、临时日志等中间产物跑完即删，不进归档。

复杂度结论必须多尺度实测，至少三个规模点；随机实验必须重复多次看稳定性，单次可能只是幸运或不幸。使用 `uv run --with numpy python`（或 `--with scipy`）运行，保持环境隔离。

## 预写偏差修正

预写结论 ≠ 实测结果时，不要偷偷改掉，要诚实记录。在讲义中插入“我说过头了”或“一个诚实的修正”段，包含：

1. 偏差描述：预想什么，实测什么；
2. 实测数据：具体数字；
3. 根本原因：为什么预想错了。

透明化偏差是教学可信度的核心。读者看到“作者也会错、错了会纠正”，比看到“永远正确”更可信。

### AA_一览.md 的格式与要求

AA_一览是**附录、字典，不是速查清单**。它不必像正文那样循循善诱从头讲，不重复铺垫、动机、推导过程；但必须和正文同样严谨，每条都说清“是什么”，给完整、自足的定义。只说“怎么样/怎么用”不说“是什么”是鬼话，禁止。

收两类内容：

1. 关键概念/术语/缩写：中文名 + 英文名/缩写 + 说清“是什么”的定义（不是用法提示）+ 首次出现讲次 + 理解层次；
2. 关键公式：公式本体 + 符号各指什么 + 适用条件 + 出处讲次。

编号固定用 `AA_`，不用数字；无论后续加多少讲，这个文件不需要重排编号或换位置。首次出现的叙述性教学仍在对应正文里，AA 提供措辞严谨的字典形态；正文不许退化成 AA 式甩条目，AA 也不许退化成只甩名字。每讲交付后补入本讲新条目，第 2 遍回查时批量对账。

```markdown
# 课程名——附录：关键概念·公式·中英对照字典（AA）

## 一、概念与术语（中英对照）
| 概念（中文） | 英文/缩写 | 定义（说清“是什么”） | 首次出现 | 理解层次 |
|---|---|---|---|---|
| 线性规划 | Linear Programming（LP） | 目标函数和约束都是线性的优化问题 | 第 01 讲 | 要会用 |
| [本讲新概念] | [英文/缩写，首次出现必给全称] | [说清“是什么”的完整定义，不是用法提示] | 第 XX 讲 | 要能推导/知道有这回事/建立直觉 |

## 二、公式
| 公式 | 符号各指什么 | 适用条件 | 出处讲次 |
|---|---|---|---|
| [公式本体] | [逐个符号：x 是…，c 是…] | [什么时候能用/什么时候不能用] | 第 XX 讲 |
```

## 多课程并行时的文件边界

- 所有操作限定在当前课程目录内；
- 严禁修改全局 README.md 或 JOURNAL.md（其他并行任务在维护）；
- 只改课程专属文档：课程 00_导览.md、AA_一览.md、PLAN.md，以及系列总览（如果有）；
- 验证脚本建在课程目录内，不污染工作区根目录；跑完归档进课程 `scripts/`。

## 常见失败形态（写作内容侧）

- 只靠“我觉得对”就交付，跳过验证；
- 跑完删脚本，断掉“实测数字怎么来的”的证据链；
- 偷偷改掉预写偏差，读者看不出哪里可能踩坑；
- 空降概念，直接不眨眼写陈述句，默认读者认识每个专有名词；
- 罗列原理开场，不先展示“学完能做出什么”；
- 只写主线、挤牙膏，等读者问一个补一个；
- 没有 PLAN 就动笔；
- 让答疑卡片替代正文；
- 讲得很投入却忘了正式定义概念，读者抓不到边界，理解退化成模式识别；
- 把思维链条写成许愿：一个笼统问题、第三人称总结、没有按顺序的具体卡壳；
- 把问答/破误段当教学容器；
- 在规则已知的地方用 ML 去学已知公式。

运行环境、Markdown 维护、PowerShell/WSL 的具体踩坑和修复，见 reference.md 的实际记录；需要处理那类问题时，按记录中的症状判断，不要凭记忆乱猜。

## 格式约定

- Markdown 行内公式用 `$...$`，块级公式用 `$$...$$`，不用 `\(...\)` / `\[...\]`；
- 新增内容前采样课程文件既有引号风格，避免半角/全角混用；
- 编号体系单一，改编号时同步更新正文交叉引用；
- 表格长文本列须能换行，编辑器自动对齐后要检查是否多插或少插 `|`。
